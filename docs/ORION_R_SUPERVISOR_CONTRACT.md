# Контракт supervisor для ORION-R

**Срез аудита:** 2026-11-09, рабочее дерево ORION-Rust. Документ сравнивает экспериментальный `orion-rust/src/lifecycle.rs` со штатным `apps/desktop/runtime/launcher.cjs`; это спецификация поведения для дальнейшей реализации, не разрешение переключить запуск.

## Дополнение: экспериментальные изменения после аудита

В отключённом `lifecycle.rs` добавлены классификация кодов `pg_ctl status`, проверка каталога и порта подключённого PostgreSQL перед изменениями, общий путь остановки и Job cleanup, а также восстановление частично созданных ролей. Скрипты используют Prisma из каталога API через `createRequire`. Проверены синтетические коды процессов, обработка ошибки остановки и mock частичного provisioning; отдельно подтверждена загрузка Prisma из подготовленного packaged runtime. Полный экспериментальный lifecycle и работа с реальным PostgreSQL этими тестами не проверены. Прямой путь остаётся отключённым, LAN и протокол подписанных обновлений не перенесены. Таблица ниже сохраняет исторические замечания аудита и требует пересмотра перед использованием как текущего перечня дефектов.

## Текущая граница

Подтверждённый запуск ORION-R — команда `supervise`, которая запускает упакованный `launcher.cjs` внутри Windows Job Object. В `lifecycle.rs:55-58` публичная `supervise_direct` пока всегда отказывает с сообщением использовать `supervise-launcher`; экспериментальная реализация `:61-142` помечена `allow(dead_code)` и штатным путём не вызывается. Поэтому ниже описанные отличия — аудит кода и требований, а не результат запуска прямого Rust lifecycle.

`apps/desktop/runtime/launcher.cjs` остаётся источником поведения. `main()` (`:220-263`) проверяет изоляцию, выбирает payload, готовит конфигурацию, запускает/проверяет PostgreSQL, создаёт роли, выполняет Prisma migrations и строит окружение API. Затем `superviseApi()` (`:309-363`) управляет готовностью, пробным payload, повторным запуском при смене режима и отказоустойчивым возвратом LAN host в local. Обработчик ошибок загрузки (`:365-380`) откатывает не прошедший проверку payload и повторяет запуск.

## Требуемый контракт

Прямой Rust lifecycle можно считать заменой launcher только после выполнения и проверки всех пунктов:

1. **Изоляция профиля и runtime.** До записи конфигурации или запуска процессов разрешать только целевые пути текущей упаковки, учитывать junction/symlink и расширенные Windows-пути, отказывать при пересечении данных с Classic-профилями. Убедиться, что API, PostgreSQL и диагностические порты допустимы, различны и не совпадают с запрещёнными портами. Соответствующая база поведения: `launcher.cjs:12-84`.
2. **Подготовка путей.** Для PostgreSQL и документов применять те же правила ASCII-путей и приватных каталогов, что `ascii-path.cjs` через `launcher.cjs:9,55-63,223-230`. Не передавать проблемный Unicode/extended путь в `initdb` и `pg_ctl` без эквивалентного проверенного преобразования.
3. **Конфигурация и секреты.** Читать совместимый `local-runtime.json`; при отсутствии конфигурации и существующего кластера создавать уникальные секреты безопасно и без перезаписи конкурентного файла. При наличии кластера без конфигурации — fail closed и не изменять данные. Сохранять и валидировать все нужные поля и формат. Baseline: `launcher.cjs:139-148`.
4. **Идемпотентный PostgreSQL lifecycle.** Инициализировать кластер только при отсутствии `PG_VERSION`; всегда очищать временный парольный файл; перед стартом проверять, не работает ли кластер уже (`pg_ctl status`); слушать только localhost; корректно отличать ошибку запуска от уже активного кластера. Baseline: `launcher.cjs:150-167`.
5. **Provisioning и миграции.** Создавать БД и роли идемпотентно при частично завершённом предыдущем запуске; сверять не только наличие `orion_app`, но и `orion_system`, членство, права схемы и default privileges. Затем выполнять именно упакованный `prisma migrate deploy` с ожидаемой схемой и корректным администраторским URL. Baseline: `launcher.cjs:169-196`.
6. **Совместимое окружение API.** Передавать параметры сборки, API и web dist, каталоги данных, секреты, режим узла, shell/runtime provenance и пути управления PostgreSQL. Не наследовать случайные переменные, способные изменить поведение. Baseline: `launcher.cjs:242-260`; режимный overlay — `:280-291,309-318`.
7. **Готовность и отказ.** Не считать успешный `spawn` готовностью. Общая готовность API проверяется оболочкой; для payload trial сам launcher опрашивает локальный `/system/health` и требует `database=ok`, а также UI ACK с ожидаемой меткой сборки. Сохранять проверку принадлежности ответа текущему запуску. Публиковать понятные фазы и диагностические ошибки с безопасным логированием. При тайм-ауте/неуспехе trial восстановить предыдущий payload. Baseline: `launcher.cjs:110-119,309-352` и shell/UI polling.
8. **Режим LAN и перезапуск.** Сохранить обработку `lan-node.json`; безопасно подготовить server mode, при отказе запуска LAN host однократно перейти в local и отобразить причину; код выхода API `75` должен перечитывать конфигурацию и перезапускать API. Baseline: `launcher.cjs:265-291,353-360`.
9. **Остановка и владение процессами.** Все дети должны принадлежать одному kill-on-close Job до возобновления запуска; при ошибках на каждом шаге остановить созданное дерево. Нормальный выход API, авария supervisor и ручное завершение должны иметь определённую семантику; PostgreSQL не должен остаться бесхозным. Для нормального выключения предпочтительно штатное завершение базы перед аварийным закрытием Job.
10. **Совместимость оболочки.** Сохранять ожидаемые оболочкой `startup-state.json`, `runtime.log`, `app-runtime.json` и семантику стадий. Shell/UI должны оставаться работоспособными при отключённом/неудачном прямом lifecycle; включение нового пути допускается отдельным изменением после полной приемки.

## Проверенные расхождения прототипа

| Область | Код прототипа | Конкретный дефект относительно контракта |
|---|---|---|
| Доступность пути | `lifecycle.rs:55-62` | Публичный запуск отказывает; экспериментальный путь отключён. Его запуск не проверен и включать его нельзя на основании этого аудита. |
| Пути и изоляция | `:62-66,72-80,87-95` | Проверяет абсолютность runtime root и наличие отдельных файлов (`layout()`), но в этом lifecycle нет аналогов `resolvedPath`, `assertEditionIsolation`, `effectiveDataDir`/`effectivePgDir`; использует `profile.data_dir` напрямую. Это оставляет непроверенными junction/Unicode/границы данных и запрещённые порты на уровне lifecycle. |
| Существующий сервер БД | `:87-96` | Сразу запускает `pg_ctl start`, не выполняя `pg_ctl status`; повторный запуск на активном кластере не имеет предусмотренной ветви. В отличие от launcher, проверка статуса обязательна до старта. |
| Идемпотентность ролей | встроенный JS `:22-32` | Проверка только наличия `orion_app`; если app роль уже существует, но системная роль или grants отсутствуют/частичны, восстановление пропускается. |
| Секреты/временные файлы | `:73-84,205-232` | Ошибка удаления initdb password игнорируется; `local-runtime.json` пишется обычным `fs::write` без атомарного create-new/приватного каталога; конфигурация читается по четырём непустым строкам без проверки версии и формата. Это слабее поведения launcher (`:139-158`). |
| Окружение API | `:121-134` | Отсутствуют как минимум `APP_VERSION`, `ORION_BUILD_TAG/COMMIT/TIME`, `ORION_INSTALL_DIR`, `ORION_WEB_DIST`, `ORION_SHELL_RUNTIME`, `ORION_SHELL_BASE_TAG`, `ORION_PG_CTL`, `ORION_PG_CLUSTER`. API/обновления/информация о сборке могут вести себя иначе. |
| Startup state / выбор payload | `:61-142` | Не записываются startup phases, runtime log, app-runtime selection; код не использует `payload.cjs` и не обслуживает trial ACK/rollback. |
| Готовность/API restart/LAN | `:121-142` | После запуска только ждёт завершения API; нет health-check, UI ACK, LAN режима/отказа в local, рестарта на код 75, payload recovery. У штатного launcher health+UI ACK проверка внутри launcher применяется к payload trial; общую готовность оболочка проверяет отдельно. |
| Очистка при отказе | `:82-84,96,100-119,135-142,189-203` | Ошибки `terminate_all()` игнорируются в `run_to_exit`; initdb cleanup тоже игнорируется. Поведение failure после создания Job проверено только по чтению, не тестировалось. Нет явного штатного `pg_ctl stop`; Job close может оборвать PostgreSQL. |

Дополнительно `restore_staged_backup` в `lifecycle.rs:307-318` остаётся заглушкой и возвращает ошибку до изменений данных; это отдельная команда и не часть успешного запуска.

## Проверки и ограничения доказательств

**Проверено чтением кода:** точные ветви публичной и experimental функций `lifecycle.rs`, shared runner/config/PostgreSQL/provisioning/migration/env/API supervision в `launcher.cjs`; рабочая ветка launcher содержит проверки пути, статуса PostgreSQL и fallback поведения, перечисленные выше. Отдельный standalone harness `orion-rust/experimental/postgres_lifecycle_harness.rs` на свежих `%TEMP%`-кластерах проверяет два пути: успешный `pg_ctl stop -m fast -w -t 10` с подтверждением выхода pg_ctl и завершения конкретного PID; и намеренно неуспешный stop через отсутствующий каталог внутри того же временного профиля, после которого проверяются bounded Job shutdown и завершение того же PID. Оба opt-in smoke прошли после исправления обработки extended Windows paths. Harness задаёт доказательную границу только для своих синтетических кластеров; он не включает прямой lifecycle. `docs/ORION_R_RUNTIME_MIGRATION.md` сообщает, что штатный `supervise` с launcher проверен на пустом временном профиле, а прямые `supervise-direct` и `restore` отказывают без изменения данных.

**Не проверено:** прямой старт Rust; сценарии частично созданных ролей; повторное подключение к уже активному PostgreSQL; приватность и атомарность конфигурации на Windows ACL; Unicode/junction paths в lifecycle; health/API/UI readiness, LAN failover, trial rollback; тайм-аут `pg_ctl stop` (симуляция проверяет отказ по отсутствующему кластерному пути). Harness проверяет graceful stop и fallback после гарантированно неуспешного stop только на собственном временном сервере. Тесты в `lifecycle.rs` подтверждают лишь, что публичные заглушки возвращают ошибку и не создают тестовый каталог; они не вызывают `supervise_direct_experimental` и не подтверждают ни одну из заявленных гарантий.

**Benchmark не является свидетельством этого контракта.** Текущие цифры не характеризуют прямой Rust startup: штатный путь всё ещё вызывает `launcher.cjs`; результаты следует оценивать только в соответствии с отдельным протоколом benchmark после его проверки.

## Критерии допуска будущего переключения

До любого изменения выбора штатного пути нужны автоматические тесты на изолированных временных профилях для: чистого и повторного старта; существующего запущенного кластера; отсутствующей/частичной конфигурации; частичного provisioning; Unicode и junction пути; конфликта запрещённых портов; ошибки каждого этапа и подтверждения закрытия всех процессов; DB health, UI ACK/тайм-аут и откат payload; LAN host success/failure и restart code 75; штатного завершения и аварийного закрытия Job. Затем сверить runtime-файлы/переменные с упаковкой и выполнить smoke штатной Tauri оболочки. Не использовать профиль пользователя или работающие сторонние процессы в таких проверках.
