# Контракт supervisor для ORION-R

**Срез аудита:** 2026-11-09, рабочее дерево ORION-Rust. Документ сравнивает экспериментальный `orion-rust/src/lifecycle.rs` со штатным `apps/desktop/runtime/launcher.cjs`; это спецификация поведения для дальнейшей реализации, не разрешение переключить запуск.

## Актуальное состояние (2026-11-16)

**Прямой Rust lifecycle — штатный путь.** `supervise_direct` (`lifecycle.rs`) полностью реализован: выбор payload, ASCII-пути (`runtime_compat.rs`), секреты, initdb, старт/статус PostgreSQL, единый identity+provisioning, Prisma migrations, API supervisor с trial-гейтом и откатом, штатная остановка с bounded-ожиданием. Tauri-оболочка (`apps/desktop/src-tauri/src/main.rs`) запускает `orion-runtime.exe supervise-direct` в собственном kill-on-close Job и считает готовность только от слушателей, принадлежащих этому Job. `launcher.cjs` остаётся для явной диагностической команды `supervise-launcher`. Сквозной прогон на пустом профиле (запуск, `database=ok`, повтор, EOF-завершение, освобождение портов) пройден; установленный Tauri и пользовательские данные не подтверждены.

Изменения 15.11.2026: identity-проверка и provisioning слиты в один Node-процесс (`PG_SETUP_JS`) — минус один холодный старт Prisma на каждом запуске; health-проба понимает `Transfer-Encoding: chunked` и CRLF/LF; ожидание выхода в Tauri ограничено жёстким дедлайном; удалены дублирующиеся `cfg`-ветки в `write_json_atomic`. Grants после `migrate reset` повторяются скриптом `pnpm db:grants` (`scripts/db-grants.mjs`).

Изменения 16.11.2026: Tauri-шелл связывается с runtime через crate `orion-runtime` (`use orion_runtime::supervisor`), а не через хрупкие `#[path]`/`include_str!` на четыре уровня вверх; порты берутся из `orion_runtime::edition()` с честной ошибкой вместо молчаливых дефолтов; добавлена ротация `app-updates/versions` (`prune_stale_versions`, TTL 48 ч) — мусорные каталоги версий больше не копятся безгранично.

Остаются открытыми: сквозной тест отката trial при сбое миграций; репетиция LAN, unicode-путей и аварийного завершения; изоляция от Classic проверяется только на этапе запуска Rust-процесса. Classic restore из контракта исключён решением 15.11.2026: классическим клиентом больше не занимаемся; отдельно остаётся в плане восстановление из резервной копии ORION-R (не из Classic). Критерии допуска ниже сохраняются как чек-лист приёмки этих сценариев.

## Текущая граница

Штатный запуск ORION-R — прямой Rust lifecycle (`orion-runtime supervise` / `supervise-direct` из `lifecycle.rs`). Команда `supervise-launcher` сохранена только для диагностики: она запускает упакованный `launcher.cjs` внутри Windows Job Object.

`apps/desktop/runtime/launcher.cjs` остаётся источником поведения и fallback-эталоном. `main()` (`:220-263`) проверяет изоляцию, выбирает payload, готовит конфигурацию, запускает/проверяет PostgreSQL, создаёт роли, выполняет Prisma migrations и строит окружение API. Затем `superviseApi()` (`:309-363`) управляет готовностью, пробным payload, повторным запуском при смене режима и отказоустойчивым возвратом LAN host в local. Обработчик ошибок загрузки (`:365-380`) откатывает не прошедший проверку payload и повторяет запуск.

## Требуемый контракт

Прямой Rust lifecycle считается заменой launcher; ниже — чек-лист приёмки, по которому сверяются открытые сценарии:

1. **Изоляция профиля и runtime.** До записи конфигурации или запуска процессов разрешать только целевые пути текущей упаковки, учитывать junction/symlink и расширенные Windows-пути, отказывать при пересечении данных с Classic-профилями. Убедиться, что API, PostgreSQL и диагностические порты допустимы, различны и не совпадают с запрещёнными портами. Соответствующая база поведения: `launcher.cjs:12-84`.
2. **Подготовка путей.** Для PostgreSQL и документов применять те же правила ASCII-путей и приватных каталогов, что `ascii-path.cjs` через `launcher.cjs:9,55-63,223-230`. Не передавать проблемный Unicode/extended путь в `initdb` и `pg_ctl` без эквивалентного проверенного преобразования.
3. **Конфигурация и секреты.** Читать совместимый `local-runtime.json`; при отсутствии конфигурации и существующего кластера создавать уникальные секреты безопасно и без перезаписи конкурентного файла. При наличии кластера без конфигурации — fail closed и не изменять данные. Сохранять и валидировать все нужные поля и формат. Baseline: `launcher.cjs:139-148`.
4. **Идемпотентный PostgreSQL lifecycle.** Инициализировать кластер только при отсутствии `PG_VERSION`; всегда очищать временный парольный файл; перед стартом проверять, не работает ли кластер уже (`pg_ctl status`); слушать только localhost; корректно отличать ошибку запуска от уже активного кластера. Baseline: `launcher.cjs:150-167`.
5. **Provisioning и миграции.** Создавать БД и роли идемпотентно при частично завершённом предыдущем запуске; сверять не только наличие `orion_app`, но и `orion_system`, членство, права схемы и default privileges. Затем выполнять именно упакованный `prisma migrate deploy` с ожидаемой схемой и корректным администраторским URL. Baseline: `launcher.cjs:169-196`.
6. **Совместимое окружение API.** Передавать параметры сборки, API и web dist, каталоги данных, секреты, режим узла, shell/runtime provenance и пути управления PostgreSQL. Не наследовать случайные переменные, способные изменить поведение. Baseline: `launcher.cjs:242-260`; режимный overlay — `:280-291,309-318`.
7. **Готовность и отказ.** Не считать успешный `spawn` готовностью. Общая готовность API проверяется оболочкой; для payload trial сам launcher опрашивает локальный `/system/health` и требует `database=ok`, а также UI ACK с ожидаемой меткой сборки. Сохранять проверку принадлежности ответа текущему запуску. Публиковать понятные фазы и диагностические ошибки с безопасным логированием. При тайм-ауте/неуспехе trial восстановить предыдущий payload. Baseline: `launcher.cjs:110-119,309-352` и shell/UI polling.
8. **Режим LAN и перезапуск.** Сохранить обработку `lan-node.json`; безопасно подготовить server mode, при отказе запуска LAN host однократно перейти в local и отобразить причину; код выхода API `75` должен перечитывать конфигурацию и перезапускать API. Baseline: `launcher.cjs:265-291,353-360`.
9. **Остановка и владение процессами.** Все дети должны принадлежать одному kill-on-close Job до возобновления запуска; при ошибках на каждом шаге остановить созданное дерево. Нормальный выход API, авария supervisor и ручное завершение должны иметь определённую семантику; PostgreSQL не должен остаться бесхозным. Для нормального выключения предпочтительно штатное завершение базы перед аварийным закрытием Job.
10. **Совместимость оболочки.** Сохранять ожидаемые оболочкой `startup-state.json`, `runtime.log`, `app-runtime.json` и семантику стадий. Shell/UI должны оставаться работоспособными при отключённом/неудачном прямом lifecycle; включение нового пути допускается отдельным изменением после полной приемки.

## Проверки и ограничения доказательств

**Проверено чтением кода и тестами:** точные ветви `lifecycle.rs` (статус PostgreSQL, частичный provisioning, атомарная конфигурация, окружение API, trial/откат, bounded-остановка); `runtime_compat.rs` (ASCII/Unicode-пути, junction, fallback-каталоги); `rust_payload.rs` (ротация версий, atomic state, валидация id); supervisor (Job, stdin-close протокол, bounded wait); шелл (порты из `edition()`, принадлежность слушателей Job). Sandbox-тесты, зависящие от запуска реальных процессов и fault-injection, в изолированной среде сборки не воспроизводятся — они проходят на полной Windows-машине разработчика.

**Не проверено:** сквозной тест отката trial при сбое миграций; LAN failover на реальном узле; unicode-пути установки на чистой машине; поведение при аварийном завершении в разных фазах. Эти сценарии закрываются репетицией LAN/чистой Windows из реестра задач, а не чтением кода.

**Benchmark не является свидетельством этого контракта.** Текущие цифры не характеризуют прямой Rust startup в полной мере; результаты следует оценивать только в соответствии с отдельным протоколом benchmark после его проверки.

## Критерии допуска будущего переключения

До любого изменения выбора штатного пути нужны автоматические тесты на изолированных временных профилях для: чистого и повторного старта; существующего запущенного кластера; отсутствующей/частичной конфигурации; частичного provisioning; Unicode и junction пути; конфликта запрещённых портов; ошибки каждого этапа и подтверждения закрытия всех процессов; DB health, UI ACK/тайм-аут и откат payload; LAN host success/failure и restart code 75; штатного завершения и аварийного закрытия Job. Затем сверить runtime-файлы/переменные с упаковкой и выполнить smoke штатной Tauri оболочки. Не использовать профиль пользователя или работающие сторонние процессы в таких проверках.
