# ORION: люди, пространства и доступ

Статус: реализовано по [ТЗ-05](tz/TZ-05-shared-workspaces-identity.md) (кроме п. 5.6, см. ниже). Проверено автотестами `apps/api/test/shared-workspaces.integration.test.ts` и `workspace-transfer.integration.test.ts` (в `pnpm test:integration`); на двух физических ПК сценарий ещё не проходили.

## Модель

Пользователь → пространство → (необязательно) проект. Группы и «семьи» как отдельного уровня владения нет. Каждый человек регистрируется **собственным аккаунтом на узле**; общего аккаунта нет.

| Пространство | Reno | Варвара | Как устроено |
| --- | --- | --- | --- |
| Личное Reno | владелец | нет доступа | создаётся при регистрации, `isPersonal = true` |
| Личное Варвары | нет доступа | владелец | то же |
| Дом | владелец | участник | шаблон «Дом» (создание → «Шаблон»), приглашение по email |
| Семейные финансы | владелец | по роли (см. ниже) | модуль финансов в «Доме» + ограничение модуля + личные счета |
| Проекты | владелец | нет, пока не приглашена | отдельное пространство |

Правила, на которых это держится: `assertMember` в каждом сервисе + RLS в PostgreSQL (оба независимо). Сторонний человек получает 403 на любой маршрут `workspaces/:id/**`; чужой id внутри своего пространства — 404.

## Личные пространства

- Создаётся при регистрации; в ответе `Workspace.isPersonal = true`; уже существующие пространства вида «<имя> — личное пространство» с одним участником помечены миграцией.
- Интерфейс не предлагает его как общее: в Настройки → Участники форма приглашения скрыта и объяснено, что для совместной работы нужно общее пространство.
- **Сервер не запрещает** владельцу вручную пригласить кого-то в своё личное пространство (запрос к API) — это его осознанное решение; жёсткий запрет сломал бы существующие сценарии и тесты. Флаг лишь управляет интерфейсом.
- Владелец «Дома» **не получает** доступа к личному пространству Варвары через ORION: ни по списку пространств, ни по id (тест).

## Приглашения

1. Владелец (или лид) в Настройки → Участники вводит email и выбирает роль: **Участник** или **Тимлид**. Роль «Тимлид» может выдать только владелец; «владелец» приглашением не выдаётся. Смена роли существующего участника — только владелец.
2. Создаётся ссылка (`/invite?token=…`) и **код** (тот же токен без адреса). В режиме LAN-хоста задайте `ORION_PUBLIC_URL`, чтобы ссылка вела на адрес узла, видимый из сети (без него — первый `WEB_ORIGIN`).
3. Варвара создаёт собственный аккаунт на узле **с тем же email**, затем принимает приглашение: по ссылке либо вставив код/ссылку на экране «Пространства» → «Войти в общее пространство по коду».
4. Статусы: `pending` → `used` (принято) | `revoked` | `expired` (14 дней). Просроченное непринятое приглашение не блокирует новое на тот же email.
5. Когда участника убирают из пространства, **все его токены агентов в этом пространстве отзываются сразу**, а вход по токену проверяет членство.

## Финансы «по назначенной роли» (решение: отдельная модель прав не нужна)

ТЗ допускало ввести `view/add/manage`, «только если без неё сценарий невозможен». Сценарий возможен на существующем:

- **Ограничение модуля** (Настройки → Модули → «Только владелец и лид») закрывает финансы от роли «Участник» (403); «Тимлид» и владелец проходят. Это и есть «по назначенной роли»: Варвара — тимлид → видит и ведёт общие финансы; участник → не видит.
- **Личные счета** (`visibility = private`) видит только их владелец (RLS), включая операции, правила и отчёты — даже тимлид и владелец пространства.
- Гранулярных `view/add/manage` **нет**: роль даёт доступ к модулю целиком (по общим счетам). Если понадобится «видит, но не вносит», это новый ADR.

## Что видит второй человек и как быстро

- Списки опрашиваются раз в 15 с (`LISTS_POLL_MS`): отмеченный в «Доме» пункт у второго виден по `checkedBy`.
- Остальные модули обновляются по инвалидации react-query после собственных действий и при повторном открытии панели; **живого пуша между клиентами нет** — чужая правка появится при следующем запросе, без гарантии срока.

## Аудит изоляции (ТЗ-05 §5.1)

Тест строит «Reno + Варвара» на трёх пространствах и обходит **все** маршруты `workspaces/:workspaceId/**`, найденные в контроллерах Nest (новый модуль попадает в проверку сам): посторонний не получает ни 2xx, ни 5xx. Отдельно проверены: заметки/задачи по чужому id, поиск, поток содержимого файла, связи `EntityLink` на чужие объекты (404 в обе стороны), адресные уведомления, входящие, токены и журнал агентов, фид календаря по токену (ротация), бэкап/restore (только владелец), снимок пространства (строки только своего `workspaceId`), финансы по ограничению модуля.

Найдено и исправлено:

| Дыра | Исправление |
| --- | --- |
| `GET …/search` с коротким запросом и `GET …/members-search` с пустым отвечали 200 постороннему (проверка членства шла после раннего выхода) | членство/роль проверяются первыми |
| `GET …/links` с неверным `type` отдавал 500 | 400 |
| Журнал агентов видели все участники — включая действия чужих токенов | участник видит только свои токены, владелец — все |
| Токен агента пережил исключение владельца из пространства | отзыв токенов при исключении + проверка членства при входе по токену |
| Просроченное `pending`-приглашение навсегда блокировало повтор | при повторе помечается `expired` |

## Перенос существующей базы (ТЗ-05 §5.5)

Процедура, а не слияние. Исходный ORION (например, локальный у Варвары): Настройки → Участники → «Выгрузить .orion» (владелец; пароль необязателен). На хосте: «Пространства» → «Перенести из файла»: **предпросмотр** (сколько записей/файлов, сколько id уже занято на узле, сколько ссылок на людей будет записано на вас, что не переносится) → подтверждение → **новое пространство**, владелец — импортирующий.

- Все строки получают новые id, внешние ключи переписываются по схеме Prisma; авторство, исполнители, владельцы личных счетов — на импортирующего. Существующие данные узла не меняются (тест: ID-коллизия с самим источником, повторный импорт даёт ещё одно пространство).
- Подтверждение требует хеш файла из предпросмотра (другой файл — отказ). Файлы кладутся под ещё не существующий id, строки вставляются одной транзакцией; при сбое файлы убираются, пространство не создаётся (тест с порчей строки посередине).
- Не переносится: здоровье (ADR-0012), токены и журнал агентов, выданные доступы между пространствами, уведомления, настройки WebDAV.
- Файл `.orion` для переноса **не** то же самое, что резервная копия узла (та привязана к `SYNC_SECRET` узла и при загрузке отклоняется с объяснением).
- Пока файл не импортирован, локальная база остаётся только локальной.
- Ограничения: файл целиком в памяти (потолок `MAX_TRANSFER_MB`, 256 по умолчанию); обрыв процесса *между* записью файлов и коммитом оставляет каталог без пространства — он записан в журнал `_import-journal/pending.json` и убирается при следующем старте API (тест).

## Идентичность устройств (§5.6) — не реализовано

Доверенные устройства ТЗ-04 хранятся на уровне **узла** (`lan-devices.json`), а не пользователя: устройство доверено хосту, а войти на нём может любой, у кого есть аккаунт. Связь «пользователь ↔ устройство» и её показ в профиле в модель не заложены. Выполняется само собой: выход пользователя не отзывает устройство, отзыв устройства не удаляет пользователя (разные хранилища). Профиль с устройствами — отдельная работа; сначала нужно решить, привязывать ли устройство к пользователю при спаривании.

## Ограничения доверия (честно)

- Администратор PostgreSQL / файловой системы узла физически видит все данные всех пространств, включая личные. Мы защищаем пользователей друг от друга, а не от оператора узла. Владелец хоста LAN — как раз такой оператор.
- Владелец пространства видит его целиком (включая журнал агентов и выгрузку `.orion`), кроме личных счетов и данных здоровья.
- Приглашение выписано на email без подтверждения почты: кто зарегистрирует на узле аккаунт с этим адресом, тот его и примет. Передавайте ссылку/код только адресату; отзыв — Настройки → Участники.
- Файл `.orion` без пароля содержит все данные открытым текстом.
- Две независимые базы это не синхронизирует (ТЗ-06).
