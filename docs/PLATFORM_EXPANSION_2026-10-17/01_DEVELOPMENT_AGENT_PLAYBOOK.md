# ORION — обязательный протокол ИИ-разработчика модулей и плагинов

Версия предложения: 1.0, 17.10.2026. **Это практический исполнительский регламент, не новая конституция проекта.** `AGENTS.md`, `ORION_CONSTITUTION.md`, `docs/AI_REFACTOR_MIGRATION_MAP.md` и актуальные contracts/ADR имеют приоритет.

## 0. Стартовый контракт агента

Перед любым изменением агент должен определить: цель пользователя, тип результата, доступный контекст, зону владения файлами, текущий HEAD, `git status --short`, зависимости от параллельных работ, запреты и минимальный проверяемый сценарий. **Не угадывать архитектуру по соседним импортам.**

Читать по порядку:
1. `AGENTS.md`, `ORION_CONSTITUTION.md`.
2. `docs/AI_REFACTOR_MIGRATION_MAP.md`.
3. `docs/MODULES_AND_PLUGINS.md`, `docs/AI_FIRST_EXTENSION_ARCHITECTURE.md`.
4. `docs/PRODUCT_DIRECTION.md`, `docs/STATUS.md`, релевантные ADR и `docs/ROADMAP.md`.
5. Точные `MODULE.md`, `AI_CONTEXT.md`, SDK, manifest, public contracts, модульный тест и один образцовый соседний плагин; не погружать целый монорепозиторий без необходимости.

Для общего каталога Cursor соблюдать `docs/KAIDEN_REDESIGN_CURSOR_5_AGENTS_2026-10-17/00_SHARED_TREE_PROTOCOL.md`. Запрещены самостоятельные переключения веток, массовый staging, reset/clean, перезапись незнакомых незакоммиченных правок; общие сборки и миграции — через координатора.

## 1. Классификация до кода: одно из четырёх

| Тип | Когда применять | Что принадлежит |
|---|---|---|
| Core | Универсальная инфраструктура платформы | auth, пользователи, разрешения, shell, registries, jobs, диагностика |
| Base module | Минимально полезный самостоятельный предметный домен | ключевые сущности/операции, работа без соседних optional-плагинов |
| Plugin/extension | Дополнительная функция существующего домена | contribution, собственная конфигурация, публичные вызовы/слоты |
| Module Bridge | Явная связь двух независимых доменов | публичный контракт связи, dependency/capability checks, no privilege inheritance |

Если соответствующее владение **уже зафиксировано** в `AI_REFACTOR_MIGRATION_MAP.md`, не классифицировать заново. Новый спорный случай: оформить `ADR / Extension Proposal` и остановить правку общих слоёв до решения. Не дублировать существующий Finance, Health, Markets/Investments, Opportunity Hub или Knowledge Hub под новым именем.

## 2. Шаги одного законченного вертикального среза

**Шаг A — аудит.** Подтвердить, что есть в коде сегодня: Base, plugins, typed slots, таблицы, API, DTO, migration, snapshot, тесты, экран, permissions. Отметить конкретные пробелы. Проверить зависимости и дефолты `default-full` / `plugins-off`.

**Шаг B — проектирование.** Описать один пользовательский сценарий от входа до результата и отмены; отдельно ошибки, отсутствие сети, отключённый модуль, смену workspace. Составить permission matrix (owner/member/restricted/guest, где применимо), публичные методы, DTO с версиями, события, точки расширения, способы хранения и удаления, backup/sync, тест-план. Для изменения shared контрактов — предложение с минимальным diff, согласование.

**Шаг C — реализация.** По существующей вертикали ORION: валидируемый API/DTO и data access → backend service с проверками доступа → client/core → core-react → UI в стандартном shell или через typed contribution slots → тесты. Реальная структура зависит от текущего реестра. Не клонировать существующую UI-библиотеку; использовать `@orion/ui` и токены KAIDEN, не фиксированные цвета.

**Шаг D — приёмка и передача.** Targeted unit tests и модульный smoke, после прекращения параллельных записей — общие gates, затем отчёт с точными командами, результатами, регрессиями, рисками и незавершёнными пунктами. Без проверок нельзя писать «готово».

## 3. Архитектурные запреты

1. Направление зависимостей **Core → публичные Contracts/SDK → Modules → Extension Points → Plugins**. Core не знает конкретных плагинов, Base не импортирует реализацию plugin, plugin не читает Base internals или внутренности других плагинов.
2. Плагин внедряет UI **только через зарегистрированный typed slot/host API**. Отсутствующий слот означает `NEW_EXTENSION_POINT_REQUIRED` + Extension Proposal, а не прямой импорт `apps/web/panels/**` или изменение Base ради одной кнопки.
3. Межмодульная связь — отдельный bridge, который обращается только к публичным контрактам, не читает чужие таблицы. ID, EntityLink или grant на одну запись **не расширяет** доступ на связанную.
4. `default-full` после извлечения встроенной функции должен сохранить прежнюю функциональность. Исходно выключенные optional-функции не включать без решения владельца.
5. Выключение plugin/module **не удаляет данные**. Разрушительный purge — отдельная явная операция со своими тестами и подтверждением.
6. Несовместимые DTO, API, events, plugin manifest и snapshot требуют осмысленного versioning/migration. Никаких скрытых broken contracts.
7. Нельзя одновременно с переносом в plugin «попутно улучшать дизайн», менять модель финансов или пересобирать соседние домены.

## 4. Модель доступа и безопасность

- Разделение пользователя и пространства: явный `workspaceId` плюс серверные membership, role, module-enabled, grants и **PostgreSQL RLS**. URL/клиентская проверка не заменяют доступ. Для индивидуально приватных медицинских и иных данных — отдельный утверждённый user-level ACL, а не автоматическое раскрытие всему workspace.
- Тесты: workspace A vs B, чужой ID, ограниченный участник, выключенная capability, отзыв доступа, вложения/связи, snapshot/restore, stale revision/CAS, конкурирующие запросы.
- Prisma миграция: additive когда возможно, индексы, backfill, валидный rollback/forward-only recovery; только тестовая БД. Новые модели должны явно входить в snapshot registry, а файлы — в blob backup. Не считать бэкап автоматическим.
- Sync: документировать local/shared/hybrid, source of truth, idempotency, conflict resolution, replay и scope. Новая таблица не синхронизируется автоматически. Нельзя самовольно разрешать offline-write для финансов, файлов или чувствительных данных.
- Импорт/экспорт: preview, явное подтверждение, limit размера/числа, allowlist типов, безопасные пути/архивы, SSRF/DNS-rebinding protection, защита от spreadsheet formula injection, dedup, audit и отмена; никаких секретов/персональных файлов в git или тестовых fixture.
- Внешние действия: отправка почты, отклик работодателю, публикация, API-запись и платёж — через approved capabilities, scopes, журнал и подтверждение человека согласно существующим правилам. `preview` ≠ `approved` ≠ `executed` ≠ `confirmed by remote`.
- Внешние сервисы и локальные companion-процессы: подписанный/версионированный протокол или аутентифицированный local API, явный Host/Origin, минимальная сетевая поверхность, timeout, retry/idempotency, безопасное отключение. Не публиковать localhost cookie наружу.

## 5. Пользовательский контракт модуля/плагина

Документировать: unique ID и manifest, зависимости/совместимость и defaults, capability flags, роли, хранение/retention, жизненный цикл install-enable-disable-update-uninstall, данные после disable, экспорт/импорт, fallback при отсутствии поставщика, UI slots, события, API/SDK, локализацию, доступность и оформление темами.

Предусмотреть UI состояния `loading / empty / error / denied / disabled / offline / conflict`; навигацию назад, клавиатуру и mobile 320/390 px, desktop/узкие dock panels; разделение персональных и общих настроек, управление несохранённым вводом. Никаких фальшивых кнопок с обещанием операции, которой нет.

## 6. Документы каждого нового домена

- `MODULE.md`: purpose, owns/does-not-own, минимальный Base, API, events, slots, permissions, deps, data lifecycle, sync/backup, non-goals, acceptance.
- `AI_CONTEXT.md`: конкретные 5–12 файлов, test commands, contracts, границы изменений, типовые ошибки, один ориентир для паттерна.
- Архитектурное предложение по шаблону `05_SPEC_AND_HANDOFF_TEMPLATES.md`, отдельный ADR для новых рисковых решений и changelog.
- Исполнительский отчёт: baseline SHA, список изменённых файлов, реальные тесты с exit/status, что не тестировалось, риски и rollback; не подменять факты планом.

## 7. Quality gates и запреты на ложное «готово»

В согласованном тестовом окружении и без конкурентной записи в общие артефакты:
`corepack pnpm typecheck` → `corepack pnpm lint` → `corepack pnpm test` → `corepack pnpm architecture-check` → `corepack pnpm plugin-contract-check` → `corepack pnpm build` → `corepack pnpm build:desktop-export`.

Интеграционные тесты — на **изолированной PostgreSQL**, с актуальными миграциями и RLS; E2E — отдельно в выделенном preview, UI с различными ролями/разрешениями, default-full и plugins-off. Факт Windows Tauri/native, DPI, popout, LAN на двух физических компьютерах фиксируется только по реальной ручной проверке. Результаты должны соответствовать **текущему HEAD**, а не `docs/STATUS.md` за старую ревизию.

**Стоп-условия:** архитектурный конфликт, неизвестный владелец общего файла, угроза пользовательским данным, секреты, недоступность нужных прав, неясный broken contract, провал миграций/negative RLS. Остановить только опасный срез, записать `BLOCKED` с файлом, воспроизведением, минимальным решением и ответственным. Не чинить обходом безопасности.

## 8. Разграничение с Agent Gateway

`docs/AGENT_MANUAL.md` — инструкция **внешнему агенту-пользователю** `/ai/v1`, scoped token и MCP, а **этот playbook** — правила **ИИ-разработчика исходников**. Первому не давать root/database/schema access и не заменять инструментом разработки его пользовательский API.
