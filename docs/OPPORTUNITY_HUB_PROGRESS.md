## API R0.1

Prefix `/workspaces/:workspaceId/opportunities`:

| Method/path | Поведение |
| --- | --- |
| GET `/` | query/kind/status/includeArchived/cursor/limit; 50 default, 200 max; items/nextCursor |
| GET `/:id` | Только карточка текущего workspace |
| POST `/` | Создание; duplicate source/external ID →409 |
| PATCH `/:id` | expectedRevision обязателен; пустой patch →400; конфликт →409 |
| POST `/:id/archive` | expectedRevision; данные/история сохраняются |
| POST `/:id/restore` | expectedRevision; вернуть из архива |
| GET `/export` | Owner-only, до 10 000 записей, включая архив; без тихого truncation |

Каждый service method проверяет membership/роль и module enabled/restricted внутри withUser. Controller guard — дополнительная защита, не замена проверки сервиса. Row lookup всегда workspace-scoped.

## Важные решения первого среза

1. Cursor упорядочен по стабильному `id asc`, а не updatedAt/id из исходного проектируемого API: правки не сдвигают уже открытый cursor. Это явно ограниченный выбор R0.1; для сортировки «свежие сверху» нужен отдельный устойчивый контракт.
2. История хранит actor/time/action/fromStatus/toStatus, не полный diff всех полей. Ни ручной статус, ни запись истории не свидетельствуют об отправке на HH.
3. При конфликте редактор сохраняет локальный ввод; кнопка загрузки свежей revision не отправляет patch. Повторное сохранение передаёт только локально изменённые поля, остальные правки второго клиента остаются. Conditions объединяются по изменённым полям.
4. Whole-workspace export ограничен owner по ТЗ. Действия агента и внешняя отправка в этом API отсутствуют.
5. Новый модуль следует текущей catalog-модели, defaultEnabled true; existing defaults не менялись. Опциональных плагинов пока нет.
6. Условия хранятся как данные карточки; финансовых проводок, валютных конверсий и связи с балансом нет. Дополнительные структурированные требования/дедлайн и специализированные представления расширять отдельным срезом, сохраняя версии.

### Профили

- Профиль человека и команды/студии; имя, город, форматы работы, минимальная сумма на руки, исключённые компании/роли.
- Факты с источником: новый факт непроверенный; только явное действие владельца подтверждает/оспаривает его с CAS revision.
- Треки со ссылками только на факты того же профиля; материалы только в треке того же профиля/пространства.
- Неизменяемые текстовые версии резюме, портфолио и предложения; список с постраничной загрузкой и просмотр содержимого. Импорт резюме не создаёт подтверждённых фактов и не выбирает активную версию автоматически.
- Профили читают разрешённые участники пространства, меняет владелец. Создание и импорт требуют подтверждения видимости материалов участникам. Это workspace-wide доступ, отдельного приватного ACL на профиль пока нет.
- Архив/восстановление с CAS, выключение расширения сохраняет данные. Ошибка сохраняет ввод; переходы/смена формы используют общий `@orion/ui ConfirmDialog`, не native window.confirm.

### Импорт HH

- Выбор папки или отдельных файлов, исключение служебных файлов/кода/браузерных сессий **до чтения и загрузки**; сервер повторно применяет allowlist.
- MD/TXT резюме, поддерживаемые JSON снимков вакансий и журналов. Папка кандидата задаёт принадлежность материала; одинаковые имена в разных исходных папках не объединяются. Выбор одной вложенной папки «Резюме» отклоняется с пояснением.
- Предпросмотр с примерами, пропусками и сроком 24 часа сохраняет план, не предметные записи. После изменения файлов/опций нужен новый предпросмотр. Применяется загруженный снимок, локальная папка повторно не читается.
- Порции по 25 операций: блокировка строки ImportRun, CAS revision, атомарные checkpoint/report/inserts. После прерывания можно открыть сохранённый импорт и явно продолжить; открытие не запускает apply.
- Повторный импорт дедуплицируется по стабильным ключам. Ручные названия/условия/предпочтения не перезаписываются. Изменённое содержимое резюме создаёт новую версию; изменённая зарплата в снимке вакансии создаёт новый capture, не переписывает карточку.
- Снимки содержат sourcePath, исходный vacancy file SHA-256, record SHA-256, normalized conditions/text и historical flag. Дата загрузки не выдаётся за дату актуальности вакансии. Для материала сохранены sourcePath и hash нормализованного текста.
- История остаётся `already_exists`, `legacy_claimed_verified`, `failed` или `unconfirmed`; новое `confirmed` не создаётся. Возможный дубль помечается. Профиль для истории выбирается явно или остаётся пустым; аккаунт по имени файла не угадывается.
- Отмена останавливает последующие порции, уже записанное сохраняется. Импорт/журналы/источники доступны только владельцу через отдельный API.

Серверный адаптер использует `OPPORTUNITIES_IMPORT_PORT.v1` и `PROFILE_IMPORT_PORT.v1`, Base не импортирует concrete plugins. Composition — `OpportunityExtensionsModule`.

### Этап 2 — завершение R0.2
- **PDF/DOCX/RTF** (`apps/web/plugins/opportunities-hh-import/document-text.ts`): формат по содержимому, не по расширению; извлечение в браузере до загрузки, без исполнения чего-либо (pdf.js без eval, DOCX читается только как текст `word/document.xml`, собственный разбор RTF). Лимиты: 25 МБ на файл, 5000 записей архива, 20 МБ распакованного XML, 150 страниц PDF, 30 с, 50 000 символов. Версия парсера пишется в сохранённый план (отдельной колонки у материала нет). **Старый двоичный `.doc` (OLE) не читается** — честный отчёт «не поддерживается, сохраните как DOCX/RTF/PDF»; зашифрованный контейнер — «защищён паролем»; PDF без текстового слоя — «нет текста (OCR не выполняется)». Сервер fail-closed: двоичный файл без метаданных извлечения, пустой текст, NUL-байты или статус не-ok никогда не становятся материалом; в предпросмотре причины сгруппированы по кодам.
- **Письма и портфолио:** `Cover_Letters` → тип `proposal`, `Портфолио` → `portfolio`; кандидат — папка над папкой материалов.
- **Большие пакеты:** клиент режет пакет на части (≤200 файлов, ≤380 000 символов) и создаёт отдельный предпросмотр на каждую; лимиты 10 000 файлов / 100 МБ объясняются до чтения; части применяются по очереди, повтор безопасен. Единого «манифеста пакета» нет — каждая часть живёт 24 часа отдельно. Измерение производительности на 10 000 записей **не проводилось** (проверен пакет из 450 файлов: 3 части, повтор — 0 новых версий).
- **Общий журнал откликов:** `GET opportunity-hh-import/history` (владелец, по 100, фильтры «итог / без карточки / возможные дубли», итоги) + раздел в UI. Это утверждения старых журналов, не подтверждённые отправки.
- **Факты и треки:** правка факта (сбрасывает подтверждение), архив/возврат факта и трека, правка трека, CAS по `revision`; миграция `20261015210000_opportunity_facts_tracks_lifecycle`.
- Не реализовано: roster команды (в ТЗ не определён), приватный ACL профиля, bridge в Notes/Documents для учебных документов.

### Этап 3 — R0.3 «Ассистент» (`opportunities-assistant`)
Оценка «возможность × профиль» (rules-v1), **без внешней модели**: требования извлекаются из описания по заголовкам/спискам; совпадение засчитывается только по **подтверждённым** фактам; непроверенные факты и упоминания в тексте резюме дают «неизвестно» с указанием основания; оспоренные — «противоречие»; пробел остаётся пробелом; числовые требования автоматически не подтверждаются; рейтинг 50/20/15/15 (неизвестное баллов не даёт), отдельно надёжность данных и список «чего ассистент не знает», `autoSendBlockers`. Текст вакансии — данные: инструкции внутри него ничего не меняют (проверено). Оценки неизменяемы; устаревание (изменились карточка, предпочтения, факты, треки, активное резюме, версия правил) вычисляется при чтении по отпечатку входных данных. Черновики (отклик/предложение/ответ на вопрос) собираются только из подтверждённых фактов, каждый раздел показывает основание, пробелы идут в заметки, а не в текст; ответ без подтверждённых данных остаётся пустым; одобрение владельца привязано к хэшу текста, правка его сбрасывает, устаревший черновик не одобряется. Пробный запуск (`send:false`) показывает точный payload, хэш и блокировки; он не создаёт ни попытки, ни права на отправку. Внешний провайдер объявлен недоступным и отвергается (409) — **для подключения LLM нужно решение владельца (провайдер, бюджет, передача данных)**. Миграция `20261015220000_opportunity_assistant`; таблицы под FORCE RLS; при восстановлении из копии одобрения черновиков сбрасываются.

### Этап 4 — R1.1 «Управляемая отправка» (`opportunities-execution`)
Подключение аккаунта (одноразовый код `ohp_…` → токен исполнителя `ohr_…`, оба хранятся хэшем; пароль HH ORION не видит), попытка = точный payload + хэш, разрешение на конкретный хэш на 5–120 мин, один раз; протокол `opportunities-executor/v1`: `claim` (одно задание на подключение, повторная проверка прав владельца, плагина, подключения, дневного лимита, разрешения и **текущего хэша содержимого**), `heartbeat`, обязательная контрольная точка `reserve` перед нажатием (проверка отмены/паузы/аккаунта/существующего отклика/минимального интервала, атомарное списание дневного бюджета, использование разрешения), `result` с единственным правилом `decideOutcome`. После `reserve` любая неопределённость — `sent_unconfirmed` (не «не отправлено», без автоповтора); подтверждение — только доказательство события/сообщения/перехода, привязанное к аккаунту, вакансии и времени; сверка владельцем ничего не отправляет. Один аккаунт HH = один бюджет даже при нескольких профилях. 3 системных сбоя подряд ставят подключение на паузу. Барьеры в БД: одна живая/успешная попытка на вакансию и профиль, одно действующее разрешение на попытку, одно подключение на профиль. В бэкап не попадают токены/коды/хэши и разрешения; при восстановлении подключение — `pending_link`, очередь отменена, возможная отправка остаётся неподтверждённой, дневной счётчик не откатывается. Миграция `20261015230000_opportunity_execution`.
**Браузерный адаптер для hh.ru НЕ реализован.** В `scripts/hh-runner` лежат эталонный цикл исполнителя (`runner-loop.mjs`: одно нажатие, только после `reserve`, при сомнении не повторять), имитирующий адаптер и CLI, работающий только с `--simulate`.

### Этап 5 — R1.2 «ИИ-менеджер» (`opportunities-manager`)
Явная политика на одно подключение (порог рейтинга ≥50, надёжность, обязательные факты, дневной лимит ≤20, всего ≤100, срок ≤30 дней, тихие часы, обязательное «понимаю последствия»), жёсткие потолки продублированы CHECK-ограничениями БД, одна живая политика на подключение. Цикл запускается **только кнопкой** (фонового планировщика нет); каждая вакансия — отдельная транзакция; при сомнении («нужно решение человека») или нарушении порогов ничего не ставится в очередь; пройденные вакансии получают черновик из подтверждённых фактов, одобренный от имени `policy:<id>`, и короткое разрешение (15 мин). Идемпотентность — уникальный ключ (политика, вакансия), параллельные циклы не дублируют действия и не превышают лимиты. Пауза/остановка/истечение отменяют ещё не начатое и отзывают разрешения; неопределённая отправка политики ставит её на паузу до сверки; после восстановления из копии любая политика возвращается `paused`. Отчёт: действия с причинами и итоги отправок политики. Менеджер не меняет собственные полномочия и не расширяет их. Миграция `20261016000000_opportunity_manager`.

### Итоговая приёмка (серверный и браузерный уровни; без hh.ru и без установленного приложения)
Приёмочный интеграционный тест: личный путь «импорт файлов HH → профиль → подтверждённый факт → оценка → черновик → одобрение → разрешение → исполнитель (имитация) → подтверждено», повторный импорт без дублей и без потери ручных правок; командный сценарий (участник читает и готовит, но не одобряет/не подключает/не создаёт политику; чужое пространство ничего не видит); выключение всех расширений оставляет Base рабочим и сохраняет данные, повторное включение ничего не запускает само.

### Что НЕ проверено и почему
- **G20 — живой сценарий HH:** не выполнялся и не может быть выполнен без разрешения владельца на конкретный аккаунт и действие. Браузерного адаптера для hh.ru нет.
- **Внешний LLM:** не подключён; нужны решения владельца (провайдер, бюджет, какие поля профиля можно передавать).
- **Производительность:** ориентиры ТЗ §16.1 (10 000 записей, p95 ≤ 500 мс, импорт ≤ 60 с/512 МиБ) не измерялись; проверены корректность и пакет из 450 файлов.
- **Pause ack ≤ 2 с** недостижимо без канала «сервер → исполнитель»: пауза доходит до исполнителя через heartbeat (≤ 15 с), а обязательный `reserve` перед нажатием гарантирует, что после паузы отправка не начнётся.
- Полный проход screen-reader/клавиатуры по всем экранам Hub, мобильные 320 px для всех экранов (проверены 390 px для профилей, ассистента, активного резюме и 320 px для импорта ранее).
- Фоновые задачи: срок политики/разрешения/аренды применяется лениво при чтении и вызовах исполнителя; отдельного cron нет.
- Скриншоты как доказательства (только хэши/ссылки), прикрепление к Documents, события v1, AI-scopes `opportunities:*`, мосты Tasks/Calendar/Notes/Projects.

## Следующий срез

**Для внешних действий и отдельных дополнительных срезов нужны исходные данные владельца; это не запрещает локальные исправления, изолированные проверки и сборку:**
1. **Живая приёмка G20:** какой именно аккаунт HH, какой профиль и какое одно конкретное действие разрешено; хранение входа (на стороне пользовательского браузера, без пароля в ORION).
2. **Внешний LLM:** провайдер, бюджет и список полей профиля, которые разрешено передавать. До этого ассистент остаётся правилами rules-v1.
3. **Установленное окно Tauri:** можно ли запускать новую сборку против существующего `%LOCALAPPDATA%\com.orion.desktop` (сделать копию кластера? использовать чистую учётную запись Windows?).
4. **Фоновый запуск менеджера:** нужен ли планировщик; если да — отдельный дизайн (расписание, окно работы, поведение после перезапуска). Сейчас цикл запускается только кнопкой.

**Технические шаги после решений:**
- Браузерный адаптер hh.ru по интерфейсу `scripts/hh-runner` (сначала только чтение: аккаунт, существующий отклик, сверка; затем отправка одного согласованного отклика) с тестами на записанных синтетических страницах и обязательной остановкой на CAPTCHA/входе.
- Доказательства-скриншоты (байты в storage с хэшем, неизменяемые), события v1, AI-scopes `opportunities:*` через AI Bridge, мосты Tasks/Calendar/Notes/Projects по публичным контрактам.
- Старый `.doc` (OLE) и OCR для сканов — только с реальным парсером, лимитами и тестами; общий манифест большого пакета; замеры производительности ТЗ §16.1 на 10 000 записей.
- Приватные ACL профилей и роли lead в командном сценарии (сейчас подключения, разрешения, политики и одобрение — только владелец пространства).
- Полная проверка доступности (screen-reader, 320 px на всех экранах Hub) и установка на чистой машине.

Перед продолжением: git status/history, этот файл, паспорта `apps/api/src/opportunities-*/MODULE.md`, ADR-0008. Режим автономии и любые внешние действия — только после явного разрешения владельца на конкретный аккаунт и действие.
