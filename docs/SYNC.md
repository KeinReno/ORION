# ORION: устройства, совместная работа и WebDAV

Статус на 15 октября 2026 года. Решение владельца от 15.10: целевая архитектура содержит **оба** режима — общий узел (запись онлайн) и гибрид (локальная копия + очередь изменений). Протокол и границы — [ADR-0016](adr/ADR-0016-hybrid-sync-protocol.md), задание — [tz/TZ-06-hybrid-sync.md](tz/TZ-06-hybrid-sync.md). Ниже — что работает и чего нет; «offline sync» обещан **только** для перечисленных моделей.

## Что работает в гибридном режиме, а что нет (ТЗ-06)

Режим выбирается на пространство (Резервные копии → «Режим пространства и устройства», только владелец): «только локально» · «общий узел» (по умолчанию, как раньше) · «гибрид». Гибрид включается осознанно; без него ничего из нижеследующего не происходит.

| | Состояние |
|---|---|
| ADR-0016, классификация **всех** моделей реестра снапшота (тест сверяет списки) | сделано; ADR ждёт принятия владельцем |
| Этап 1 — локальная копия, чтение офлайн, метка «данные на …», отзыв членства/выключение гибрида стирает копию при следующем подключении | сделано для списков, пунктов, заметок и задач (IndexedDB в браузере/Tauri WebView) |
| Этап 2 — очередь операций, повтор отправки, идемпотентность, tombstone-ы, конфликты «двое отметили / удалили», откат устройства из бэкапа | сделано **на списках и пунктах**; набор тестов сбоев и fuzz на сходимость — зелёный |
| Этап 3 — заметки (явный конфликт по `revision`, без слияния; «Сохранить мою версию» / «Оставить версию узла»), задачи (LWW по полю) | сделано; автоматические тесты зелёные. **Ручная проверка UX конфликтов на двух ПК не проводилась** |
| Документы и файлы, финансы, склад, учёт времени, здоровье, остальные модули | **не синхронизируются офлайн** (только онлайн на узле); данные здоровья не покидают узел |
| Подпись операций устройством (Ed25519), шифрование локальной копии ключом устройства | не сделано (описано в ADR как ограничение) |
| Интернет, постоянный узел, мобильные клиенты, relay (этап 4) | только описание в ADR |

Ограничения, о которых нужно знать: **отзыв доступа не отзывает уже скачанное**; локальная копия хранится в открытом виде (защита — шифрование диска ОС); при потере связи более чем на 90 дней копия перезагружается целиком (неотправленные операции сохраняются); часы устройства влияют на «последнее слово» в пределах окна в 24 часа; «Новый круг», дубликаты и шаблоны списков, корзина заметок и поиск по тексту требуют связи с узлом. Лента изменений не чистится автоматически чаще раза в сутки (крон 03:30).

Как это устроено кратко: триггеры БД записывают в `sync_changes` «что тронуто» при любой записи (REST, sync, крон, восстановление); `pull` отдаёт текущее состояние тронутых строк; операции клиента (`opId`, HLC) решает чистая функция `decideOp` на узле под блокировкой. Код: `apps/api/src/sync/hybrid-sync.*`, `packages/shared-types/src/hybrid-sync*.ts`, `packages/core/src/sync/*`.

## Что существует сейчас

ORION использует локальный или серверный API с PostgreSQL. WebDAV применяется для зашифрованных полных снимков пространства, хранения и восстановления. Наличие двух копий базы на разных компьютерах **не** делает их синхронизированными. Перед релизом нужно заново проверить backup/restore на чистом сервере вместе с файлами документов, ключами и правами: [DEPLOYMENT_READINESS.md](DEPLOYMENT_READINESS.md).

Доступ к одной WebDAV-папке сам по себе не обеспечивает конфликтное объединение строк, мгновенное обновление чата или строгий read-only для участника, имеющего запись в папку. Уже скачанную копию данных физически отозвать нельзя. WebDAV-хранилище остаётся полезным для резервных копий и переносимых экспортов.

## LAN Host / Client (реализовано, ТЗ-04)

Первый шаг общего узла без облака: один компьютер — **хост** («Хост LAN»), остальные desktop-клиенты работают с его API по HTTPS внутри сети; аккаунты и данные принадлежат хосту. Базы **не** синхронизируются; клиент без связи показывает «узел не в сети» и ничего не пишет локально (offline — ТЗ-06). Обнаружение — mDNS `_orion._tcp` (без данных) или адрес вручную; доверие — подтверждение кодом на хосте и закрепление сертификата. Детали: [ADR-0015](adr/ADR-0015-lan-host-client.md). Проверено автотестами; на двух физических ПК ещё не проходило.

## Перенос пространства между узлами (реализовано, ТЗ-05)

Это не синхронизация и не восстановление: файл `.orion` для переноса (экспорт владельцем) импортируется на другом узле **как новое пространство** с новыми id, не затрагивая существующие данные; сначала предпросмотр с подсчётом коллизий id, затем подтверждение. Формат отличается от зашифрованной резервной копии узла (та привязана к `SYNC_SECRET`). Подробности и ограничения — [TEAM_AND_ACCESS.md](TEAM_AND_ACCESS.md).

## Рекомендуемая схема для командной работы

Один авторитетный ORION API + PostgreSQL + файловое хранилище обслуживают web, desktop и будущий mobile. Каждый запрос проходит аутентификацию, membership, module policy и RLS. Уведомления/обсуждения доставляются через сервер. Владелец может разместить сервер у себя; модель не требует конкретного облачного провайдера. WebDAV — отдельно для шифрованных резервных копий. Это рекомендация для первой закрытой web-беты, а не уже принятое решение о единственном будущем режиме.

Преимущества для первого релиза: единый источник истины, предсказуемый отзыв доступа на сервере, совместное редактирование с явным конфликтом и реальный чат. Требования: установка сервера, HTTPS, обновления, backup/restore, доступность узла и понятный режим при потере сети.

## Если сохранять самостоятельные локальные базы на каждом устройстве

Это отдельный дорогой проект, а не продолжение snapshot-backup. Нужны журнал изменений для каждой модели, стабильные ID, версии/векторные часы или другой механизм порядка, идемпотентность, tombstones, merge по типам данных, шифрование, защита от повреждённого удалённого состояния, миграция протокола и UX конфликтов. Для документов/таблиц требуется особенно явное правило конкурирующих правок. Сначала — двухустройственный прототип на одной модели с конфликтными изменениями, отключением сети, удалением и восстановлением; затем оценка по всем workspace-моделям. Чат в таком режиме всё равно требует relay либо честного асинхронного обмена, который нельзя выдавать за мгновенную беседу.

## Решение, которое должен подтвердить владелец

1. Основной режим ORION для личного/семейного и командного пространства: общий сервер, или два официальных режима (общий сервер и локальный одиночный узел)? Первый закрытый web-релиз в [DEPLOYMENT_READINESS.md](DEPLOYMENT_READINESS.md) планируется на одном сервере.
2. Каков требуемый offline-режим мобильного/desktop-клиента: только чтение ранее загруженного, безопасные локальные черновики или полная двусторонняя запись? До решения не обещать «offline sync».
3. Где будет работать сервер: локально у владельца или на выбранном хостинге? Это эксплуатационное решение, не часть модели сущностей.

До ответа агенты реализуют только проверяемое улучшение текущего backup и общесерверного beta-сценария; не запускают скрытую вторую архитектуру синхронизации. Связанные продуктовые принципы — [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md).
