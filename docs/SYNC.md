# ORION: устройства, совместная работа и WebDAV

Статус: продуктовая развилка на 11 октября 2026 года. Этот документ различает реализованный backup, рекомендованный общий режим и исследовательский local-first вариант. Он не заявляет, что двусторонняя синхронизация уже работает.

## Что существует сейчас

ORION использует локальный или серверный API с PostgreSQL. WebDAV применяется для зашифрованных полных снимков пространства, хранения и восстановления. Наличие двух копий базы на разных компьютерах **не** делает их синхронизированными. Перед релизом нужно заново проверить backup/restore на чистом сервере вместе с файлами документов, ключами и правами: [DEPLOYMENT_READINESS.md](DEPLOYMENT_READINESS.md).

Доступ к одной WebDAV-папке сам по себе не обеспечивает конфликтное объединение строк, мгновенное обновление чата или строгий read-only для участника, имеющего запись в папку. Уже скачанную копию данных физически отозвать нельзя. WebDAV-хранилище остаётся полезным для резервных копий и переносимых экспортов.

## Рекомендуемая схема для командной работы

Один авторитетный ORION API + PostgreSQL + файловое хранилище обслуживают web, desktop и будущий mobile. Каждый запрос проходит аутентификацию, membership, module policy и RLS. Уведомления/обсуждения доставляются через сервер. Владелец может разместить сервер у себя; модель не требует конкретного облачного провайдера. WebDAV — отдельно для шифрованных резервных копий. Это рекомендация для первой закрытой web-беты, а не уже принятое решение о единственном будущем режиме.

Преимущества для первого релиза: единый источник истины, предсказуемый отзыв доступа на сервере, совместное редактирование с явным конфликтом и реальный чат. Требования: установка сервера, HTTPS, обновления, backup/restore, доступность узла и понятный режим при потере сети.

## Если сохранять самостоятельные локальные базы на каждом устройстве

Это отдельный дорогой проект, а не продолжение snapshot-backup. Нужны журнал изменений для каждой модели, стабильные ID, версии/векторные часы или другой механизм порядка, идемпотентность, tombstones, merge по типам данных, шифрование, защита от повреждённого удалённого состояния, миграция протокола и UX конфликтов. Для документов/таблиц требуется особенно явное правило конкурирующих правок. Сначала — двухустройственный прототип на одной модели с конфликтными изменениями, отключением сети, удалением и восстановлением; затем оценка по всем workspace-моделям. Чат в таком режиме всё равно требует relay либо честного асинхронного обмена, который нельзя выдавать за мгновенную беседу.

## Решение, которое должен подтвердить владелец

1. Основной режим ORION для личного/семейного и командного пространства: общий сервер, или два официальных режима (общий сервер и локальный одиночный узел)? Первый закрытый web-релиз в [DEPLOYMENT_READINESS.md](DEPLOYMENT_READINESS.md) планируется на одном сервере.
2. Каков требуемый offline-режим мобильного/desktop-клиента: только чтение ранее загруженного, безопасные локальные черновики или полная двусторонняя запись? До решения не обещать «offline sync».
3. Где будет работать сервер: локально у владельца или на выбранном хостинге? Это эксплуатационное решение, не часть модели сущностей.

До ответа агенты реализуют только проверяемое улучшение текущего backup и общесерверного beta-сценария; не запускают скрытую вторую архитектуру синхронизации. Связанные продуктовые принципы — [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md).
