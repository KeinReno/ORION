# Orion Link — многоканальная синхронизация и соединение устройств

**Статус:** продуктовые требования согласованы в обсуждении 18.10.2026; приведённая ниже конструкция протокола — **проектное предложение, не реализованная функция**. Приоритеты и порядок внедрения определяет [PLATFORM.md](PLATFORM.md), фактическое состояние — [STATUS.md](STATUS.md), имеющийся протокол — [SYNC.md](SYNC.md) и [ADR-0016](adr/ADR-0016-hybrid-sync-protocol.md).

## 1. Цель и ограничения

Единый Orion для Windows, будущего Android-клиента (первое тестовое устройство — OnePlus) и позднее других платформ. Пользователь должен работать локально, без обязательной аренды сервера, даже при отключении интернета. **В перспективе собственный постоянно работающий сервер — планируемый основной координатор и авторитетный узел**. WebDAV/S3 — доступный промежуточный способ обмена и последующий резервный/дополнительный транспорт, **не постоянная замена сервера**.

Принципы:
- Offline-first там, где модель поддержана: локальные изменения сохраняются до доставки; без связи не обещается совместная работа в реальном времени.
- Нет привязки к одному провайдеру или сервису VPN; работа в сетях РФ требует эксплуатационных испытаний, не декларации совместимости.
- Синхронизация, резервные копии и удалённое управление — **три разные функции** с разными гарантиями.
- Orion Core владеет контрактами синхронизации и устройств. Orion Link — условное имя общего платформенного сервиса/набора транспортных адаптеров; **не создавать отдельный конкурирующий sync engine**.
- Изоляция по workspace, права, RLS, идемпотентность, версионирование и защита данных сохраняются при любом транспорте.

## 2. Что уже есть, а чего ещё нет

По документации репозитория на 18.10.2026 (проверять заново на конкретном commit):
- LAN host/client, mDNS + ручной адрес, TLS с pinning, pairing шестизначным кодом, доверенные устройства: реализованы в коде; двух физических ПК и Android не проверяли.
- Hybrid Sync: локальная копия IndexedDB, журнал и офлайн-операции для **списков/пунктов, заметок и задач**; серверные конфликты и повтор отправки для перечисленных типов; покрыто автотестами, физический end-to-end не подтверждён.
- WebDAV: зашифрованные **полные резервные снимки** с восстановлением; **не** канал двусторонней поэлементной синхронизации.
- Другие модели, включая документы, файлы, финансы и т. п., не получают офлайн-синхронизацию автоматически.
- Нет Android-клиента, cloud change relay, S3-адаптера, роутинга каналов, автоматического failover и Orion Link как готового продукта.
- Ограничение текущей локальной копии: она не зашифрована ключом устройства; нельзя называть её зашифрованной, пока не будет отдельной реализации и проверки.

Выполнение этапов определяется не формулировками здесь, а кодом, тестами и [STATUS.md](STATUS.md).

## 3. Целевая схема

```text
       Windows Orion                           Android Orion (OnePlus)
  UI + локальный клиент                    mobile UI + локальное хранилище
             |                                       |
          Sync Client <---- единый протокол ----> Sync Client
             |                                       |
       Orion Link Transport API (подбор доступного канала)
            |                |                  |
     LAN HTTPS/mDNS     WebDAV / S3          Future Orion Server
     прямой узел       шифрованный relay     авторитетный сервис
            \                |                  /
             ---- журнал операций / версии ----
                     |  отдельный путь |
                 Backup / Restore
```

Операции и правила разрешения конфликтов принадлежат Sync Engine; адаптеры только доставляют/получают зашифрованные пакеты, не реализуют свою предметную логику. Коммуникация приложений и ИИ-команды не наследуют «мгновенность» от облачного файлового обмена.

### Типы подключения

| Транспорт | Назначение | Ожидаемые свойства |
| --- | --- | --- |
| LAN | ПК и OnePlus в одной сети | Прямое защищённое соединение, обнаружение через mDNS или ручной адрес |
| WebDAV | Асинхронная доставка изменений через совместимое хранилище (в т. ч. проверяемая конфигурация Mail.ru/Яндекс/других) | Без собственного постоянно доступного сервера; задержки, квоты, сбои провайдера |
| S3-compatible | Альтернативный объектный backend, например совместимые сервисы Cloudflare/AWS и другие | Отдельные настройки/стоимость/региональные ограничения; не считать любой S3 бесплатным |
| Orion Server (будущее) | Основной авторитетный узел, многопользовательская координация, события и политика доступа | Постоянная доступность при корректном развёртывании; прямая онлайн-связь |
| P2P/туннель/relay (исследование) | Интерактивное управление вне LAN | Требует отдельного решения NAT traversal, доверия и доступности; Tailscale/Headscale/WireGuard — варианты исследования, не обязательная зависимость |

**Mail.ru через WebDAV и другие провайдеры — кандидаты, не гарантированные интеграции.** Перед реализацией проверить актуальные endpoint, авторизацию, правила провайдера, доступность из РФ, квоты, версии файлов, ETag/conditional writes, ограничения частоты запросов. Не полагаться на устные утверждения о поддержке.

## 4. Абстракция транспорта (предложение)

`SyncTransport` предоставляет обнаружение/проверку доступности, отправку и получение пачек изменений и checkpoint, безопасное подтверждение доставки, диагностические метрики. Контракт не должен включать доменные методы `syncNotes`/`syncTasks`: новые модули подключаются к Sync Engine через стабильные интерфейсы платформы. Каждый пакет содержит `protocolVersion`, `workspaceId`, `sourceDeviceId`, `batchId`, `operationIds`, границу курсора, целостность и указание шифрования. Форматы/семантика требуют отдельного ADR и версии протокола.

Стратегия выбора:
1. Устройство офлайн: запись в локальную очередь; не терять её при перезапуске.
2. Доступен прямой доверенный LAN/позднее сервер: предпочтительный путь.
3. Недоступен основной путь: доступный и разрешённый владельцем WebDAV или S3 как **асинхронный** запасной канал.
4. Когда основной канал вернулся: сверка checkpoint/операций и безопасная дедупликация, затем переключение.
5. Если оба канала недоступны: продолжать локально, показывать «не синхронизировано» и ошибки.

**Важно:** автоматическое переключение между двумя одновременно доступными write-endpoint нельзя выпускать без тестов split-brain, epoch/fencing или иного механизма единого порядка. Первая версия — явный выбор одного активного облачного транспорта и **ручное безопасное переключение** после сверки журналов; автоматический failover — следующий этап после доказанной сходимости. UI не должен говорить «синхронизировано», если операции лишь загружены в промежуточное облако, но не применены второй стороной.

## 5. Безопасность и конфликты

- В облако уходят только клиентски зашифрованные пакеты; ключи шифрования не хранятся рядом с данными в WebDAV/S3. Запроектировать отдельную модель управления ключами, обмена для пользователей и ротации, не смешивать с `SYNC_SECRET` резервных копий.
- Защита TLS в транзите, pinning/проверка peer в LAN; ограниченные разрешения, per-workspace ACL, журнал доступа и отзыва, отсутствие секретов в URL/logs.
- Версии операций, идемпотентность, tombstone, повторные доставки, дедупликация, курсоры, schema migrations и восстановление после частичных пачек.
- Для заметок сохранять явный UX конфликтов по revision; для задач — утверждённую доменную стратегию, не превращать LWW в универсальное «решение всего».
- Невозможно отозвать уже загруженные на устройство данные. Облачное хранилище, куда участник имеет запись, **само по себе** не реализует строгое read-only/отзыв; до сервера нужен специально спроектированный, документированный threat model.
- Backup — независимый снимок для восстановления; синхронизационные пакеты не заменяют резервные копии.

## 6. Приоритеты и критерии приёмки

Очередность согласована с [PLATFORM.md](PLATFORM.md): сначала закончить текущую стабилизацию/контракты, затем системную инфраструктуру sync, не запускать параллельную архитектуру в обход Core.

1. **База:** зафиксировать commit, проверить CI, текущий LAN и Hybrid Sync, сеть пропала/восстановилась, конфликты, отзыв прав и backup/restore на независимых тестовых узлах. Обновить устаревшие подсказки UI, не вводить пользователя в заблуждение.
2. **Контракты:** ADR о `SyncTransport`, формате пакета, ключах, версиях и критериях «доставлено/применено»; контракт независим от WebDAV/S3.
3. **WebDAV-прототип:** одна разрешённая модель (например Lists) между двумя независимыми экземплярами, без сервера, с зашифрованными операциями, рестартом, tombstone, конфликтами и повреждёнными ответами.
4. **Расширение:** заметки/задачи на том же протоколе, точное состояние синхронизации, ручное переключение облачного провайдера; затем S3 на идентичном контракте.
5. **Android:** мобильное локальное хранилище и связка OnePlus ↔ Windows по LAN и через выбранное облако (см. [ANDROID_CLIENT_PLAN.md](ANDROID_CLIENT_PLAN.md)).
6. **Будущий сервер:** тот же протокол/контракты, миграция без потерь очереди и workspace identities; server-first + cloud fallback там, где это безопасно. Интерактивные команды и удалённые агенты — отдельный защищённый канал.
7. **После доказанной сходимости:** автоматический выбор каналов/failover с испытаниями split-brain, ключей и политики доступа.

Приёмка: два независимых клиента сходятся при чередовании онлайн/офлайн и после crash; нет дублирования/потери операций; изменения не покидают разрешённое workspace; удалённый backend не может читать содержимое шифрованных пачек; ручное/автоматическое переключение не создаёт две расходящиеся истории.
