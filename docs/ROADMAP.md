# ORION: исполнимый план от текущего состояния до платформы

Срез: 11 октября 2026. Приоритеты — продуктовые; статус реализации нельзя выводить из этого списка. Каждый пункт закрывается только новой проверкой на текущем commit. Действующие правила разработки — [AGENTS.md](../AGENTS.md) и [ORION_CONSTITUTION.md](../ORION_CONSTITUTION.md).

## 0. Сверить фактическую базу

- Записать commit, рабочее дерево, версии зависимостей и матрицу существующих модулей/плагинов/слотов. Не переписывать уже закрытое по историческому отчёту.
- Прогнать `pnpm quality` и интеграционные тесты на отдельной чистой PostgreSQL; отдельно проверить миграции и `default-full`/выключенный plugin. В CI уже добавлены `architecture-check` (запрет Core/Base → конкретный frontend-плагин и plugin → внутреннюю панель/другой plugin) и `plugin-contract-check` (манифесты/реестр); плагинам доступны только `lib/extensions/contracts`, `host-api`, а реестру — ещё `registry`. DOCX/XLSX-кодеки перенесены в `apps/web/plugins/documents-office/codecs`, исключений `LEGACY_HOST_IMPORTS` больше нет.
- Браузерный baseline на 1280 px есть и проверяется в CI: `e2e/panels.spec.ts` открывает каждую панель в профилях `default-full` и «все плагины выключены», ловит ошибки страницы и сверяет перечень вкладок и кнопок с текстовым снимком (`e2e/__snapshots__`); скриншоты прикладываются к отчёту. Осталось: 720/390 px и узкая Dockview-панель. Для native smoke проверить собранное приложение; успешный web build этого не заменяет.

## 1. Закрытая веб-бета — блокеры до приглашения людей

1. **Права и границы данных.** Повторить негативные HTTP/SQL тесты RLS, restricted modules, выдачи/отзыва read-only grants, связанных сущностей, поиска, overview, backup и уведомлений. Grant читается через отдельный `GET /shared/:grantId/...`, не наследует соседние объекты и не даёт запись. Проверить `ENABLE/FORCE RLS` и роль приложения на свежей БД. Устранить оставшиеся дефекты до релиза.
2. **Публичный контур.** Доверие к `X-Forwarded-For` исправлено (`ORION_TRUSTED_PROXIES`); `server`-режим при старте проверяет секреты, HTTPS-origin, `PUBLIC_API_URL` и роль БД (`server-config.ts`); production-клиент без `NEXT_PUBLIC_API_URL` не использует `localhost:4000` на чужом хосте. Осталось подтвердить на staging: реальный прокси, перезапись `X-Forwarded-For`, недоступность API и БД напрямую.
3. **Восстановление.** Согласованный backup БД и файлов, а также восстановление на пустую БД со сверкой сумм реализованы (`apps/api/src/ops`, раздел «Резервная копия и восстановление узла» в `DEPLOYMENT_READINESS.md`); ключи/секреты хранятся отдельно, restore сверяет `SYNC_SECRET`. Осталось: расписание и срок хранения копий, ответственный, восстановление на другой машине, объём больше локального. Зафиксировать срок хранения, периодичность, ответственность и процедуру отката миграций/артефактов.
4. **Реальная установка.** Подготовить один воспроизводимый серверный пакет/скрипт с HTTPS, миграциями, persistent volumes, health/readiness и инструкцией обновления. Нативный инсталлятор пока содержит клиентское окно, а не автономные API+PostgreSQL; не называть его полноценной самостоятельной установкой.
5. **Приёмка.** Два реальных аккаунта на staging проходят создание личного и командного пространства, разные роли, документы/таблицы, финансы, связи, grant/revoke, два окна. Выполнить UI и клавиатурный smoke; результаты привязать к commit и среде.

Точный текущий статус каждого воротного условия ведётся в [DEPLOYMENT_READINESS.md](DEPLOYMENT_READINESS.md). Историческое «PASS» не переносится автоматически на новую ревизию.

## 2. Довести существующий интерфейс и модули

Сначала исправлять потерю данных, недоступные действия и ошибочные состояния; затем компоновку, визуальную иерархию и вторичные украшения. Работать небольшими вертикальными срезами с проверкой в живом UI, не одной перекраской всех панелей.

| Область | Следующий практический результат |
| --- | --- |
| Оболочка | постоянные иконки, понятное переключение пространств, устойчивые dock-layouts, узкие панели, открытие рядом/в новом окне и обратный путь без потери черновика |
| Проекты | читаемый обзор и статус; план/Гант, материалы, зависимости, сроки, стоимость и прогресс как связанные виды; без горизонтальной свалки карточек |
| Задачи и календарь | видимые основные действия, понятные фильтры/пустые состояния, создание события, доступные переключатели видов и работа с отношениями |
| Заметки | название, краткое «о чём», Markdown-содержимое; чистое превью списка, группировка, поиск, кнопки Markdown/команды, компактный редактор |
| Документы и таблицы | надёжные черновики и round-trip DOCX/XLSX, формулы/форматы/слияния/диаграммы без тихой потери; инструменты редактора и работа в узкой панели |
| Финансы, списки, имущество | счёт-источник операции, семейный/личный/рабочий контекст, понятные суммы; цепочка покупки и объекта с заметкой/напоминанием |
| Время и привычки | проверить реальную ценность; время запускать из задачи/проекта, привычки показывать в «Сегодня»; разрешить скрыть неиспользуемый модуль |

Критерий для каждого среза: основное действие понятно без постоянной обучающей подписи; нет пустой правой панели и беспричинной ширины; есть loading/empty/error/denied; клавиатура и 390/720/desktop/узкий Dockview работают; данные и права сохранены. Детальная спецификация — [FRONTEND_WORKSPACE_SPEC.md](FRONTEND_WORKSPACE_SPEC.md).

## 3. Связность, поиск и архитектурные контракты

- Единый публичный переход `openEntity(type, id, title?)` (`apps/web/lib/panel-bus.ts`) используется палитрой команд, блоком связей и списком активности проекта. Событие вне текущего окна календаря и операция вне загруженной страницы читаются по ID через API с проверкой прав; финансы переключаются на вкладку операций. Inbox, календарь, редактор заметок, обзор, материалы проекта и плагины (Гант, план, идеи) тоже переведены на `openEntity`; прямые `focusX` остались в дашборде, колокольчике уведомлений, палитре и «Доме» — их трогают параллельные срезы. Никакого расширения доступа по ссылке.
- Реализовать полезные цепочки из [PRODUCT_DIRECTION.md](PRODUCT_DIRECTION.md), начиная с задач/календаря/времени/финансов и списков/имущества. Не дублировать суммы при нескольких связях.
  Первая цепочка сделана: плагин-мост «Покупки → Склад» (`lists-inventory`, [ADR-0009](adr/ADR-0009-lists-inventory-bridge.md)) — пункт списка связывается с позицией склада, «Куплено» один раз пишет приход, позиция с низким остатком отправляется в список покупок. Вторая цепочка сделана: плагин «Покупки → Финансы» (`lists-finance`) — купленные пункты одним чеком становятся одной операцией-расходом, повторно не записываются.
- Проверить потребителей существующих `ModulesService.assertEnabledTx`/`accessibleSetTx`; не вводить третий параллельный механизм проверки доступа.
- Замер 11 октября (локальный PostgreSQL 16, одно пространство, 100 000 задач и 50 000 заметок): глобальный поиск через `ILIKE %…%` занимает 34–217 мс на запрос без индекса. Для личных/семейных объёмов этого достаточно, а переход на `tsvector` отнял бы поиск по части слова, поэтому поведение не менялось. Возвращаться, если замер на реальных данных покажет >300 мс; вариант без потери семантики — `pg_trgm` GIN. Пагинация крупных списков и полнотекстовый поиск поверх имеющихся индексов вместо бесконечного `contains`; индексирование содержания PDF/DOCX/XLSX — отдельно, с правами и обновлением индекса.
- Импорты плагинов из внутренних `apps/web/lib/*` и `components/*` переведены на `lib/extensions/host-api.ts` (66 импортов, 31 файл), запрет включён в CI. Кодеки `lib/office` перенесены в плагин. Осталось: проверка Base с выключенным плагином / parity `default-full` в браузере.

## 4. Новые пользовательские возможности

1. Контакты как базовая сущность с заметками, связями и напоминаниями — **первая версия сделана (14.10):** модуль `contacts` поверх той же таблицы, что контакты «Дома» (`homeId` необязателен, удаление дома контакты не удаляет), поиск, тип `contact` в связях и напоминаниях, палитра команд. **Расширено (15.10):** несколько телефонов/почт/мессенджеров, организации, теги, избранное, архив, дни рождения (календарь, дашборд, уведомления), журнал общения и «связаться раз в N дней», связи между контактами, импорт/экспорт vCard и CSV, поиск и слияние дубликатов, массовые действия — см. `apps/api/src/contacts/MODULE.md`. CRM-воронка — по-прежнему опциональное расширение.
2. Обсуждения пространства/проекта на общем сервере: membership, непрочитанное, ссылки и уведомления; без попытки заменить мессенджер.
3. Настоящий мобильный клиент с мобильными сценариями, единым API и честным offline-статусом.
4. Шаблоны пространств «Дом»/«Работа» как конфигурации модулей и видов, без нового уровня доступа. **«Дом» сделан (15.10, ТЗ-05):** шаблон при создании пространства; вместе с ним приглашения с ролью, код приглашения, аудит изоляции и перенос базы `.orion` как нового пространства — [TEAM_AND_ACCESS.md](TEAM_AND_ACCESS.md). «Работа» и профиль устройств пользователя (ТЗ-05 §5.6) — не сделаны.
5a. **Agent Manager сделан (15.10, ТЗ-03):** режимы токена (наблюдатель / помощник / менеджер), матрица прав, забор по проектам, запросы на изменение с превью, журнал с откатом создания и CSV, «Отозвать все» — [ADR-0007](adr/ADR-0007-ai-bridge.md). Удалённый доступ для ChatGPT — только исследование, ждёт решения владельца: [ADR-0017](adr/ADR-0017-agent-remote-access.md). Не сделано: предупреждение «объект изменился после запроса» при подтверждении, описание режимов в MCP-инструментах.
5. Гибридная синхронизация (ТЗ-06, [ADR-0016](adr/ADR-0016-hybrid-sync-protocol.md)) — **этапы 0–3 сделаны для списков, заметок и задач** (15.10): локальная копия, очередь записи, конфликты. Остаются: принятие ADR владельцем, ручная проверка UX конфликтов на двух ПК, миграция остальных LWW-моделей (`later` в классификации), шифрование копии и подпись операций, этап 4 (интернет/relay/мобильные) — только после решения владельца. Подробности и границы — [SYNC.md](SYNC.md).
6. Canvases/mind map после решения ADR и проверки контрактов связей; Knowledge Hub после стабильной базы.

## 5. Платформа и внешние проекты

1. API для ИИ-клиентов: версии, ограниченные токены, аудит, preview опасных действий; затем MCP-адаптер.
2. Внутренний каталог и управление жизненным циклом встроенных расширений. Публичный marketplace только после проверенного SDK и модели безопасности.
3. Outbox/event bus и очередь — по измеренной потребности, не как предварительное условие UI-беты.
4. Интеграция FinControl после сверки источника и модели финансов; Compass Vertex — последним. Не переносить внешние данные или UI без отдельного контракта и приёмки.

5. LAN Host/Client (ТЗ-04, [ADR-0015](adr/ADR-0015-lan-host-client.md)): режимы узла, mDNS, доверие устройств, TLS реализованы и покрыты автотестами; **приёмка на двух физических ПК и сборка установщика с режимом хоста ещё не выполнены** — сценарий в [DEPLOYMENT_READINESS.md](DEPLOYMENT_READINESS.md).

## Порядок и пределы

**Безопасная бета → законченные текущие сценарии → связность и масштаб → чат/мобильное приложение → AI API → каталог/marketplace → внешние интеграции.** Этапы могут пересекаться в независимых срезах, но новая функция не закрывает дефект прав, восстановления или потери данных. Не считать «готовым» то, что есть только в документации.
