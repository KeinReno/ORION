# ORION — жизненный цикл и приоритет документации

**Вступило в силу:** 19.10.2026. **Назначение:** один понятный путь от документа к проверяемому коду, без уничтожения истории.

## Классы и источник истины

| Тип | Метка | Что означает | Приоритет |
|---|---|---|---|
| Конституция и утверждённая продуктовая стратегия | `GOVERNING` | Архитектурные инварианты и цель развития, пока владелец явно не меняет решение | [ORION_CONSTITUTION.md](../ORION_CONSTITUTION.md), [PLATFORM.md](PLATFORM.md), [AGENTS.md](../AGENTS.md) |
| Контракт/API и нормативная карта владения | `NORMATIVE` | Обязателен после принятия; незавершённая реализация указывается отдельно | [MODULES_AND_PLUGINS.md](MODULES_AND_PLUGINS.md), [AI_REFACTOR_MIGRATION_MAP.md](AI_REFACTOR_MIGRATION_MAP.md), [platform-api/](platform-api/) |
| Фактический статус реализации | `CURRENT-SNAPSHOT` | Проверяемое утверждение **только для указанного HEAD**; устаревает после изменений | [STATUS.md](STATUS.md), исходники и тесты |
| Одобренный ADR | `ACCEPTED` | Решение и причины; даже если код изменился, ADR не переписывается без `Superseded by` / новой записи | [adr/](adr/) |
| Предложение / будущее направление | `PROPOSED` | Сохраняет идею; **не разрешает реализацию** | [PRODUCT_IDEAS_2026-10-18/](PRODUCT_IDEAS_2026-10-18/), концепции, ещё не принятые ADR |
| Завершённое ТЗ, отчёт, ревизионный аудит | `HISTORICAL` / `COMPLETED` | Доказательство на определённом commit; **не текущая команда разработчику** | [archive/README.md](archive/README.md) |
| Тестовые материалы | `FIXTURE` | Образцы для демонстрации/тестов, не продуктовые требования | `scripts/demo-content/` |

**При коллизии «документ ↔ код»:** контракт требует анализа и теста; код показывает фактическое поведение, но не отменяет архитектурный запрет. Агент сообщает расхождение и предлагает исправление, а не объявляет любую реализацию допустимой. **При коллизии двух документов:** решение владельца / действующий `ACCEPTED` ADR и соответствующий `NORMATIVE` документ выше старого ТЗ; даты сами по себе не дают прав отменять архитектуру.

## Обязательный порядок для ИИ-агента

1. Прочитать `AGENTS.md`, `ORION_CONSTITUTION.md`, `PLATFORM.md` и `STATUS.md`.
2. Установить SHA `git rev-parse HEAD` и состояние рабочей копии `git status --short`; определить, относится ли документ к этому SHA.
3. Прочитать соответствующий `MODULE.md` / `AI_CONTEXT.md`, применимые принятые ADR, `platform-api` и текущие типы/тесты. В автогенерируемых блоках запускать `pnpm module-docs:check`, не править их руками.
4. Описать дельту между существующей реализацией и желаемой, не повторять уже сделанное.
5. Для изменения публичного контракта, прав, границ данных или ownership — сначала ADR / Extension Proposal, затем тесты и реализация. Исторический отчёт не является разрешением на работу.
6. В том же PR обновлять `STATUS.md` (изменение фактов), соответствующую спецификацию/паспорт (изменение контракта), и ссылки/индекс при появлении новой папки. В отчёте раздельно показывать `passed`, `failed`, `not run`, ОС и SHA.

## Правила архивирования без поломки ссылок

- Первоначальные ТЗ и рабочие отчёты *не удалять* и *не перемещать автоматически*: относительные ссылки на изображения, исходные evidence и ссылки из ADR должны работать.
- У завершённого пакета — ссылка на индекс [archive/README.md](archive/README.md), предупреждение в README пакета и, при необходимости, в каждом исполнимом старом ТЗ.
- Исходные результаты тестов, дефекты, решения и даты **сохранять дословно**; противоречивые «сейчас/нет» исправлять примечанием `Статус на HEAD` либо ясно обозначать как исходный срез.
- Не считать любой `PROPOSED` ADR или продуктовое предложение устаревшим только из-за отсутствия кода.
- Нет массового удаления и массового переноса до проверки ссылок, импортов, названий путей в тестах, scripts и документах.
- Не менять автоматически сгенерированные `MODULE.md`, `AI_CONTEXT.md` или `AGENT_MANUAL.md`: корректировать генератор/манифест и запускать проверку.

## Регулярная проверка

После значимых PR: статус и ссылки, соответствие паспорта и манифеста, корректная классификация `PROPOSED/ACCEPTED/HISTORICAL`; при релизе: fresh CI, Windows/Tauri, два физических устройства и реальные интеграции **отдельно** от документационных правок. Документационная уборка не является выпускной приёмкой.
