# ORION — предпросмотр перед Beta

## Принцип

Изменения проходят отдельный Draft PR в KeinReno/ORION. Ни один предпросмотр
не публикует релиз и не подменяет установленный Orion. Пользователь получает
исходники PR в отдельной локальной папке и проверяет UI и функции. Публикация
Windows Beta разрешается только после явного одобрения конкретного PR/commit.

## Скачать и открыть PR на основном Windows ПК

Однократно положить файлы scripts/review-pr.mjs и scripts/review-pr.cmd
в папку scripts/ своей основной Git-копии Orion. Они входят в PR #94;
после принятия инфраструктуры останутся в репозитории.

Дважды щёлкнуть scripts/review-pr.cmd, указать номер PR (например 94).
Или выполнить из корня основного checkout:

    node scripts/review-pr.mjs 94

Что произойдёт:

- Git прочитает refs/pull/94/head непосредственно из origin KeinReno/ORION;
- код попадёт в соседнюю папку ORION-Review/PR-94 как отдельный Git worktree;
- основной рабочий checkout, master и установленная программа не изменятся;
- зависимости будут установлены в preview worktree (нужны Node 24,
  Corepack/pnpm и Git с доступом к приватному репозиторию);
- запустится отдельное демо на http://localhost:3020, с локальным API :4010
  и PostgreSQL :5435, с демо-данными и базой внутри preview checkout.

Для скачивания исходников без запуска:

    node scripts/review-pr.mjs 94 --download-only

Повторный запуск обновит preview до актуального SHA PR, **но откажется менять
preview worktree при обнаружении локальных правок в отслеживаемых файлах**.
Локальные .env и демонстрационная БД остаются в отдельной preview папке.
При занятых портах :5435/:4010/:3020 проверка не запустится, чтобы не
подключиться к чужому сервису.

Тестовый предпросмотр — web-UI и API с демо-данными; это **не сборка
нативного Tauri/NSIS**, поэтому специфические для Windows/Tauri интеграции
нужно отдельно проверять перед выпуском беты.

## Приёмка

Пользователь сообщает, что исправить; новые изменения пушатся в тот же
PR, и предпросмотр загружается повторно. После явной команды «PR #N одобрен,
выпускай Beta» фиксируется SHA принятой версии.

**Нет автоматического выпуска беты при каждом коммите в PR или master.**

## Что происходит после одобрения

Для принятого SHA уполномоченный агент создаёт отдельную ветку вида
release/approved-beta-N (например release/approved-beta-94) из точно этого
commit. Push в эту ветку вызывает workflow
.github/workflows/windows-beta-release.yml:

- self-hosted Windows x64 runner на сборочном компьютере;
- typecheck, lint, целевые unit-тесты и NSIS build;
- автоматический номер следующей Beta после последней публикации;
- вычисление SHA-256 и GitHub Release с установщиком.

Если runner недоступен, job не стартует и релиз не появляется: публикация
не подделывается. Владелец может запустить локальную публикацию командой
node scripts/publish-windows-beta.mjs auto из принятого checkout вместо
GitHub workflow.

**Для действия агента по созданию release/approved-beta-N требуется явное
одобрение в диалоге.** Проверять одобренный SHA, не заменять его более
новой непроверенной версией.

После реальной публикации установщик появляется в GitHub Releases, а
установленная Windows-бета Orion обнаруживает его в Настройки → Обновления
при действующем GitHub token с Contents:read.

## Ограничения

Ассистент с GitHub-интеграцией может изменять исходники и создавать ветки
PR и approved-release, но не имеет постоянно работающей собственной Windows
среды. Само нативное исполняемое приложение собирается на Windows ПК/runner;
запуск self-hosted runner требует его однократной установки владельцем.
