# ORION-13 — Права ИИ-агентов: расширяемая матрица разрешений

> **Статус:** APPROVED BACKLOG / к технической сверке, не реализовано этим документом. **Дата согласования:** 27.10.2026. **Приоритет:** P1. **Область:** Agent Manager/RBAC.  
> **Источник:** наблюдение пользователя в установленном Orion и согласование продуктовых решений. Техническая причина и соответствие текущему HEAD пока не установлены.

## Проблема

Часть чекбоксов/разрешений некликабельна и не объясняет причину. Пользователь хочет более гранулярные полномочия.

## Задачи для реализации

- Аудит фактических разрешений и disabled states: отсутствующая capability, политика, роль, дефект UI.
- Управление по операциям read/create/update/delete/execute и областям workspace/project/module при соблюдении существующих контуров безопасности.
- Профили привилегий, preview расширения прав, подтверждение чувствительных операций, журнал, отзыв прав.
- Серверная проверка полномочий и UI объяснения причины запрета.

## Критерии приёмки

1. Каждый disabled пункт показывает конкретную причину; работающие permissions можно менять по правилам.
2. Изменение прав отражается при следующей операции агента и заносится в аудит.
3. Доступ к чужому пространству/ресурсу невозможен даже при подмене клиента.

## Зависимости

Существующие Agent Manager/ADR, API/RLS и capability contracts.

## Риски / ограничения

Нельзя «разблокировать» только UI и считать разрешение реализованным.

## Инструкции исполнителю

1. Перед реализацией прочитать `AGENTS.md`, `docs/PLATFORM.md`, `docs/STATUS.md`, `docs/AI_REFACTOR_MIGRATION_MAP.md`, локальный `MODULE.md` и применимые ADR.
2. Сверить наличие функций/дефектов на текущем HEAD и в установленной сборке; не переписывать уже работающий механизм без доказательства необходимости.
3. Для новых API, capabilities, прав или границ Core/Module/Plugin — сначала согласовать публичные контракты/ADR; не импортировать internals другого модуля.
4. Добавить необходимые модульные/контрактные и UX/регрессионные проверки; проверить desktop/Tauri и узкий Workbench.
5. В отчёте указать commit SHA, изменённые файлы, доказательства приёмки и тесты `passed/failed/not run`. Не объявлять документ подтверждением готовности продукта.
