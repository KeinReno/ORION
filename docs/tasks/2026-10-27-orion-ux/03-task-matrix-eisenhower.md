# ORION-03 — Матрица: гибкие две оси + Эйзенхауэр

> **Статус:** APPROVED BACKLOG / к технической сверке, не реализовано этим документом. **Дата согласования:** 27.10.2026. **Приоритет:** P1. **Область:** Проекты → Задачи → Матрица; План.  
> **Источник:** наблюдение пользователя в установленном Orion и согласование продуктовых решений. Техническая причина и соответствие текущему HEAD пока не установлены.

## Проблема

Представление почти дублирует Доску. Согласовано превращение в интерактивную двумерную аналитику, включая предложенную Варей матрицу Эйзенхауэра.

## Задачи для реализации

- Настраиваемые оси и пресеты: важность×срочность (4 квадранта Эйзенхауэра), статус×приоритет, исполнитель×загрузка, проект×риск при наличии данных.
- Задачи распределяются по ячейкам по явным атрибутам, а не только по координатам. Drag-and-drop пересчитывает соответствующие свойства с предпросмотром.
- Создание внутри ячейки, мультивыделение, пакетное редактирование, аналитика плотности/перегруза, drill-down.
- Один и тот же режим Эйзенхауэра доступен в задачах и из планирования без дублирования данных; фокус/перепланирование при добавлении важных задач.

## Критерии приёмки

1. Каждая задача отображается в ожидаемом квадранте; перенос изменяет только обусловленные выбранными осями поля.
2. Срочность, важность, дедлайн, приоритет и риск остаются различными понятиями.
3. Настройки матрицы сохраняются и работают с фильтрами/правами; пустые значения имеют определённое место.

## Зависимости

Контракт явной важности/срочности и API редактирования; общие команды/DnD.

## Риски / ограничения

Не вычислять важность только из приоритета, а срочность только из даты без прозрачного правила.

## Инструкции исполнителю

1. Перед реализацией прочитать `AGENTS.md`, `docs/PLATFORM.md`, `docs/STATUS.md`, `docs/AI_REFACTOR_MIGRATION_MAP.md`, локальный `MODULE.md` и применимые ADR.
2. Сверить наличие функций/дефектов на текущем HEAD и в установленной сборке; не переписывать уже работающий механизм без доказательства необходимости.
3. Для новых API, capabilities, прав или границ Core/Module/Plugin — сначала согласовать публичные контракты/ADR; не импортировать internals другого модуля.
4. Добавить необходимые модульные/контрактные и UX/регрессионные проверки; проверить desktop/Tauri и узкий Workbench.
5. В отчёте указать commit SHA, изменённые файлы, доказательства приёмки и тесты `passed/failed/not run`. Не объявлять документ подтверждением готовности продукта.
