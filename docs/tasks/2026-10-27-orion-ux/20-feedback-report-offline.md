# ORION-20 — Обратная связь: баг-репорт при сбое API

> **Статус:** APPROVED BACKLOG / к технической сверке, не реализовано этим документом. **Дата согласования:** 27.10.2026. **Приоритет:** P1. **Область:** Обратная связь/Diagnostics.  
> **Источник:** наблюдение пользователя в установленном Orion и согласование продуктовых решений. Техническая причина и соответствие текущему HEAD пока не установлены.

## Проблема

На скриншоте отправка «Баг» заканчивается «Не удалось отправить», предположительно API/БД не запущены.

## Задачи для реализации

- Проверить реальную цепочку feedback→API→GitHub, ошибки auth/отсутствия базы/сети; воспроизвести на Windows.
- Локальный черновик и безопасная очередь отправки с повтором, idempotency и статусами; не терять введённый текст.
- Понятное сообщение об ошибке, явный ручной повтор, при возможности резервная внешняя отправка без секретов.
- Диагностика по согласию: версия UI/API, commit, платформа, обезличенные логи/скриншот с предпросмотром.

## Критерии приёмки

1. При недоступном API отчёт сохраняется локально и отправляется при восстановлении сети или по ручной команде.
2. Одна жалоба не создаёт дубликатов после повторов; пользователь видит статус.
3. Токены, URL с секретами и личные данные не уходят без явного разрешения.

## Зависимости

№14 (build provenance), feedback API, хранение локальной очереди.

## Риски / ограничения

Прямая запись в GitHub может требовать авторизацию; не считать её гарантированным fallback.

## Инструкции исполнителю

1. Перед реализацией прочитать `AGENTS.md`, `docs/PLATFORM.md`, `docs/STATUS.md`, `docs/AI_REFACTOR_MIGRATION_MAP.md`, локальный `MODULE.md` и применимые ADR.
2. Сверить наличие функций/дефектов на текущем HEAD и в установленной сборке; не переписывать уже работающий механизм без доказательства необходимости.
3. Для новых API, capabilities, прав или границ Core/Module/Plugin — сначала согласовать публичные контракты/ADR; не импортировать internals другого модуля.
4. Добавить необходимые модульные/контрактные и UX/регрессионные проверки; проверить desktop/Tauri и узкий Workbench.
5. В отчёте указать commit SHA, изменённые файлы, доказательства приёмки и тесты `passed/failed/not run`. Не объявлять документ подтверждением готовности продукта.
