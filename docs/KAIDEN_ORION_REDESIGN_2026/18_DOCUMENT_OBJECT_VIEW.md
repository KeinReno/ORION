# 18. Самостоятельное представление файла

Дата: 2026-10-16. Основа: `ace8ee6`. Продолжение общей объектной навигации этапов 15–17.

## Что доступно

Файл можно открыть собственной вкладкой, рядом или отдельным окном через общее меню «⋯» в заголовке предпросмотра документов, результатах поиска, связанных записях и материалах проекта. Обычное открытие по названию сохраняет прежнее поведение. Повторное открытие той же вкладки фокусирует существующий экземпляр.

Зарегистрирован `document:<id>` с navParent documents. Новая DocumentPanel использует тот же PreviewPane и публичный слот documents.editor: при наличии подходящего редактора работает существующий плагин, иначе FilePreview. Самостоятельной копии содержимого/хранилища/офисного редактора нет. Название, изменённость и состояние сохранённости активного файла передаются через прежний ObjectContextScope; режим автосохранения конкретному плагину не приписывается.

В новой панели доступны содержимое, скачивание, связи и доступ из общего предпросмотра. Управление именем, перемещение, корзина и прежние действия истории остаются в полном модуле «Документы». Офисное сохранение выполняется прежней кнопкой редактора и прежним content API. Скачивается сохранённый файл по действующим правилам модуля.

## Данные, права и ввод

- Метаданные загружаются через useDocuments текущего workspace. Только активная запись kind=file может стать самостоятельным представлением. Удалённый/чужой/неизвестный ID получает общий placeholder без имени и содержимого; заголовок вкладки сбрасывается к нейтральному «Документ».
- Поиск и связи адресуют как файлы, так и папки. ObjectOpenMenu читает общий кэш разрешённых метаданных только для document в текущем пространстве при включённом модуле. У папки или ещё не подтверждённого файла нет фиктивного standalone-меню. Байты не запрашиваются ради проверки меню.
- Чтение/запись байтов проходят прежний API с серверной авторизацией. ViewRef и panelId сами не дают доступа. Материалы проекта ссылаются на исходный файл, а не создают новый.
- При временной ошибке фонового обновления метаданных уже загруженный редактор остаётся на месте, показывается предупреждение с повтором. Ответы 401/403/404 не используют кэш как разрешение: содержимое и метаданные активного объекта скрываются.
- Dirty callback редакторского слота подключён к useUnsavedDraft и beforeunload самостоятельной панели. PreviewPane передаёт также состояние несохранённого/отправляемого переименования из полного модуля. Рабочие guards блокируют переход, который закроет несохранённый файл.
- Ошибка записи оставляет содержимое в текущем редакторе; повтор выполняется штатной кнопкой. Постоянное восстановление несохранённого содержимого после принудительного завершения приложения этим срезом не добавлено и не проверено. Сообщение существующего плагина не является доказательством такой сохранности.
- Новый бизнес-API, схема БД, зависимости, правила преобразования DOCX/XLSX, ownership и plugin registrations не менялись. Конкретные офисные плагины в Base не импортируются. Основной Desktop/ORION и его БД не затронуты.

## Проверка

Итоговые значения: [validation.json](evidence/document-object-view/validation.json). Снимки: [DOCX](evidence/document-object-view/document-office.png), [просмотр без плагинов](evidence/document-object-view/document-viewer.png), [XLSX](evidence/document-object-view/document-sheet.png).

На финальном коде прошли 809 unit-тестов (105 файлов), 10 проверок контрактов плагинов, полный typecheck и architecture-check. Lint: 0 ошибок, 2 прежних предупреждения CalendarPanel:361 и DocumentsPanel:261. Последовательно выполнены desktop static export (47 страниц), production-сборка API/web и полный browser regression: **68/68, 3,1 минуты**, включая три новых сценария документов. Отдельный повтор после итогового browser regression не требовался; код и таймауты в ходе этого запуска не менялись.

Новые browser-сценарии на синтетических аккаунтах и изолированных API/БД:

1. Создать DOCX штатным documents.create → открыть отдельной вкладкой → изменить текст → получить 503 при content POST и при фоновом обновлении метаданных → повторить обновление сведений без потери текста → сохранить текст при 1920→390→1920 и заблокированном переходе → повторить сохранение → перезагрузить → открыть отдельное окно и прочитать сохранённый текст. Проверяются тот же ID, единственная запись, workspace/instance окна и контекст сохранения документа.
2. Выключить все плагины → загрузить текстовый файл через API → открыть из поиска рядом → проверить содержимое и исходные байты. Поиск папки не показывает standalone-меню. Ответ 403 после загрузки скрывает содержимое; повтор восстанавливает разрешённый просмотр. Другой пользователь/пространство не видит имя и содержимое; после удаления собственный файл также показывает placeholder.
3. Создать XLSX штатным plugin action → открыть отдельной вкладкой → увидеть существующую таблицу/инструменты → проверить, что просмотр не переписал байты и не создал копию. Это smoke XLSX-host, не повторная приёмка всех формул/диаграмм/сводных таблиц.

Среда: web 3110 / API 4100 / PostgreSQL 5547. Проверки чтения и сохранения используют реальный API; 503 моделируется только в браузерном тесте. Native Tauri/физические мониторы, вся матрица форматов и конкурентная запись в один файл несколькими редакторами этим срезом не подтверждаются.

## Продолжение и откат

Остаются история переходов, сериализуемое view state и восстановление окон/фильтров/скролла, полный каталог видов, команды в сетках календаря и визуальная миграция внутренних экранов. Самостоятельная панель не закрывает эти фазы. Откат не требует миграций БД или удаления пользовательских файлов.
