# 10. Контекст задачи в рабочей оболочке

Дата: 2026-10-16. Продолжение этапа 09, ветка `redesign/kaiden-foundation-20261015`, [draft PR #1](https://github.com/KeinReno/ORION/pull/1).

## Что работает

В Precision верхняя строка показывает название задачи и состояние её автосохранения. Источник — существующий TaskDetail, общий для модуля задач, проекта и самостоятельной панели. Второй редактор или новый слой поверх списка не добавлены. На широком экране детали остаются рядом со списком/доской; на узком заменяют список с возвратом «Задачи».

Открытая задача проекта временно скрывает инспектор проекта. После закрытия задачи инспектор возвращается, если был открыт. На узком экране в верхней строке приоритет у названия активного объекта; название пространства доступно через переключатель.

В Core React добавлен публичный контракт PanelObjectContext: workspaceId, panelId, entityType/entityId, title, saveState и hasPendingChanges. Реестр живёт в текущем JS-окне, адресуется парой workspaceId/panelId; оболочка читает только активную панель текущего пространства. Модули публикуют метаданные через SDK. Core не импортирует реализацию задач или конкретные плагины. Позднее снятие регистрации прежнего редактора не удаляет новый контекст.

## Сохранность ввода

Пока автосохранение полей задачи не закончено, завершилось ошибкой или ожидает разрешения конфликта, переход к другой задаче и закрытие встроенных деталей удерживают текущий редактор. Интерфейс предлагает дождаться сохранения или устранить ошибку. После успешного сохранения переход снова доступен. Можно переключиться на другую сохраняющуюся вкладку Dockview и вернуться к прежнему тексту. Переход между широким и узким режимом теперь меняет размер одного контейнера, сохраняя экземпляр редактора: прежняя смена div/ResizablePane пересоздавала TaskDetail и теряла несохранённые поля. Этот дефект выявлен новым браузерным сценарием и устранён.

Этот же признак подключён к существующей защите закрытия вкладки, выхода и смены пространства. Явное подтверждение отказа от черновика остаётся существующим пользовательским действием. При перезагрузке/закрытии браузера установлен beforeunload; фактический показ системного предупреждения зависит от браузера. Постоянного локального хранилища черновиков задач этот срез не добавляет. Сообщение об ошибке больше не обещает сохранение на диск: задача должна оставаться открытой до повтора/выбора версии.

CAS и существующие действия «Загрузить версию сервера» / «Сохранить мою поверх» сохранены. Обёртка сохранения задачи проекта теперь возвращает сохранённую Task редактору, чтобы следующая правка сразу использовала новую revision и не зависела от скорости повторной загрузки списка. Повторное сохранение проверяется отдельно.

## Затронутые области

- `packages/core-react/src/object-context*`: публичный frontend-контракт, публикация, чтение, изоляция и тесты реестра.
- `apps/web/app/(app)/layout.tsx`: scope панелей, заголовок/сохранение активной задачи, условие инспектора.
- `apps/web/app/panel/[panelId]/panel-window.tsx`: тот же scope и учёт несохранённых полей в отдельном окне.
- `apps/web/panels/tasks/task-detail.tsx`: регистрация контекста и незавершённого сохранения, защита закрытия, перенос строк при ошибке и узкая форма.
- `apps/web/components/resizable-pane.tsx`: выключение изменения ширины без пересоздания дочернего редактора.
- `TasksPanel.tsx`, `projects/project-tasks.tsx`, `ProjectWorkspacePanel.tsx`, `lib/use-object-navigation.ts`: защита смены задачи и ухода с раздела проекта.
- `packages/ui/src/autosave-status.tsx`: необязательный errorText; прежние редакторы сохраняют существующий текст.
- `e2e/task-object-context.spec.ts`: проверка через реальный API и сборку приложения на синтетических учётных записях.

Новые зависимости, SQL-миграции, доменные поля и смена прав доступа не требуются. Бизнес-операции остаются в действующих API/SDK. Старые темы доступны; включение Precision остаётся явной настройкой. Основной checkout на Desktop и его БД не изменялись.

## Повтор проверки и запуск локальной демонстрации

Для этой версии Next.js desktop export оставляет экспортированные файлы в `.next-desktop`, но промежуточную сборку формирует в `.next` (в required-server-files.json у export указаны distDir `.next`, output `export`). Поэтому сборки нужно запускать последовательно: сначала desktop export, затем web production build с NEXT_PUBLIC_API_URL `http://localhost:4100`, после него next start на 3110. Нельзя запускать desktop export во время проверки/работы production preview: он подменяет его промежуточные файлы. Этот эффект воспроизведён при проверке, диагностирован по trace запросов к стандартному 4000 и устранён для финального прогона правильным порядком сборки. Отдельное исправление общего build tooling остаётся за пределами контекста задач.

## Оставшиеся этапы

1. Аналогичный контекст заметок/документов; отдельно — постоянное восстановление черновиков задач и приёмка остальных редакторов/плагинных полей.
2. Завершить универсальные ObjectRef/ViewRef, provenance смешанных пространств и восстановление выбранных объектов/подвидов после перезапуска. PanelObjectContext — только текущие метаданные редактора, не готовый каталог объектов.
3. Theme Engine: сохранение custom theme, независимый выбор оболочки/палитры, per-space overrides, проверка light/dark/custom во всех модулях.
4. Последовательный редизайн внутренних экранов модулей согласно документам 00–05. Этот срез связывает существующий редактор задач с оболочкой; это не полная визуальная миграция модуля задач.
5. Native gates: Tauri-окна, восстановление с двумя пространствами, несколько физических мониторов, показатели скорости и масштабирование. Web export не заменяет эти проверки.
