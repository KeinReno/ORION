# Решения и расхождения с исторической документацией

## D01 · Два равноправных сценария · принято владельцем

Пользователь явно выбрал личный и командный сценарий как равноправные. Это новее утверждений «single-user product» в комментариях NotificationPolicyService и ограничения «таймер на workspace». Эти ограничения сохраняются как факт текущей реализации, но должны измениться по S06/S07.

## D02 · Сохранить стек · предложение плана

Нет доказанной причины менять Nest/Prisma/Postgres, shared client, Next/Tauri, dockview. Изменения вертикальные и адресные. Это сохраняет вложенные усилия и снижает риск регрессий. Новая база/микросервисы/plugin runtime не требуются.

## D03 · Модули/плагины · сохранить существующий контракт

Compiled-in расширения; team расширяет tasks. Идентичность, роли, membership, policy, личные уведомления и время — core domain responsibilities, не отключаемая безопасность. Marketplace отложен.

## D04 · Дизайн · уточнение существующего направления

UI_UX_DESIGN остаётся историческим источником направления. Semantic tokens и AutosaveStatus уже реализованы — не делать заново. Двойной shrink compact следует исправить. Настройки WebGL/стекла/курсора не удалять и не сбрасывать; новые defaults спокойные. Это предложение плана, не отдельное одобрение владельцем конкретных значений CSS.

## D05 · Подтверждения · исправить противоречие

Старый UI_UX_DESIGN называет действия необратимыми, одновременно описывая возврат через корзину. В новом контракте обратимость определяется реальным backend. Bulk move не требует typed confirmation автоматически; restore/постоянное массовое удаление требуют. Основание: `rule/destructive-proportional`.

## D06 · Sync · название должно соответствовать поведению

Стадия 1 — резервные копии, не двусторонняя синхронизация. Пока backup неполон, явно говорить о составе и ограничениях; существующий `.orion` нельзя сделать полным переименованием. Совместная команда работает через один авторитетный сервер, offline sync не является prerequisite.

## D07 · Режим доступа · предложение плана

Local account picker/PIN не должен автоматически становиться сетевым login. Явные local/server режимы. Server mode до hardening заблокирован для выпуска. Это не требование публиковать проект наружу сейчас.

## D08 · Приватность · не обещать того, чего нет

Workspace — граница общих данных. Названия «Личное», «Мои», «Черновик» имеют конкретную семантику. «Мои задачи» — фильтр, не ACL. Персональные habits в v1 живут в личном workspace; private entities внутри общего workspace потребуют отдельной модели и не вводятся исподволь.

## D09 · Team roles · целевая матрица

Owner управляет доступом и backup; lead координирует работу и members; member работает в доступных доменах. S01/S02 обязаны закрыть aggregate bypass до дальнейшего UI. Полная матрица в 08; она является предложенным целевым контрактом, требующим реализации и тестов.

## D10 · Новые функции · порядок

Сначала сохранность/доступ/основные сценарии, затем комментарии/аудит, экспорт/импорт/шаблоны; AI/automation/runtime позже. Это не запрет будущего развития, а scope v1.

## Открытые решения, не блокирующие аудит

| Вопрос | Рабочее допущение | Когда уточнить |
|---|---|---|
| Размер команды | Небольшая команда, без enterprise ACL | Перед масштабированием/SaaS |
| Серверный хостинг | Self-hosted/локальный API, не публичное развёртывание сейчас | Перед сетевым release |
| Несколько валют | Отчёты отдельно, без неявного FX | Перед конвертацией |
| Дробной склад | Текущие integer quantities сохраняются | Перед поддержкой весового учёта |
| Offline | Черновики и recoverable errors, без двустороннего sync | Перед offline-first |
| Финансовый смысл времени | Оценка по ставке, не payroll/invoice | Перед коммерческой тарификацией |
| Светлая тема | Отдельный полный этап | После v1 |

## Приоритет документов

Явные новые инструкции владельца → проверенные факты текущего кода → принятые решения/инварианты проекта → данный план как целевой проект → старые roadmap-пункты. Если реализация уже выполнила acceptance, не откатывать её до текста плана. Если новое решение меняет осознанный invariant CLAUDE, обновить CLAUDE и PLAN вместе с соответствующей задачей.

## 2026-09-22 (первая правка дня) · Офисное редактирование согласовано владельцем — ONLYOFFICE Docs

Пользователь уточнил упор на Google Таблицы, Excel и Word и согласился с Office-first направлением. DOCX/XLSX — канонические файлы; ONLYOFFICE Docs — основной кандидат интеграции через Docs API. Не начинать native-first Tiptap/Univer по прежнему предложению. Google Таблицы — ориентир сценария, не выбранный внешний сервис. Согласованы подготовка интеграции и документации; коммерческая покупка и внешняя передача реальных файлов не подразумеваются.

**Это решение отменено следующей записью того же дня (см. ниже) — не действует.**

## 2026-09-22 (финальный пересмотр, поздняя правка) · ONLYOFFICE отменён, native-путь снова в силе

Владелец продукта в прямом разговоре с другим агентом-собеседником явно пересмотрел решение выше про ONLYOFFICE Docs / Document Server. Финальное решение:

- **Никакой внешней зависимости/Docker.** ORION — self-hosted инструмент соло-разработчика; обязательный сопутствующий Document Server (обычно разворачиваемый через Docker) противоречит этому позиционированию и разделу CLAUDE.md «Осознанные упрощения v0» о том, что вспомогательные процессы не тянут за собой внешние службы.
- **Совместная работа в реальном времени не нужна.** Владелец явно подтвердил модель «один открыл → отредактировал → сохранил → следующий открыл» — обычная модель файла с версиями (уже есть как `DocumentVersion`), не co-editing/co-presence/live cursors. Именно совместная сессия была главным техническим доводом за Document Server; без неё он избыточен.
- **Native-путь**: текстовый редактор — Tiptap (расширение уже принятого в проекте подхода «зрелая библиотека поверх собственного UI», как CodeMirror 6 для тела заметки, но это отдельный редактор отдельной сущности — office-документа, не заметки); табличный редактор — библиотека с собственным формульным движком (класс HyperFormula/Univer, не заглушка); сериализация в файл — `docx`/`exceljs` (или актуальные эквиваленты, зафиксировать выбор в O01). Канонический формат хранения остаётся DOCX/XLSX — это решение отдельное от выбора движка редактирования и не пересматривается.
- **Не гарантируется байт-в-байт совместимость** (сложные формулы, сводные таблицы, VBA) — целевой уровень «открывается и выглядит разумно», это осознанный компромисс, не техдолг.
- Возможное **будущее** расширение (не задача этого этапа) — LibreOffice headless как локальный опциональный CLI-конвертер по требованию (`soffice --headless --convert-to`, без постоянного сетевого порта) для файлов, которые native-парсер не потянул.

Продуктовое решение — [20-DOCUMENT-EDITORS](20-DOCUMENT-EDITORS.md) (раздел «финальный пересмотр»), исполнимый контракт — [21-OFFICE-IMPLEMENTATION](21-OFFICE-IMPLEMENTATION.md); эти документы и эта запись приоритетнее записи выше про ONLYOFFICE и прежних предложений по редакторам. Будущим агентам: в git-истории 20/21 существуют две версии решения одного дня — доверять только более позднему тексту (native, без ONLYOFFICE) и этой записи 14-DECISIONS, а не более ранним коммитам/секциям, оставленным как историческая справка внутри самих документов.

## 2026-09-22 · Связанные универсальные инструменты

По новому разговору владельца: Дом/Работа — личные сферы; workspace владеет данными и доступом; модули универсальны, их данные независимы; объект связывается с заметками/действиями/материалами без копий. Панели имеют собственный workspace context, несколько окон работают независимо. Позже допускается явный полный/частичный межпространственный доступ, который не выводится из одной ссылки. Уточнение отменяет абсолютный запрет любого cross-space сценария, но его безопасная реализация выделена в U09. Контакты могут расширяться CRM; учёт вещей становится полезен через обслуживание/контекст. Спецификация — 23, реализация — 24.

Native office решение, уже записанное в 20/21, сохраняется. 25 уточняет требования сохранности: минимальная совместимость не разрешает молчаливую потерю содержимого. Не возвращать старое ONLYOFFICE-поручение из исторических записей.
