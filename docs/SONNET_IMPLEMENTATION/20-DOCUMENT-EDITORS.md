## Актуальное решение после уточнения пользователя (финальный пересмотр, 2026-09-22, поздняя правка)

**Этот раздел отменяет решение про ONLYOFFICE Docs / Document Server, зафиксированное выше по тексту документа и в более ранней записи того же дня.** Владелец продукта в прямом разговоре явно пересмотрел выбор: он не хочет зависимости ORION от внешнего сервиса и Docker вообще. Причины пересмотра:

1. **Внешний Document Server — неприемлемая зависимость.** ORION — «ядро для соло-разработчика», локальный self-hosted продукт (см. корневой `CLAUDE.md`); обязательный сопутствующий сервис (обычно разворачиваемый через Docker) противоречит этому позиционированию и разделу «Осознанные упрощения v0» о том, что Tauri и десктоп-путь не тянут за собой внешние службы.
2. **Совместная работа не нужна**, а именно она была главным техническим доводом в пользу Document Server (общая редакторская сессия, `document.key`, callback-протокол). Владелец явно подтвердил: «один открыл — отредактировал — сохранил — следующий открыл» — обычная модель файла с версиями, которая в ORION уже есть (`DocumentVersion`). Без требования real-time совместной работы Document Server избыточен: всё, что он даёт сверх этого, ORION не использует.

Решение силы: **native-путь**, реализованный библиотеками внутри процесса web/desktop-клиента, без отдельного сервера редактирования, сессий редактирования, callback-эндпоинтов и Docker.

- **Текстовый редактор — Tiptap.** Расширяет уже принятый в проекте подход «использовать зрелую библиотеку поверх собственного UI», как `MarkdownEditor` (CodeMirror 6) для тела заметки — но это отдельный редактор для отдельной сущности (office-документ, не заметка): CodeMirror остаётся source-markdown редактором заметок и не трогается, Tiptap используется только для DOCX-документов Модуля Documents. Tiptap уже упоминался как исходно рекомендованный вариант до появления ONLYOFFICE-решения в этом же документе.
- **Табличный редактор — библиотека с собственным движком формул** (класс HyperFormula/Univer), не read-only просмотрщик и не заглушка. Univer уже рассматривался в проекте до ONLYOFFICE-решения и остаётся кандидатом по умолчанию (React-компонент, собственный формульный движок на HyperFormula, есть готовые DOCX/XLSX-плагины); альтернатива — взять `react-spreadsheet`/своя таблица поверх голого `hyperformula` для формул, если Univer на спайке (O01) окажется слишком тяжёлым по bundle size или плохо совместимым с уже используемым стеком (React 18 + Next.js app router). Выбор зафиксировать по результатам O01 с явным обоснованием, а не постфактум.
- **Сериализация в файловый формат — `docx` (npm) для документов и `exceljs` для таблиц** (или их актуальные на момент реализации эквиваленты, если у выбранных пакетов к тому времени появятся объективно более подходящие преемники — зафиксировать в O01, а не менять по ходу без причины). Канонический сохраняемый результат — по-прежнему валидный DOCX/XLSX, а не JSON-модель редактора: JSON — только промежуточное представление в памяти клиента между открытием и сохранением.
- Никакого Document Server, никаких редакторских сессий между сервером ORION и внешним движком, никаких callback-эндпоинтов, никакого `document.key`. Документ — обычный `Document` + `DocumentVersion`, как любой другой файл в Модуле Documents; поверх него на клиенте открывается native-редактор вместо read-only `FilePreview`.

### Явно осознанный компромисс

Полная байт-в-байт совместимость с Word/Excel (сложные формулы с зависимостями между листами разных типов, сводные таблицы, макросы VBA, Power Query, произвольные шаблоны из корпоративного мира) **не гарантируется и не является целью**. Целевой уровень — «открывается и выглядит разумно» для текста, базовых таблиц, распространённых формул и базовой стилизации (шрифты, отступы, простые стили ячеек), а не «идентично исходному файлу для любого документа». Это сознательно принятое ограничение, а не забытый технический долг; при столкновении со сложным файлом, который собственный парсер не осилил, поведение по умолчанию — сохранить оригинал нетронутым и явно сообщить пользователю о неподдержанном содержимом, а не тихо испортить файл.

### Возможное будущее расширение (не задача этого этапа)

В будущем, отдельным этапом и по отдельному запросу, возможно добавление **LibreOffice headless как локального опционального процесса-конвертера** — не сетевого сервиса с постоянным портом, а CLI-вызова по требованию (`soffice --headless --convert-to ...`) для файлов, которые собственный native-парсер не потянул. Это не меняет архитектуру («никакого обязательного внешнего сервиса»), потому что такой процесс запускается локально по требованию и не является постоянно работающей зависимостью, аналогично тому как `scripts/copy-pdf-worker.mjs` копирует воркер pdf.js без сетевого сервиса. Явно не реализовывать сейчас — упомянуто только чтобы будущий агент не заново открывал этот вопрос.

### Ожидаемый пользовательский результат

- Документ: страницы визуально не постранично (Tiptap — непрерывный поток, как большинство веб-редакторов текста), поля/отступы, стили абзацев и символов, заголовки, изображения, таблицы, списки; печать через браузерную печать/экспорт в PDF. Колонтитулы, отслеживание исправлений и комментарии — по возможностям выбранных Tiptap-расширений на момент O01, не гарантированы «из коробки» и фиксируются по факту в O01.
- Электронная таблица: несколько листов, формулы и ссылки между листами через собственный формульный движок, форматы чисел/дат, автозаполнение, фильтры/сортировка, закрепление строк. Диаграммы и сводные таблицы — по факту поддержки выбранной библиотеки, зафиксировать в O01; не обещать, если библиотека их не даёт без существенной доработки.
- «Создать документ» создаёт корректный DOCX через `docx`; «Создать таблицу» — корректный XLSX через `exceljs`, из проверенных пустых шаблонов, а не пустой файл с подходящим расширением. Загрузка своего файла → открытие во вкладке ORION (native-редактор парсит DOCX/XLSX в редактируемую модель) → редактирование → сохранение (сериализация обратно в DOCX/XLSX, новая `DocumentVersion`) → скачивание и проверка в Word/Excel.
- Полноразмерная вкладка редактора с собственной панелью инструментов ORION (Tiptap/табличная библиотека предоставляют только состояние документа и примитивы редактирования, не готовый брендированный UI, поэтому панель инструментов — свой компонент в `@orion/ui`, в духе уже существующих `MarkdownEditor`/`FilePreview`). ORION сохраняет собственную навигацию и контекст проекта.
- Редактор загружается лениво (`React.lazy`, отдельный чанк — как уже сделано для `FilePreview`), не попадает в login bundle.

### Актуальная последовательность реализации

1. Исправить дефекты 18-REVIEW-FINAL-PASS, особенно согласованность файлов/БД — независимо от выбора office-стека.
2. Изолированный спайк (O01): выбрать и обосновать конкретные версии Tiptap-расширений, spreadsheet-библиотеки и `docx`/`exceljs`; вне основного приложения создать пустой DOCX и XLSX программно, открыть их в редакторе, отредактировать, сохранить обратно в валидный DOCX/XLSX, открыть результат в реальном Word/Excel.
3. Реализовать серверную часть как обычный upload/download DOCX/XLSX поверх уже существующего контракта `DocumentsService`/`DocumentVersion` — без новых сущностей сессии редактирования. Конфликт одновременного сохранения — по уже принятому в проекте паттерну ревизии/CAS (сверить с `Note.revision`), не новый механизм.
4. Клиентская часть: открытие парсит текущий `DocumentVersion` в модель редактора (JSON Tiptap / состояние spreadsheet-библиотеки), редактирование живёт в клиентском state, сохранение сериализует модель обратно в DOCX/XLSX байты и делает обычный upload новой версии — та же операция, что «загрузить новый файл», без специального API.
5. Прогнать round-trip на подготовленных фикстурах: открыть → изменить → сохранить → открыть в исходном офисном приложении. Проверять текст/стили/таблицы/изображения для DOCX; несколько листов, межлистовые формулы, форматы чисел/дат — для XLSX. Явно фиксировать неподдержанное (VBA, Power Query, сводные таблицы, сложные шаблоны), не обещать полную совместимость.

## Историческое решение от 2026-09-22 (ОТМЕНЕНО последующей правкой выше)

Ниже сохранён текст решения про ONLYOFFICE Docs, действовавшего в течение части дня 2026-09-22, для истории и чтобы будущий агент видел, что именно было отменено и почему. **Не реализовывать ничего из этого раздела.**

Пользователь явно выбрал упор на привычные возможности Google Таблиц, Excel и Word. Приоритет Office-first: DOCX/XLSX и полноценный встроенный офисный редактор. Основной кандидат для прототипа — ONLYOFFICE Docs через Docs API: ORION предоставляет файлы, проекты, права, поиск и версии; офисный сервер предоставляет текстовый и табличный редакторы, расширенные безопасными сессиями редактирования, подписанными callback и идемпотентной историей версий. Отменено по причине, изложенной в разделе выше: владелец не хочет внешних сервисов/Docker, а совместная работа, ради которой был нужен Document Server, не требуется.
