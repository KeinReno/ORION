## R18-01 · P1 · Restore уничтожает текущие байты до успешного применения БД

Места: `apps/api/src/sync/sync.service.ts:295–299`, `apps/api/src/sync/blob-backup.service.ts:180–187`.

`blobs.restore()` заменяет дерево файлов, удаляет прежнее дерево и журнал. Только после этого `snapshots.apply()` применяет строки внутри транзакции БД. При ошибке этой транзакции файлы уже заменены; возврата к предыдущему состоянию нет. Проверка checksum и staging защищает от сбоя записи staging, но не от сбоя следующего этапа.

Воспроизведение: сохранить файл `BACKUP`, сделать бэкап, заменить содержимое на `LATEST`, инжектировать исключение в `SnapshotService.apply`, выполнить restore. API возвращает 500, а чтение файла возвращает `BACKUP` вместо `LATEST`. Строки БД не восстановлены. Контент имеет одинаковую длину, поэтому результат не обусловлен Content-Length.

Задание: ввести общую операцию восстановления с durable operation ID и состояниями файлов/БД; сохранять старое дерево до подтверждённого commit; обеспечить компенсацию при отказе БД и однозначное восстановление после падения процесса, в том числе между commit и обновлением файлового журнала. Блокировать конфликтующие restore/записи в workspace. Простая перестановка двух операций проблему не решит. До завершения восстановления не отдавать смесь старых строк и новых файлов.

Приёмка: fault injection до/после каждого rename, до/после commit, при очистке; перезапуск и повторный recover; параллельные restore и запись документа. После отказа доступно целостное прежнее состояние либо явно заблокированное восстанавливаемое состояние с сохранёнными данными; после успеха — целостный снимок.

## R18-02 · P1 · Восстановление версии заметки обходит CAS

Место: `apps/api/src/notes/notes.service.ts:439–442` (`restoreRevision`). Повтор прежнего R02.

Обычный update увеличивает `revision`, restoreRevision меняет текст без увеличения. Редактор, открытый до восстановления, остаётся формально актуальным и успешно перезаписывает восстановленный текст.

Воспроизведение: создать OLD; update → NEW, сохранить текущий revision; восстановить OLD из истории; update → STALE с сохранённым revision. Ожидался конфликт, фактически успешно сохранён STALE. Тест подтверждает обход даже когда клиент передаёт expectedRevision.

Задание: увеличивать revision атомарно при восстановлении; определить и реализовать проверку ожидаемой текущей версии для самой операции restore; проверить остальные пути изменения заметки. Отдельно закрыть обход защиты через отсутствие optional expectedRevision на пользовательских изменениях контента; мигрировать все соответствующие клиенты согласованно.

Приёмка: устаревшее сохранение после restore возвращает 409, восстановленный текст остаётся; два конкурентных restore/edit не затирают данные незаметно; история сохраняет вытесненную версию.

## R18-03 · P1 · Уведомления раскрывают данные закрытого модуля

Места: `apps/api/src/notifications/notification-center.service.ts:62–77`, `createTx` и `markRead`. Повтор прежнего R03.

Фильтрация по recipientId исправляет чужой inbox, но не проверяет доступ адресата к исходному модулю/сущности. После ограничения tasks обычный member продолжает получать заголовок ранее созданного уведомления через list.

Воспроизведение: создать member в workspace владельца; создать адресованное member уведомление о задаче; установить restrictedModules=["tasks"]; вызвать NotificationCenterService.list от member. Заголовок SECRET TASK TITLE присутствует. Использована настоящая PostgreSQL и app-role/RLS. Тест касается чтения сохранённой строки, не доказывает конкретный путь её создания cron-производителем.

Задание: применить централизованную actor-aware политику исходного модуля/сущности при чтении и создании уведомлений, включая счётчики, markRead и внешние каналы. Для неизвестных/удалённых источников задать явное безопасное поведение; системные уведомления обрабатывать отдельным контрактом. Не скрывать только кнопку перехода: утечка уже в title/body.

Приёмка: member после отзыва доступа не видит ни title/body, ни счётчик закрытых уведомлений; owner сохраняет разрешённый доступ; disabled modules и изменение роли также учитываются; новые уведомления не отправляются адресату без доступа.
