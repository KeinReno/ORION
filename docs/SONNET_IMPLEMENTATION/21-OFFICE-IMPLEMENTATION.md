## Принятое решение и границы

Владелец подтвердил упор на работу уровня Word/Excel/Google Таблиц, но явно отказался от внешнего Document Server и Docker-зависимости: **native-путь внутри клиента ORION**, без отдельного сервиса редактирования. Текстовый редактор — Tiptap; табличный — библиотека с собственным формульным движком (по умолчанию Univer, иначе — HyperFormula поверх более лёгкого табличного UI, с обоснованием выбора в O01); сериализация в файл — `docx`/`exceljs`. Google Таблицы/Excel/Word — ориентир удобства работы, а не требование подключать внешний аккаунт или сервис. Совместная работа в реальном времени **не требуется** — владелец явно подтвердил модель «один открыл → отредактировал → сохранил → следующий открыл», не совместное редактирование одновременно.

Первая поставка: DOCX и XLSX — создание/загрузка/редактирование/скачивание, просмотр без права записи (там, где редактор недоступен или файл слишком сложен для парсера), история версий и восстановление через уже существующий механизм `DocumentVersion`. Презентации, редактирование PDF, VBA, Apps Script, Power Query, AI и внешний гостевой доступ в этот объём не входят. Существующие PDF preview, аннотации и остальные типы файлов сохранить без изменений.

Полная байт-в-байт совместимость с Word/Excel не гарантируется и не является целью (зафиксировано в 20-DOCUMENT-EDITORS) — целевой уровень «открывается и выглядит разумно» для типичного документа/таблицы, не «идентично для любого файла».

## Рабочая поверхность

В Документах: «Создать документ», «Создать таблицу», «Создать папку», «Загрузить». Первые два действия создают валидные DOCX/XLSX из проверенных пустых шаблонов средствами `docx`/`exceljs`, а не пустые файлы с подходящим расширением.

Открытие поддерживаемого файла — большая вкладка native-редактора (Tiptap для DOCX, spreadsheet-библиотека для XLSX), собственная панель инструментов ORION в стиле `@orion/ui` (готового брендированного UI библиотеки нет, панель — свой компонент, как у `MarkdownEditor`). ORION показывает имя, проект, состояние сохранения, историю и возврат в папку. Редактор загружается лениво (`React.lazy`), не попадает в login bundle. Имена и идентификаторы стабильны при переименовании файла. Проверить фокус, клавиатуру, zoom и узкий экран; для файла, который парсер не осилил, явно предложить просмотр/скачивание оригинала вместо попытки открыть в редакторе.

Не объединять два разных состояния: «изменения есть в клиентском state редактора» и «версия сохранена в ORION». Второе показывать только после подтверждённого ответа upload API (новая `DocumentVersion` создана). При сбое сохранения пользователь видит ошибку и повтор, а прежде сохранённая версия остаётся доступна и не подменяется частично записанными байтами.

## Контракты: как модель редактора ложится на существующий DocumentVersion/upload

Никакого отдельного протокола редактирования не вводится — офисный документ остаётся обычным `Document` + `DocumentVersion`, как любой другой файл в Модуле Documents, с native-редактором поверх вместо read-only `FilePreview`. Контракты ниже описывают только это сопряжение, не новый API-слой:

- **Открытие**: клиент запрашивает текущее бинарное содержимое файла через уже существующий эндпоинт скачивания/стрима `DocumentsService` (как `GET …/documents/:docId/content`, применяемый для остальных типов файлов), парсит DOCX/XLSX-байты в редактируемую in-memory модель (JSON-документ Tiptap / состояние spreadsheet-библиотеки) на клиенте. Парсинг — чистая клиентская операция, серверу не нужно ничего знать о формате модели редактора.
- **Редактирование**: живёт целиком в клиентском React-state (как черновик заметки перед сохранением); сервер о промежуточных изменениях не уведомляется, автосохранение — по тому же паттерну, что уже есть в проекте для черновиков (см. AutosaveStatus), без новых серверных сущностей.
- **Сохранение**: клиент сериализует модель редактора обратно в валидные DOCX/XLSX байты (`docx`/`exceljs`) и делает обычный upload новой версии через уже существующий контракт `DocumentsService.upload` (`multipart/form-data`, `FilesInterceptor`, тот же путь, что «загрузить новый файл поверх существующего»). Никакого `document.key`, editor-session или callback-эндпоинта не требуется — вся операция синхронна в рамках одного HTTP-запроса от клиента, инициированного явным действием пользователя «Сохранить».
- **Конфликт одновременного сохранения**: два последовательных сохранения от разных клиентов — обычный случай оптимистичной конкуренции upload новой версии. Сверить с уже принятым в проекте паттерном ревизии/CAS (`Note.revision` — если у заметок конфликт решается сравнением ревизии перед принятием правки, применить тот же паттерн к `Document`/`DocumentVersion": передавать base-версию при сохранении, отклонять upload с понятной ошибкой, если текущая версия документа на сервере уже новее той, что клиент открывал, и explicitly обосновать, если для Document решено оставить last-write-wins вместо CAS — с указанием почему это приемлемо для office-файлов, но не для заметок).
- **История**: используется существующий `DocumentVersion` без новой модели содержимого; native-редактор не хранит собственную историю, только текущее открытое состояние.

## Открытие/редактирование/сохранение — упрощённая модель вместо editor-session states

Вместо состояний editor-сессии (opening/editing/save-pending/disconnected/conflict/…), актуальных для внешнего Document Server с сетевым callback, модель здесь — обычный клиентский жизненный цикл, симметричный остальным формам ORION:

1. **open** — вкладка редактора запрашивает текущий `DocumentVersion`, парсит DOCX/XLSX в модель. Ошибка парсинга (файл слишком сложен/повреждён) — не крах вкладки, а деградация до просмотра/скачивания оригинала с понятным сообщением.
2. **edit** — чисто клиентское состояние, не покидает браузер/WebView до явного сохранения. Несохранённые изменения теряются при закрытии вкладки без сохранения — как в любом другом редакторе ORION без черновиков; если решено добавлять автосохранение черновика, использовать существующий паттерн черновиков, а не новую сущность.
3. **save** — сериализация в DOCX/XLSX, upload новой `DocumentVersion` с проверкой конфликта ревизии (см. выше). Успех — подтверждённое «сохранено» в UI; отказ (сеть, конфликт ревизии, отказ storage) — явная ошибка с возможностью повторить, прежняя сохранённая версия остаётся нетронутой и доступной для скачивания.

Восстановление версии (`restore`) — уже существующий механизм `DocumentVersion`, применяемый ко всем типам файлов; для office-документов он не требует дополнительной логики, restore просто делает старую версию текущей, следующее открытие редактора парсит её как обычно.

| OF04 | Повторное сохранение и устаревший результат | Повторный upload той же версии (сеть повторила запрос) не размножает версии; сохранение поверх уже изменённого документа (устаревшая base-ревизия) явно отклоняется как конфликт, а не тихо затирает новую версию |
| OF05 | Сбой сохранения | Отказ storage, обрыв загрузки, перезапуск процесса: прежняя версия цела, пользователь видит ошибку сохранения, нет ложного «сохранено» |
| OF06 | Два последовательных сохранения | Пользователь A сохраняет, закрывает вкладку; пользователь B открывает файл (видит версию A), редактирует и сохраняет; версия B видна следующему открывшему. Одновременное редактирование не тестируется — оно не входит в целевой сценарий |
| OF07 | История и backup | Restore повышает revision документа тем же механизмом, что у остальных файлов; бэкап гарантированно включает подтверждённую сохранённую версию |
| OF08 | Web/desktop | Production web, static export и реальный Tauri WebView; клавиатура, clipboard, поведение при парсинге сложного/повреждённого файла |
| OF09 | Форматы и размеры | На фиксированных малом/среднем/большом образцах измерены время открытия/сохранения и память в браузере/WebView; пределы установлены по измерению; неподдерживаемый парсером файл сохраняет оригинал и предлагает просмотр/скачивание |
| OF10 | Эксплуатация | Новый агент запускает ORION без каких-либо дополнительных сервисов и получает работающий офисный редактор «из коробки»; секреты не нужны (нет внешнего API); обновление и rollback не теряют сохранённые файлы |

Отсутствие Word/Excel или Tauri для соответствующей проверки отметить NOT RUN; не объявлять совместимость подтверждённой другим редактором.
