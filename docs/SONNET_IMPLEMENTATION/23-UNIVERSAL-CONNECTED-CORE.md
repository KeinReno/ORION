# Универсальное связанное ядро ORION

2026-09-22. Согласованное направление из разговора владельца: личная жизнь, семья и небольшая команда равноправны; одинаковые инструменты работают в разных пространствах, а сущности связаны. Это целевая спецификация, не утверждение о готовности кода. Исполнение — 24-CONNECTED-CORE-BACKLOG.md.

## Иерархия и владение

**Сфера** («Дом», «Работа», «Учёба») — личная группировка пространств пользователя. Название, порядок и состав не задают права другим людям. Один семейный workspace может находиться в разных сферах у разных участников. Первый запуск допускает одно пространство без обязательного создания сферы. В первой версии одно пространство входит не более чем в одну сферу данного пользователя; для быстрого доступа есть независимое избранное.

**Пространство** — владелец данных, членства, настроек модулей и политики доступа. **Проект** — результат/дело внутри пространства. **Модуль** — предметные правила и инструменты. **Представление** — фильтр и компоновка существующих данных. **Окно** — независимый контекст навигации. Не вводить рекурсивные пространства внутри пространств.

Каждая сущность сохраняет конкретное пространство-владелец. Финансы семьи и студии используют один модуль, но разные записи и настройки. Личный layout и фильтры не изменяют интерфейс других участников. Общие категории, назначения и правила меняются явно в scope пространства.

Сферы не должны сломать существующий backup workspace: пользовательские группировки относятся к personal preferences/account export, а не копируются чужим участникам при восстановлении workspace. Для любой новой таблицы определить владельца, RLS и включение в соответствующий export/restore.

## Карта текущих модулей

| Модуль | Источник истины | Контекстные связи |
|---|---|---|
| Задачи | Действие, статус, исполнитель, сроки, зависимости | Проект, материалы, событие; позже контакт/вещь. Из карточки объекта создаётся обычная задача, видимая также в Задачах |
| Проекты | Результат, этапы, сроки | Собирают задачи, события, документы, заметки, расходы, время; не копируют их в отдельные хранилища |
| Календарь | События, время, повторы | Повестка/заметка, проект, материалы, связанные задачи. Показ дедлайна не создаёт дубликат события |
| Заметки | Текст, история, вложения | Один текст доступен из нескольких разрешённых контекстов; ссылки в тексте и явные смысловые связи могут сосуществовать |
| Документы | Файлы и версии | Чек подтверждает расход; инструкция относится к вещи; договор относится к проекту/контакту |
| Финансы | Счета, операции, бюджеты, финансовые цели | Проект, покупка, документы, контакт. Счёт задаёт фактическое списание, контекст не создаёт вторую проводку |
| Время | Интервалы работы и исполнитель | Задача/проект. Стоимость времени не становится автоматически расходом или поступлением |
| Привычки | Расписание поведения, отметки дней | Инструкция, цель, напоминание. Не размножать ежедневные задачи автоматически |
| Списки | Лёгкие пункты/отметки | Поездка, закупка, оборудование. Явное превращение пункта в задачу сохраняет происхождение и не дублируется при retry |
| Склад | Позиции, остатки, движения | Покупка, проект, документы. Связь с финансами добавляет отдельное подтверждаемое действие |

Входящие, поиск, уведомления, напоминания, связи и рабочая оболочка — общие инструменты. Не создавать десять независимых движков напоминаний или редакторов заметок внутри модулей.

Будущие сущности: Контакты с историей и следующими действиями; Коллекции для ссылок/товаров/мест; Покупки для заказа/получения/возврата; Имущество для конкретных вещей с гарантией/обслуживанием. CRM — расширение Контактов: по воронке движется **сделка**, один контакт может участвовать в нескольких сделках. Не реализовывать будущие модули до готовности базового вертикального сценария.

## Общий контракт сущности и связи

Сохранить Prisma-модели модулей. Не переносить бизнес-данные в универсальную EAV/JSON-таблицу и не вводить graph database. Реестр типов предоставляет adapter: resolve/exists, безопасный summary, open-target, canRead/canLink и поддерживаемые действия. Сервер использует закрытый перечень типов; клиентские строки не выбирают произвольную таблицу.

Ссылка содержит тип, id и workspaceId; сервер проверяет соответствие фактическому владельцу. Summary не должен содержать закрытые title/preview/amount. Навигация всегда несёт workspaceId объекта, а не берёт глобальное активное пространство при отложенном открытии.

Перед миграцией прочитать EntityLink, NoteLink и существующие projectId/taskId связи. Предметные FK остаются источником истины: не дублировать projectId второй независимо редактируемой generic-связью. Общая панель связей может собирать FK и EntityLink единым read adapter.

Первая версия смыслов: `related_to`, `supports` (материал для задачи), `evidence_for` (документ подтверждает расход). Точные stable ids утвердить в U01 и не использовать локализованную label как тип отношения. Каталог описывает допустимые пары, направление, обратную подпись и разрешённые действия. Для симметричного related_to нормализовать порядок концов: A→B и B→A не две разные связи. Запретить self-link, дубликаты и недопустимые пары.

Создание связи требует чтения обоих объектов и разрешения управлять связями исходного объекта. Это не даёт права редактировать содержимое цели. Чтение обратных связей фильтруется по текущим правам обоих концов; скрытые записи не увеличивают счётчик и не раскрываются в экспорте/уведомлениях.

Удаление связи не удаляет объекты. Удаление объекта не каскадит в произвольные связанные сущности; для ссылки задаётся tombstone/очистка. Недоступный/удалённый объект не раскрывает бывшее название неавторизованному пользователю. Отключение модуля не удаляет данные, но закрывает его содержимое через агрегаторы по текущей политике ORION.

## Интерфейс связанного контекста

Общий entity picker с поиском, типом, пространством и подтверждённым доступом; контекстный scope предложен по месту открытия. Не показывать все поля/модули на каждом экране. Карточка объекта сначала показывает собственные данные и ближайшее действие, связанные группы — по наличию и запросу пользователя.

Действия: «Связать существующее», «Создать задачу», «Написать заметку», «Прикрепить документ», «Напомнить». Новая запись создаётся в явно указанном пространстве; команда create-and-link атомарна для БД или имеет durable recovery для файлов. Retry не создаёт второй объект.

Напоминание возвращает к объекту и не требует искусственной задачи. Задача означает выполняемую работу. Предлагаемый reminder contract: owner/recipient, target ref, scheduledAt, timezone, status, delivery occurrence key. Проверять права при создании, срабатывании и открытии; повтор обработки не дублирует уведомление. Начать с одноразовых личных напоминаний, существующие recurring/event reminders не переписывать без миграционного плана.

Любая форма сохраняет ввод при ошибке; сценарии loading/empty/error/conflict/denied/deleted/offline-or-disconnected заданы. Связи и размещение панелей доступны без мышиного drag.

## Независимые окна и раскладки

Контекст окна: userId, windowId, workspaceId; каждая панель дополнительно хранит module/type, entityId или view/filter. Layout ключуется пользователем, пространством и назначением раскладки; активное пространство конкретного окна не хранится единственным глобальным localStorage key.

Переключатель показывает сферу и название пространства. Список включает поиск, закрепление, «Открыть в новом окне». Стрелки переключают закреплённые пространства в явном порядке, не имитируют browser back. Два окна могут показывать разные пространства; повторное открытие восстанавливает свой контекст. Закрытое/запрещённое пространство даёт выбор другого без утечки прошлых данных.

Drag раздела из sidebar создаёт/размещает представление в Dockview: центр — вкладка, край — split. Вынос в отдельное окно имеет явную альтернативную команду. Данные при этом не переносятся. Первая версия не обязана поддерживать перенос drag между независимыми окнами ОС; команда открытия на втором мониторе обязательна. Фильтр проекта принимается только модулем, который его поддерживает, и виден пользователю.

## Межпространственные данные: отдельный этап

Сначала связи работают **внутри** пространства. Безопасная ошибка объясняет неподдержанный межпространственный выбор. Затем личный обзор собирает данные пространств, где пользователь уже имеет доступ. Он не выдаёт новых прав и не переносит записи.

После этого — явные grants на целый объект/разрешённое представление. Владелец данных сохраняется. Объединение пространств, shared ownership и перенос счетов для этой задачи не нужны. Не ослаблять membership RLS всей таблицы: выделить узкий grant-aware policy/endpoint и тестировать каждый путь доступа. Отзыв действует для новых reads, поиска, cache refresh, экспорта и уведомлений; уже скачанные копии отозвать нельзя.

Частичный доступ — серверная проекция с allowlist полей/строк/агрегатов, а не клиентский фильтр. Начать с read-only. Публикация всего бюджета не подразумевает публикацию всех его операций. Политику обновления live projection vs snapshot и допустимые измерения задать явно, иначе разные агрегаты могут раскрыть скрытые суммы.

Финансовая форма различает счёт (источник денег), категорию (назначение), бюджет (план/лимит), проект/контекст и доступ. «Наличные на работу» могут быть счётом, а «лимит на обеды» — бюджетом; интерфейс не создаёт новые деньги. В агрегате dedup по стабильной идентичности исходной операции/счёта, итоги отдельно по валютам; переводы между включёнными счетами не считаются новым доходом. Общий picker счетов предлагает только те, где разрешено **создание операции**, а не только просмотр.

## Сквозной сценарий результата

Семья → проект Поездка → заметка с планом → задача Забронировать → событие дат → документ бронирования → расход с семейного счёта → напоминание о доплате. Каждая запись видна в своём модуле и контексте проекта без копий. Студия проходит ту же цепочку на рабочем примере. Закрытый личный расход не раскрывается семье через связь с общим материалом.

Основания продуктовых решений: `rule/smallest-intervention` (переиспользование модулей), `rule/name-object-scope-consequence` (scope и действия), `rule/cover-reachable-states`, `rule/preserve-user-input`, `rule/keyboard-complete-flow`. Порядок разработки — продуктовая гипотеза; coverage gap (proposed) `rule/connected-workflow-priority`, категория Product strategy: сначала завершать сквозной сценарий, затем расширять набор сущностей.
