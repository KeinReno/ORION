# Диаграммы и сводные таблицы в XLSX — исследование альтернатив (без Docker/внешнего сервиса)

2026-09-22. Продолжение O01 (`12-PROGRESS.md`) после того, как владелец продукта
подтвердил: диаграммы и сводные таблицы в модуле Documents/таблицы — важны, не
опциональны. O01 уже установил: Univer (базовый `@univerjs/preset-sheets-core`)
отклонён по размеру (~9.9 МБ unpacked) и без официального open-source XLSX I/O;
выбран fallback `exceljs` + `hyperformula`, но `exceljs` **не пишет** диаграммы и
сводные таблицы в XLSX вообще (только читает существующие, не создаёт). Эта
записка — целевое исследование: есть ли реальная (не «открывает файл», а
«создаёт/редактирует через UI и сохраняет валидный XLSX») поддержка диаграмм и
pivot table без внешнего сервиса/Docker.

Все данные проверены `npm view`/`npm search`/веб-поиском 2026-09-22, не по
памяти модели. Даты и цифры — на момент проверки, у некоторых коммерческих
продуктов может быть скрытый прайсинг (запрос к отделу продаж).

## Рекомендация

**Чистого бесплатного open-source решения, которое реально создаёт/редактирует
диаграммы и сводные таблицы в XLSX через UI и надёжно сохраняет валидный файл,
не существует** на уровне зрелости, сопоставимом с уже принятыми в проекте
библиотеками (Tiptap, `docx`, `exceljs`). Все жизнеспособные кандидаты — либо
коммерческие лицензии (Univer Pro, SheetJS Pro, jspreadsheet Pro), либо
экспериментальные/незрелые проекты (modern-xlsx, WASM-порты офисных движков),
либо решают только часть задачи (стратегия «сохранить нетронутым»).

Рекомендуемый путь — **комбинация двух уровней, без изменения решения о
«без Docker/внешнего сервиса»**:

1. **Базовый уровень (реализовать сейчас, входит в текущий O01-стек)** —
   стратегия «сохранить нетронутым» поверх уже выбранного `exceljs`: при
   открытии существующего XLSX с диаграммами/pivot table эти объекты **не
   парсятся в редактируемую модель**, а сохраняются как opaque OOXML-части
   ZIP-архива и просто копируются обратно при сохранении, если пользователь
   не трогал данные, на которые они ссылаются. Это не требует новой
   зависимости, закрывает главный риск «пользователь загрузил файл с
   диаграммой — ORION её стёр», и честно соответствует уже принятому в
   `20-DOCUMENT-EDITORS.md` принципу «не осилили — сохраняем оригинал, не
   портим тихо».
2. **Явный компромисс для владельца продукта**: создание **новых** диаграмм
   и сводных таблиц через UI ORION в этом релизе не поддерживается. Если это
   неприемлемо, единственный реалистичный путь — купить коммерческую лицензию
   **Univer Pro** (`@univerjs-pro/sheets-chart(-ui)` + `@univerjs-pro/sheets-pivot(-ui)`
   + `@univerjs-pro/exchange-client` для XLSX import/export), потому что это
   единственный кандидат, где (a) диаграммы/pivot официально заявлены и
   поставляются тем же вендором, что и сам движок таблиц (меньше риска
   несовместимости версий, в отличие от связки «open-source UI + сторонний
   XLSX-пакет»), (b) это не внешний сетевой сервис — библиотека встраивается
   в клиентский бандл как обычная npm-зависимость, (c) проект активно
   поддерживается (версии Pro-пакетов идут в ногу с open-source core, 0.25.x
   на момент проверки). Цена не публична — нужен прямой запрос к
   `univer.ai/pro`/`pro.univer.ai` до принятия решения, и это должно быть
   осознанным «да, разработчик готов платить за коммерческую библиотеку»
   решением владельца, а не тихой заменой ранее принятого «`exceljs`
   бесплатный».
3. **Не рекомендуется**: modern-xlsx (слишком незрелый — 5 звёзд, 542
   скачивания/месяц, заявленные фичи не подтверждены собственными тестами),
   любой WASM-порт офисного движка (LibreOffice WASM не production-ready как
   встраиваемая библиотека; x2t-WASM — закрытый как "not planned" эксперимент
   без официальной поддержки), Luckysheet (официально мёртв, авторы сами
   советуют мигрировать на Univer), Fortune-sheet как основа именно ради
   диаграмм/pivot (сама библиотека жива и React-first, но её путь к валидному
   XLSX с диаграммами идёт через маленькие неофициальные сторонние плагины
   уровня «один автор, непонятная зрелость» — не тот фундамент, на который
   стоит опираться ради ключевой фичи).

### modern-xlsx — PASS (с обязательной оговоркой про Node 24)

Точное имя пакета на npm подтверждено: `modern-xlsx@1.2.1` (это уже новее,
чем `542 скачивания/месяц` и «5 звёзд», зафиксированные в исходном
исследовании выше по файлу 2026-09-22 утром — за день до вечерней проверки
вышел релиз 1.2.1, `unpackedSize` 7.4 МБ). У пакета **задокументирован и
реально существует** fluent `ChartBuilder` API (`ws.addChart('bar', b => …)`)
и API pivot table/pivot cache (`wb.addPivotCache(...)`, `ws.addPivotTable(...)`)
— это не только строка в README-таблице, а рабочий, типизированный (`.d.ts`)
публичный API с описанием параметров в `README.md` (секции «Charts» и
«Pivot Tables»).

**Найденная проблема — `initWasm()` в Node.js 22 падает**: пакет требует
Node **24+** (`engines` в `package.json`, `npm install` явно предупреждает
`EBADENGINE`). На Node 22.14 (текущая версия окружения) `initWasm()` без
аргументов делает `fetch('file://…wasm')` под капотом (`wasm-bindgen`
дефолтная инициализация через `import.meta.url`) — в Node 22 `undici`
не реализует схему `file://` для `fetch()` (`TypeError: fetch failed`,
`cause: Error: not implemented... yet...`), что ломает инициализацию
«из коробки».

**Обход, тоже эмпирически проверенный и рабочий**: пакет экспортирует
`initWasmSync(bytesOrModule)`, принимающий уже прочитанные байты `.wasm`.
Вызов `initWasmSync(fs.readFileSync('node_modules/modern-xlsx/dist/modern-xlsx.wasm'))`
вместо `await initWasm()` полностью решает проблему на Node 22 — дальше
API работает штатно. Для ORION (Node 24 везде не гарантирован на десктопе
пользователя, `apps/api` — Node LTS) это значит: **обязательно использовать
`initWasmSync` с явным чтением файла**, не полагаться на дефолтный
`initWasm()`.

Минимальный скрипт (создание bar-чарта по трём точкам `Sales!$A$1:$A$3`/
`$B$1:$B$3` с заголовком, подписями осей и легендой, плюс pivot cache +
pivot table по диапазону `A5:B7`) выполнился успешно:

```
WROTE out-modern-xlsx.xlsx 5093 bytes
```

Файл распакован как обычный ZIP (`unzip`) — структура подтверждает **реальный
OOXML**, а не заглушку:

```
[Content_Types].xml          — Override-записи для chart1.xml, drawing1.xml,
                                pivotCacheDefinition1.xml, pivotTable1.xml
                                с правильными officedocument content-type'ами
xl/charts/chart1.xml         — валидный DrawingML chart XML (namespace
                                c:/a:/r:, <c:barChart>, <c:ser>, <c:cat>,
                                <c:val>, оси с <c:title>, легенда)
xl/drawings/drawing1.xml     — anchor диаграммы на листе
xl/drawings/_rels/drawing1.xml.rels
xl/pivotCache/pivotCacheDefinition1.xml
xl/pivotTables/pivotTable1.xml — <pivotTableDefinition name="SalesPivot"
                                  cacheId="0"><location ref="D5:F10"/>
                                  <pivotFields><pivotField axis="axisRow"
                                  name="Region".../></pivotFields>
xl/worksheets/sheet1.xml, sharedStrings.xml, styles.xml, workbook.xml — как обычно
```

Чтение файла через уже принятый в проекте `exceljs` прошло без ошибок
(`wb.xlsx.readFile('out-modern-xlsx.xlsx')` → `Sheets: ['Sales']`, значения
ячеек `A1`/`B1` читаются верно) — файл не битый на уровне ZIP/XML, который
`exceljs` умеет парсить (chart/pivot-части `exceljs` игнорирует при чтении,
как и ожидается — он их не парсит, но и не падает на их наличии).
LibreOffice/Excel для визуального открытия в этом окружении недоступны
(`soffice`/`libreoffice` не установлены на машине) — полный «открылось и
показало диаграмму глазами» тест не выполнен, но структурная валидность
OOXML (корректные `Content_Types`, `r:id`-связи через `.rels`, валидный
DrawingML namespace в `chart1.xml`) — сильный сигнал, что реальные Excel/
LibreOffice примут файл; риск смещается в сторону «граничные случаи API
(много серий, комбинированные диаграммы, сложные pivot-поля с
`dataFields`/`colFields`)», не «базовый кейс не работает».

**Вывод по modern-xlsx**: заявление README **подтверждено собственным
тестом**, не только маркетингом. Библиотека всё ещё молодая (проверить
нужно будет более сложные сценарии перед принятием в прод — множественные
серии, смешанные типы осей, реальные `dataFields`/`colFields` в pivot — этот
тест покрыл только базовый happy path), но открытый вопрос «работает ли
заявленный API вообще» закрыт положительно. Обязательное условие
интеграции — `initWasmSync` с ручной загрузкой `.wasm`-байтов (не дефолтный
`initWasm()`), задокументировать это в коде, а не полагаться на quick start
из README, который на Node < 24 не работает как написано.

### Fortune-sheet (`@fortune-sheet/react` + `@fortune-sheet/core`) — FAIL на экспорте в XLSX

Установлен `@fortune-sheet/react@1.0.4` (тянет `@fortune-sheet/core@1.0.4`).
Проверка официального экспорта **до** похода к сторонним плагинам, как
просил владелец: поиск строки `xlsx` (без учёта регистра) по всему
собранному `dist` (`index.js`/`index.esm.js`) обоих официальных пакетов —
**0 совпадений**. README обоих пакетов тоже не содержит ни слова «export»,
«xlsx», «chart» или «pivot» — это не readme-заглушка не по теме, это
подтверждение, что официальный npm-пакет **не предоставляет вообще никакой
публичной функции записи в XLSX**, даже частичной. Для сравнения — строка
`pivot` встречается 45 раз, `chart` — 72 раза в собранном коде: in-app
UI-фичи (просмотр/работа с pivot-таблицей и диаграммой на канвасе) реально
есть, что подтверждает часть исходного исследования про UI, но это
**никак не связано с сериализацией в файл `.xlsx`** — данных для гипотезы
«официальный путь работает хотя бы частично» не нашлось: частично работать
нечему, потому что XLSX-writer в этих двух пакетах отсутствует как класс
функциональности.

Сторонние неофициальные пакеты для этого действительно существуют на npm
(проверено `npm search`, не устанавливались и не тестировались отдельно —
именно то «маленький автор, непонятная зрелость», что было предположено в
исходном исследовании до эмпирической проверки): `@corbe30/fortune-excel`
(2.3.4, опубликован **вчера**, 2026-09-21), `@lofcz/fortune-excel` (1.0.1,
2026-07-23), `@zenmrp/fortune-sheet-excel` (1.0.3, 2024-02-17, самый старый
и потенциально самый заброшенный). Ни у одного нет клейма «официальный
плагин экосистемы Fortune-sheet» — это отдельные сторонние проекты под
personal npm scope. Углублённая проверка (установка + попытка
экспортировать реальную диаграмму/pivot и открыть результат) не
проводилась в этой сессии: она осмысленна только если Fortune-sheet вообще
рассматривается как замена основного табличного движка (`exceljs` +
`hyperformula`), а это уже отдельное архитектурное решение с более высокой
ценой пересмотра, чем разовая проверка библиотеки диаграмм.

**Вывод по Fortune-sheet**: как путь к диаграммам/pivot **в XLSX-файле**
подтверждён FAIL на официальном пакете эмпирически (не только по
документации) — 0 экспорт-функций в собранном коде. Как отдельный табличный
UI-движок (не ради экспорта) тема не оценивалась — вне рамок этой задачи.

### Итоговое обновление рекомендации после эмпирической проверки

Первоначальный вывод исследования («чистого зрелого open-source решения
для UI-редактирования нет, Univer Pro/коммерция — единственный полноценный
путь») остаётся в силе для **редактирования диаграмм/pivot через UI ORION**.
Но конкретно по **программной записи** диаграммы/pivot table в XLSX (не
обязательно через визуальный редактор — например, «пользователь ввёл
данные в таблицу, нажал кнопку "вставить диаграмму", ORION сериализует
DrawingML chart по выбранному типу/диапазону сам, без drag-n-drop
конструктора a-ля Excel») **появился рабочий бесплатный вариант**:
`modern-xlsx` с оговоркой про `initWasmSync`. Это не отменяет вывод «нет
зрелого готового **UI-редактора** диаграмм» — modern-xlsx не предоставляет
никакого UI, это writer уровня `exceljs`/`docx`, чарт-конструктор пришлось
бы писать в `apps/web` (форма «выберите тип/диапазон/заголовок» → вызов
`ChartBuilder`), но именно то ограничение, что «`exceljs` физически не
умеет писать диаграммы вообще», для modern-xlsx эмпирически не
подтвердилось — библиотека пишет.

**Рекомендация к принятию (программный, не UI, путь)**: если владелец
продукта готов принять на этом этапе программное добавление диаграмм/pivot
(кнопка «вставить диаграмму по выбранному диапазону» со своей простой
формой в `apps/web`, а не полноценный drag-and-drop конструктор уровня
Excel), `modern-xlsx` — рабочий бесплатный open-source кандидат для этого,
подтверждённый собственным round-trip тестом, а не только README. Риски,
которые остаются открытыми и требуют доп. проверки перед продовым
использованием: (1) незрелость пакета (1.2.1, вышел только что, малое
число загрузок — баги на менее тривиальных сценариях вероятны), (2)
`Node >= 24` формально заявлен в `engines` — обход через `initWasmSync`
работает, но это неофициальный путь, не гарантированный будущими минорными
версиями, (3) полный визуальный round-trip в Excel/LibreOffice не сделан в
этой сессии (нет установленного LibreOffice на машине проверки) — то, что
файл прошёл структурную ZIP/OOXML-проверку и `exceljs`-чтение, не заменяет
«открылось в реальном Excel и диаграмма отрисовалась», это следующий шаг
перед принятием решения в `21-OFFICE-IMPLEMENTATION.md`. Если ни один из
этих рисков не приемлем на этом этапе — базовый уровень «сохранить
нетронутым» (п. 1 рекомендации выше) остаётся действующим планом без
изменений, программная запись диаграмм через modern-xlsx — опциональное
дополнение сверху, не замена.
