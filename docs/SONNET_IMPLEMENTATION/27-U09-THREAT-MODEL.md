участником пространства-источника, но должен увидеть один конкретный объект
(или его ограниченную проекцию) через явный grant, выданный владельцем
данных. Это первый механизм в ORION, где RLS-политика должна пустить чтение
строки мимо `workspace_members` — до сих пор такого пути не было нигде.

## 1. Модель угроз (threat model)

### T1 — Grant на объект раскрывает связанные объекты через EntityLink/FK

Grant выдаётся на **конкретный `(objectType, objectId)`**, не на «всё, что с
ним связано». Если пользователю выдан grant на `Project`, это не должно
автоматически открывать все `Task`/`Note`/`Event`/`Document`/`Transaction`
этого проекта, даже если сервер обычно рендерит их вместе на карточке
проекта (см. 23-документ: «Проекты собирают задачи... не копируют их в
отдельные хранилища» — карточка проекта у member'а именно ЧИТАЕТ FK-связанные
таблицы). Для grantee это поведение обязано быть выключено: grant-aware
endpoint отдаёт только сам объект + его собственные скалярные поля (в
allowlist-варианте по типу, см. раздел 3.1), **не** делает traversal по
`projectId`-FK или по `EntityLink` в обе стороны. Если продукту нужен grant
на «проект и всё его содержимое», это отдельный, явно более широкий scope
(`scope: "full"` из раздела 2, переименован ниже — см. замечание о
терминологии), который в первой версии U09 **не реализуется** — контракт
23-документа прямо говорит «явные grants на целый объект/разрешённое
представление», не на граф связанных объектов.

Практическое правило: `EntityLink`-панель (`entity-links.tsx`) и любой другой
generic collector связей у grant-aware endpoint **не подключается**. Список
разрешённых полей для grant-aware чтения — allowlist на уровне одной
Prisma-модели, не «то же самое, что видит member, минус что-то». Финальный
per-type allowlist — раздел 3.1.

### T2 — Отозванный grant продолжает действовать из-за кэша

Два независимых уровня кэша, оба обязаны инвалидироваться по-своему при
`revoke`:

- **Клиент (react-query, `core-react`).** Как и `useNotes`/`useTasks`, будущий
  `useSharedObject(grantId)` держит `staleTime`. `revoke` должен
  инвалидировать `queryKey` через явный сигнал — либо через уже существующий
  `panel-bus.ts` (пере-broadcast «grant revoked» с `grantId`), либо коротким
  `staleTime` на shared-запросах по умолчанию (эти данные принципиально не
  «мои», кэшировать их агрессивно опаснее, чем для обычного workspace-ресурса).
  Практика ORION уже имеет решённый аналог: `NoteAutosave`/revision conflict —
  клиент никогда не предполагает, что локально закэшированное состояние
  бессрочно верно, конфликт обрабатывается явно, не молча.

  **Техническая поправка владельца, принята как финальное решение.** Отсутствие
  серверного кэша не означает отсутствие сохранённых данных на экране — React
  Query в ORION уже держит закэшированный результат предыдущего успешного
  чтения в памяти клиента независимо от `staleTime`. После revoke новое
  чтение обязано отказать (RLS + endpoint, см. ниже), но UI обязан явно
  **очистить** уже показанный контент при получении этого отказа, а не просто
  показать ошибку поверх устаревших данных. Клиент грант-aware запроса
  (`useSharedObject`) обрабатывает `403`/`404` явным `onError`, который
  вызывает `queryClient.removeQueries({ queryKey: ["shared", grantId] })` —
  именно `removeQueries`, не `invalidateQueries`: `invalidate` только помечает
  данные stale и рефетчит (рефетч тут же снова получит 403 и покажет старые
  данные ещё раз, если UI рендерит `data` до `error`), `removeQueries` реально
  стирает объект из памяти QueryClient, так что компонент, читающий кэш, видит
  `undefined`, а не последний успешный снимок.

  Явно зафиксированное и принятое ограничение: то, что уже отрисовано на
  экране или скачано пользователем до отказа (в т.ч. видимое человеческим
  глазом в момент revoke, до следующего рендера), объективно невозможно
  «отозвать» — как и запрос, который начался ДО revoke и был в полёте
  (in-flight) на сервер: ORION не может гарантированно прервать уже
  выполняющийся сетевой запрос (классический race между revoke-транзакцией и
  параллельным `SELECT`, выигранным до COMMIT revoke). Оба случая — не баг
  дизайна, а физическое ограничение, принятое явно, не «забытый край».
- **Сервер.** В ORION сегодня нет отдельного серверного query-кэша (все
  чтения идут прямой транзакцией к Postgres через `withUser`/`asSystem`) —
  значит для U09 «серверный кэш» это в первую очередь сама RLS-политика:
  если grant-aware policy проверяет `revokedAt IS NULL` (и `expiresAt`, см.
  раздел 2.1) в `EXISTS`-подзапросе на каждый read (не единожды при логине, не
  через JWT claim), отзыв работает мгновенно на следующий запрос без
  отдельного механизма инвалидации. **Grant не должен кодироваться в
  JWT/сессии** — это создало бы третий, самый живучий кэш (до истечения
  токена), который правило «отзыв действует для новых reads» прямо запрещает.

### T3 — Отозванный grant виден через search/export/notifications

Три отдельных канала, каждый со своим существующим кодом, который нужно
свести к тому же принципу — «grant проверяется на каждое использование, не
кэшируется в решении заранее»:

- **Search** (`SearchService`/`search.service.ts`) — сегодня строго
  `@Controller("workspaces/:workspaceId")`, ищет только внутри member'ского
  пространства. Grant-aware объекты **не** должны попадать в обычный
  workspace search вызывающего (это был бы объект без `workspaceId`,
  принадлежащего пользователю пространства — ломает инвариант №1 модульного
  контракта). Если продукту нужен «поиск по тому, что мне расшарено» — это
  отдельный индекс/endpoint (`GET /me/shared` по аналогии с `GET /me/overview`
  из U08), не расширение существующего `SearchService`.
- **Export/backup** (`snapshot-registry.ts`). Snapshot одного workspace
  бэкапит его собственные модели через `SNAPSHOT_MODEL_REGISTRY`. Объект,
  видимый через grant из ЧУЖОГО пространства, при экспорте пространства
  grantee **не входит** ни в снапшот, ни в blob-backup — он не принадлежит
  этому workspace. Новая модель `CrossWorkspaceGrant` — таблица
  пространства-источника (хранит и его `workspaceId`, и `granteeUserId`
  внешнего пользователя, см. раздел 2.1) и, по аналогии с
  `SentReminder`/`Notification.recipientId`, `included` в снапшоте
  пространства-**источника** (грант — часть его политики доступа), но **не**
  должна протекать в снапшот пространства grantee. Зафиксировать это явно при
  написании реестра в U09-реализации.
- **Notifications.** Если продюсер когда-нибудь создаст уведомление
  «пользователю X про объект Y через грант» — обязан следовать уже
  установленному R18-03 паттерну `notification-center.service.ts`:
  `moduleIdForEntityType` + `isVisibleToActor` фильтрует по доступности
  МОДУЛЯ; для grant-aware уведомлений аналогичная функция должна проверять
  **активность гранта**, а не модуля (у grantee модуль пространства-источника
  часто вообще недоступен — он не участник). Уведомление о ревокнутом гранте
  не должно раскрывать бывший title/summary — тот же принцип, что уже
  реализован в `entity-registry.ts` (`summary()` возвращает `null`, если
  `row.workspaceId !== workspaceId`): grant-revoked уведомление показывает
  generic placeholder («Доступ к объекту закрыт»), не последний известный
  title.

### T4 — Guessed/enumerated ID напрямую к обычному endpoint

Grant — это ДОПОЛНИТЕЛЬНЫЙ путь чтения, не замена существующей проверки.
`assertMember`-барьер на обычных `workspaces/:workspaceId/<resource>/:id`
endpoint'ах остаётся ровно как есть — обычный endpoint **никогда** не
консультирует grant-таблицу. Пользователь без membership и без гранта,
угадывающий id через `GET workspaces/:foreignWorkspaceId/projects/:id`,
получает тот же 403/404, что и сегодня. Grant открывает доступ **только**
через отдельный grant-aware endpoint (`GET /shared/:grantId/...`, раздел 2),
который сам проверяет активность гранта и не принимает произвольный
`workspaceId`/`objectId` от клиента вне того, что записано в самом гранте.
Это защищает от смешения двух разных резонов «имею доступ»: member-check и
grant-check физически не должны жить в одном SQL `WHERE`, который легко по
ошибке заменить одним ослабленным условием (ровно то, что явно запрещено
контрактом: «Не ослаблять membership RLS всей таблицы»).

**Техническая поправка владельца, принята как финальное решение — почему
одного лишь «отдельного endpoint» НЕДОСТАТОЧНО.** Дословно: «PostgreSQL
действительно объединяет permissive-политики через OR, но база не знает, из
какого HTTP-пути пришёл запрос. Без дополнительного условия grant-политика
может расширить видимость и в обычных запросах. Поэтому grant-ветка должна
действовать только в явно установленном сервером контексте shared-чтения
конкретного grant. Этот контекст ограничен транзакцией и не остаётся в
соединении пула. Политика — строго FOR SELECT; обычные операции записи
сохраняют прежние проверки.»

Черновик раздела 2.2 (первая версия документа) был неполон: если grant-aware
`CREATE POLICY ... FOR SELECT USING (EXISTS (... grant ...))` просто
проверяет «есть активный грант для этого пользователя+объекта», Postgres
применит её через `OR` **на любом** SELECT к этой таблице — включая обычный
`GET workspaces/:workspaceId/projects/:id` через `ProjectsController`, не
только `GET /shared/:grantId/...`. Postgres физически не видит, через какой
HTTP-путь пришёл запрос — только то, что видно из GUC-переменных текущей
транзакции. Значит одной новой permissive-политики insufficient: она должна
быть обусловлена **дополнительным** transaction-scoped флагом, который
сервер выставляет только внутри самого узкого возможного блока кода —
grant-aware endpoint, — и никогда в обычных `withUser`-транзакциях.

Финальная схема (заменяет черновик 2.2 раздела 2 ниже полностью, см. раздел
2.2 обновлённую версию): по аналогии с уже существующим
`set_config('app.current_user_id', userId, true)` из `PrismaService.withUser`,
вводится второй GUC — `set_config('app.active_grant_id', grantId, true)`,
третий аргумент `true` означает `is_local = true`: значение живёт только до
конца текущей транзакции и **не остаётся в соединении пула** после
COMMIT/ROLLBACK (обычный `SET LOCAL`-паттерн, тот же, что уже используется
для `app.current_user_id`). Только новый метод `PrismaService.withGrant(
grantId, userId, tx => …)` (специфичный для `SharedController`, никогда не
вызывается из обычных модульных сервисов) устанавливает этот GUC. RLS-policy
проверяет не просто «грант существует», а «грант существует **и**
`current_setting('app.active_grant_id', true) = grant.id`» — то есть строка
видна через grant-политику только когда сервер явно «включил» именно этот
конкретный grant-контекст для этой конкретной транзакции. Обычные
`withUser`-транзакции никогда не устанавливают `app.active_grant_id` (пустая
строка/`NULL` через `current_setting(..., true)` с `missing_ok=true` —
третий аргумент true не даёт функции упасть, если переменная не установлена),
поэтому grant-policy для них не срабатывает никогда, даже теоретически, даже
если бы кто-то по ошибке начал ходить в `Project`-таблицу из другого
контроллера. Политика остаётся строго `FOR SELECT` (не `ALL`) — обычные
`INSERT`/`UPDATE`/`DELETE` не получают grant-veto вообще, сохраняют только
membership-проверку (T5).

### T5 — Privilege escalation через связанные действия (comment/link/edit)

Первая версия U09 — **строго read-only** (явное требование контракта:
«Начать с read-only»). Grant на просмотр не даёт grantee возможности:
создавать `EntityLink` от/к объекту, писать `TaskComment`, редактировать
поля, прикреплять документы, ставить связи с чужими объектами своего же
пространства. Практически это означает: grant-aware endpoint физически не
монтирует ни один mutating route (`POST`/`PATCH`/`DELETE`) — не «проверка
роли внутри контроллера», а отсутствие маршрута. `TaskComment.userId`
проставляется только сервером для member'а данного workspace — grantee не
является `WorkspaceMember` пространства-источника, поэтому создание
комментария от его лица там структурно невозможно без отдельной, не
предусмотренной этим этапом модели «внешний участник».

Первый пользовательский сценарий (раздел 6) подтверждает это на уровне UX:
«никаких прав на дальнейшую передачу через ORION по умолчанию» — то же самое
read-only-и-ничего-больше правило, явно сформулированное владельцем продукта.

### T6 — Statistical disclosure через частичные агрегатные проекции

Зафиксировано как ИЗВЕСТНЫЙ РИСК для будущей реализации, не решается в этой
сессии и не должно решаться кодом без отдельного продуктового решения.
Пример: `scope: "projection"` открывает «средний чек» или «сумма операций за
месяц» по `Transaction`, не отдельные строки. При малом количестве операций
(1–2 за период) агрегат тривиально обратим в точную сумму конкретной
транзакции — то, что 23-документ явно называет («разные агрегаты могут
раскрыть скрытые суммы»). Практическое минимальное требование к будущей
реализации: проекция обязана явно перечислять допустимые измерения
(`allowedDimensions`) и **не** предлагать группировку, которая может
схлопнуться до одной строки (минимальный `k`-anonymity порог — например
отказ показывать агрегат по периоду/категории с count < N). Это не
реализуется в U09-read-only-full-object срезе (там нет агрегатов вообще —
только allowlisted поля целого объекта per-type, раздел 3.1), но must-read
для сессии, которая возьмётся за `scope: "projection"` с агрегатами. Раздел 5
черновика поднимал это как открытый вопрос №5 — владелец продукта подтвердил
(раздел 5 этой редакции), что первая версия U09 `projection`/агрегаты не
затрагивает вовсе; бюджет как тип объекта получает свою отдельную,
не-агрегатную проекцию (раздел 3.1, «бюджет»), которая не подпадает под этот
риск, потому что не суммирует множество строк, а отдаёт заранее определённое
подмножество уже агрегированных владельцем полей представления.

### T7 — RLS-политика grant-aware чтения обязана быть ОТДЕЛЬНОЙ политикой, не правкой membership-политики

Каждая существующая RLS-политика в ORION (`lists_isolation`,
`habits_isolation`, и т.д.) — одна `CREATE POLICY ... USING (EXISTS (SELECT 1
FROM workspace_members wm WHERE wm."workspaceId" = ... AND wm."userId" =
current_setting(...)))` на таблицу. Postgres разрешает **несколько
permissive-политик на одной таблице для одной команды** — они комбинируются
через `OR` автоматически (это стандартное поведение `PERMISSIVE`-политик,
дефолт в Postgres, если не объявлено `AS RESTRICTIVE`). Значит grant-aware
чтение реализуется как **вторая** `CREATE POLICY` на той же таблице (например
`projects_grant_read`), не как правка `projects_isolation`. Как объяснено в
T4, эта вторая политика обязана дополнительно проверять
`app.active_grant_id`, иначе её `OR`-комбинирование с `projects_isolation`
буквально означает «расширить видимость и в обычных запросах» — ровно тот
риск, о котором предупредил владелец продукта.

Structural-тест `api-rls.integration.test.ts`, который проверяет «ENABLE +
FORCE + хотя бы одна политика», продолжит проходить и с двумя политиками на
таблице — но для U09-реализации потребуется **новый** тест, который проверяет
ИМЕННО, что (а) member без гранта не видит чужой объект, (б) grantee без
membership видит ровно его и только его через `GET /shared/:grantId/...`,
(в) revoke закрывает доступ немедленно, и (г) — новое требование из
поправки 1 — **тот же самый grant, будучи активным, не расширяет видимость
объекта через обычный `workspaces/:workspaceId/projects/:id` endpoint**, то
есть что `app.active_grant_id` действительно не «протекает» за пределы
транзакции `SharedController`.

## 2. Допустимые SQL/RLS-политики (черновик для U09-реализации; финализированы решения владельца, детали SQL/Prisma всё ещё уточняются в реализации)

### 2.1 Модель `CrossWorkspaceGrant`

```prisma
// Финализировано по решениям владельца продукта (раздел 5). Поля/индексы
// могут получить незначительные уточнения в U09-реализации, но
// granteeUserId/expiresAt/scope зафиксированы как финальный контракт.
model CrossWorkspaceGrant {
  id              String    @id @default(cuid())
  // Пространство-владелец объекта (для RLS-подзапроса и для snapshot-registry).
  workspaceId     String
  // Кто выдал: WorkspaceMember.id выдавшего. Только owner пространства-источника
  // (раздел 5, вопрос 1) — не любой member/lead. Будущее расширение: отдельное
  // разрешение "Управление внешним доступом" для делегирования права выдачи
  // (НЕ реализуется сейчас, см. раздел 5).
  granterId       String
  // Кому: User.id получателя, НЕ WorkspaceMember.id и НЕ Workspace.id.
  // Grant выдаётся конкретному человеку, не пространству-получателю: grantee
  // сам решает, в каком из СВОИХ пространств отображать доступ (например
  // через личные "сферы"/избранное из U05) — это вопрос UI-организации на
  // его стороне, не часть модели гранта. "Выдать всем участникам пространства
  // Б" — отдельное будущее workspace-level правило, не реализуется здесь
  // (раздел 5, решение владельца).
  granteeUserId   String
  // Закрытый enum, тот же принцип, что SearchableEntityType в entity-registry.ts —
  // никогда не произвольная строка от клиента.
  objectType      String    // SearchableEntityType
  objectId        String
  scope           String    // "full" | "projection" — projection не реализуется в первом срезе
  // Для projection: allowlist полей. NULL для scope="full".
  projectionFields String[]?
  // Опциональный срок действия (раздел 5, вопрос 3). NULL = без срока.
  // RLS-подзапрос (2.2) проверяет revokedAt IS NULL AND (expiresAt IS NULL OR
  // expiresAt > now()) на каждый read — то же "живой чек", что и revokedAt,
  // не отдельный крон, который материализует revokedAt при истечении: живая
  // проверка в самой политике достаточна и не требует шестого @Cron-сервиса.
  expiresAt       DateTime?
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt
  revokedAt       DateTime?
  // Кто отозвал — для аудита; не влияет на то, КТО имеет право отозвать
  // (см. раздел 4, Revoke) — это фиксируется в коде сервиса, не в схеме.
  revokedByUserId String?

  @@index([workspaceId])
  @@index([granteeUserId, objectType, objectId])
  @@map("cross_workspace_grants")
}
```

Комментарий по месту таблицы в реестре: `CrossWorkspaceGrant` физически
хранит и `workspaceId` источника, и `granteeUserId` внешнего пользователя —
она `included` в снапшоте пространства-**источника** и никогда не входит в
снапшот пространства grantee (T3, финализировано выше — устраняет
неопределённость, которую черновик оставлял открытой).

**Client-side hide (раздел 5, вопрос 2, уточнение).** Grantee не может
отозвать грант, но может убрать объект из своего личного списка отображения
— это чисто клиентское состояние (аналог локального "скрыть", по типу уже
существующих client-side предпочтений вроде layout из U06), не отдельное
поле в `CrossWorkspaceGrant` и не серверный revoke: объект остаётся
технически доступным по гранту, просто grantee решил не видеть его в своём
UI. Реализуется как обычная клиентская настройка (localStorage/user
preference — конкретный механизм решается в U09-реализации), не как
изменение модели гранта.

### 2.2 Grant-aware RLS: транзакционный контекст + ADDITIVE-политика (финальная схема, заменяет черновик)

Существующая политика на `projects` (по образцу `lists_isolation`, реальный
паттерн из миграций) не меняется:

```sql
-- УЖЕ СУЩЕСТВУЕТ (пример, не трогать):
CREATE POLICY projects_isolation ON "projects"
  USING (EXISTS (
    SELECT 1 FROM "workspace_members" wm
    WHERE wm."workspaceId" = "projects"."workspaceId"
      AND wm."userId" = current_setting('app.current_user_id', true)
  ));
```

Новая политика для U09 — отдельный `CREATE POLICY`, обусловленный
транзакционным контекстом гранта (см. T4 выше — почему одного `EXISTS`
недостаточно):

```sql
-- Черновик SQL для U09-реализации: направление финализировано владельцем,
-- точная запись подзапроса будет уточнена в момент написания миграции.
-- ADDITIVE: не заменяет projects_isolation, Postgres берёт OR обеих политик
-- для permissive policies на одну команду (SELECT). FOR SELECT явно —
-- INSERT/UPDATE/DELETE не получают grant-политику вообще (T5).
CREATE POLICY projects_grant_read ON "projects"
  FOR SELECT
  USING (
    current_setting('app.active_grant_id', true) IS NOT NULL
    AND EXISTS (
      SELECT 1 FROM "cross_workspace_grants" g
      WHERE g."id" = current_setting('app.active_grant_id', true)
        AND g."objectType" = 'project'
        AND g."objectId" = "projects"."id"
        AND g."granteeUserId" = current_setting('app.current_user_id', true)
        AND g."revokedAt" IS NULL
        AND (g."expiresAt" IS NULL OR g."expiresAt" > now())
    )
  );
```

`app.active_grant_id` — второй transaction-local GUC (`set_config(...,
true)`, `is_local = true`, тот же механизм, что уже несёт
`app.current_user_id`), выставляется **только** внутри нового
`PrismaService.withGrant(grantId, userId, tx => …)`, который вызывает
исключительно `SharedController`/`SharedService` (раздел 2.3). Обычные
`withUser`/`asSystem`-транзакции никогда не устанавливают эту переменную —
значит `projects_grant_read` не может сработать ни в одном обычном
member-запросе, даже теоретически (устраняет риск, описанный в поправке 1).
Значение живёт строго в рамках одной транзакции и не переживает возврат
соединения в пул.

### 2.3 Grant-aware endpoint — отдельный path, не расширение обычного

```
GET /shared/:grantId/project    -- endpoint отдаёт данные конкретному
                                    авторизованному пользователю (текущий
                                    JWT userId должен совпасть с
                                    grant.granteeUserId), не "любому
                                    участнику указанного пространства" —
                                    у grant-получателя своего пространства
                                    здесь вообще нет в игре.
```

Почему отдельный endpoint, а не grant-aware ветка внутри обычного
`ProjectsController`:

1. **Контракт явно требует это**: «выделить узкий grant-aware policy/endpoint
   и тестировать каждый путь доступа» — не одну проверку внутри общего пути.
2. Обычный endpoint принимает `workspaceId` из URL и решает через
   `assertMember` — если туда же добавить grant-fallback, любая будущая
   правка `assertMember`/забытый `else` случайно откроет grant-путь для
   member-only операций (mutating routes того же контроллера). Отдельный
   `SharedController` физически не может смонтировать mutating route по
   ошибке — grant-объекты не проходят через `ProjectsController` вообще.
3. `:grantId` в URL, не `:workspaceId/:objectId` — endpoint сам резолвит
   `objectType`/`objectId`/`workspaceId` из записи гранта после проверки
   `revokedAt IS NULL`, `expiresAt` и `granteeUserId === текущий userId`.
   Клиент не может подставить чужой `objectId` при валидном `grantId` —
   единственный контролируемый вход это сам `grantId`, который выдаётся
   владельцем и не угадывается (cuid).
4. Ответ идёт через тот же принцип, что `entity-registry.ts summary()` —
   allowlist полей per-type (раздел 3.1), собранный вручную в
   `toDto`-подобной функции `toSharedProjectDto`, не тот же `toDto`, что
   видит member (member-DTO может содержать поля, не предназначенные для
   grantee, например внутренние заметки участников).
5. Внутри обработчика запрос идёт через `PrismaService.withGrant(grantId,
   userId, tx => …)` (раздел 2.2), а не через `withUser` — именно этот вызов
   устанавливает `app.active_grant_id` и делает возможным срабатывание
   `*_grant_read`-политики только для этой транзакции.

### 3.1 Allowlist per entity type — финальное решение владельца

Черновик формулировал T1 обобщённо («read full object, allowlist на уровне
одной Prisma-модели»). Владелец продукта явно расписал это по каждому типу —
эта таблица финализирует конкретный allowlist-контур на верхнем уровне (точные
имена полей — в U09-реализации при написании `toSharedXDto`, но семантическая
граница ниже — не подлежит расширению без нового продуктового решения):

| Тип (`objectType`) | Что входит в grant-aware чтение | Что явно НЕ входит |
|---|---|---|
| `note` | Текст заметки (тело, заголовок, теги) | Связанные документы (вложения заметки — те же `Document`, не подтягиваются автоматически, T1); история ревизий (см. таблицу выше) |
| `document` | Текущее содержимое файла (последняя версия, как выдана `StorageAdapter`) + базовые метаданные карточки | История версий (`DocumentVersion`) — не включается ни при каком scope; **предупреждение владельца (см. ниже)**: сам файл может содержать встроенные картинки, скрытые листы, метаданные — весь файл целиком становится видим получателю, частичного «показать только некоторые страницы/ячейки» нет |
| `project` | Разрешённые поля карточки проекта (название, описание, статус, даты — конкретный список уточняется в реализации по образцу `toDto`) | Автоматическое раскрытие связанных `Task`/`Event`/финансовых данных проекта (T1) — если нужен доступ к содержимому, это отдельный, более широкий и явно не реализуемый сейчас scope |
| `document` (продолжение — предупреждение UI) | — | UI выдачи grant на `Document` **обязан** явно предупреждать владельца перед выдачей, что весь файл целиком (включая скрытые листы XLSX, встроенные изображения и другие данные, которые сам владелец может не помнить, что там есть) станет видим получателю — нет постраничного/поячеечного ограничения в первой версии |
| `project`/финансы (`бюджет`) | Отдельно определённая проекция представления бюджета (заранее заданный, не произвольно агрегируемый набор полей) | Доступ ко всем финансовым операциям (`Transaction`) проекта — бюджет как понятие в ORION не отдельная Prisma-модель (в `schema.prisma` нет `model Budget`; бюджетная логика — `apps/api/src/finance/budget-alerts.service.ts` поверх `Transaction`/категорий), поэтому «grant на бюджет» реализуется как `scope: "projection"` над агрегированным представлением бюджета конкретного проекта/пространства, не как grant на новую сущность — это уточнение зафиксировать при написании реализации, но принцип «проекция, не полный доступ к операциям» финальный |
| `task` | Поля задачи по allowlist (по аналогии с остальными; конкретный список — при реализации) | Комментарии (`TaskComment`), `TaskActivity`-журнал, подзадачи — не подтягиваются автоматически (T1) |
| `transaction` | Поля отдельной операции по allowlist | Агрегаты по множеству транзакций — это `scope: "projection"`, не входит в `scope: "full"` одной транзакции; risk см. T6 |

Общий принцип, действующий для всех типов: allowlist — это **явный список
полей одной Prisma-модели**, не «всё, что видит member, минус что-то
вычеркнутое». Ни один тип не получает traversal по FK/EntityLink в
grant-aware чтении.

## 4. Lifecycle гранта

**Create.** Финализировано (раздел 5, вопрос 1): выдаёт **только `owner`**
пространства-источника — не любой `member`/`lead`. Это узкий безопасный
дефолт, принятый владельцем продукта как окончательное решение для первой
версии, а не временная заглушка до ответа. Будущее расширение (явно не
реализуется в этой сессии и не в ближайшей реализации U09): отдельное
делегируемое разрешение «Управление внешним доступом», которое owner сможет
выдать конкретному `member`/`lead`, чтобы тот тоже мог создавать гранты — но
это отдельная, явно обозначенная будущая карточка, не часть текущего среза.

**Active.** `revokedAt IS NULL AND (expiresAt IS NULL OR expiresAt > now())`.
Единственное состояние, в котором grant-aware RLS-политика (2.2) и
grant-aware endpoint (2.3) пропускают чтение. `expiresAt` (раздел 5, вопрос
3, финализировано) — опциональное поле; UI предлагает три варианта при
создании: «Без срока» (`expiresAt = null`), «На 7 дней» (сервер вычисляет
`now() + 7d` при создании — конкретное значение, не дрейфующее «релативное»
поле), «До даты» (явный date picker, конкретная дата от владельца). Истечение
проверяется той же живой RLS/endpoint-проверкой на каждый read, не отдельным
`@Cron`-сервисом — шестой периодический джоб не нужен, потому что проверка
"дешёвая" (сравнение с `now()` в уже существующем подзапросе) и не требует
материализации `revokedAt` заранее.

**Revoke.** Финализировано (раздел 5, вопрос 2): право отозвать есть у двух
ролей одновременно — (а) тот, кто выдал грант (`granterId`, если он всё ещё
имеет доступ выдавать, т.е. хотя бы member пространства), **либо** (б)
текущий `owner` пространства-источника, даже если грант выдавал не он (например
предыдущий owner, до смены владения пространством). Это осознанное расширение
полномочий текущего owner за пределы того, что было в черновике описано как
предположение — теперь финальное правило. Получатель (`granteeUserId`) НЕ
может отозвать грант никогда — только выполнить client-side "hide" в своём
личном списке отображения (раздел 2.1): объект остаётся технически доступным
по гранту (owner по-прежнему может явно revoke), просто получатель решил не
видеть его у себя в UI.

Эффект revoke по каналам, раздельно (контракт требует разного для каждого):

- **Reads** — мгновенно на следующий запрос: RLS-политика (2.2) и
  grant-aware endpoint оба проверяют `revokedAt IS NULL` (и `expiresAt`) при
  каждом чтении, не кэшируют решение (T2).
- **Search** — grant-объекты никогда не входили в обычный search (T3), эффект
  revoke здесь нулевой по построению; если появится отдельный «мой shared»
  индекс — тот же принцип, live-проверка `revokedAt`/`expiresAt`, не
  отдельный переиндексируемый снапшот.
- **Cache refresh** — клиентский react-query явно очищается (не просто
  инвалидируется) при получении 403/404 на grant-aware запрос:
  `queryClient.removeQueries` по сигналу panel-bus «grant revoked» или прямо
  из `onError`-обработчика самого запроса (T2, техническая поправка 2 выше).
  Явно НЕ полагаться на TTL длиннее, чем у обычных workspace-ресурсов, и явно
  НЕ полагаться на то, что `invalidateQueries` достаточно — она не стирает
  уже отрисованные данные из памяти.
- **Export** — снапшот пространства grantee никогда не содержал чужой объект
  (T3); revoke не меняет это. Снапшот пространства-источника, взятый ДО
  revoke, естественно содержит активную запись гранта на тот момент времени —
  это ожидаемое поведение бэкапа-как-снимка-времени, не утечка.
- **Notifications** — будущий grant-aware продюсер обязан фильтровать по
  `revokedAt IS NULL`/`expiresAt` в момент отправки/чтения, тем же паттерном
  `isVisibleToActor`, и не раскрывать бывший title в placeholder (T3).

**Уже скачанные/отрисованные копии.** Явно принимается как известное и
нерешаемое техническими средствами ограничение: если grantee экспортировал/
скопировал данные объекта до revoke (скриншот, скопированный текст, PDF,
ручная выгрузка) — или просто уже видел их на экране в момент revoke, до
следующего рендера, — у ORION нет и не будет механизма отозвать эту копию.
Аналогично, запрос, начавшийся до revoke (in-flight на сервер), физически не
может быть гарантированно прерван — это race между двумя параллельными
транзакциями, не архитектурный пробел. Документ контракта прямо признаёт
первый случай («уже скачанные копии отозвать нельзя»), а технические
поправки владельца продукта явно распространяют то же признание на
уже-отрисованный React Query кэш и на in-flight запросы — не пытаться
закрыть DRM-подобным решением, не заводить это как открытый вопрос.

## 5. Открытые вопросы для владельца продукта — ФИНАЛЬНЫЕ РЕШЕНИЯ (закрыто, 2026-09-22)

Все 5 вопросов черновика закрыты. Решения ниже — окончательные, не подлежат
пересмотру без нового продуктового запроса.

1. **Кто может выдать грант.** Только `owner` пространства-источника. Позже
   (отдельная, явно не начатая карточка) — делегируемое разрешение
   «Управление внешним доступом» для расширения этого круга. Раздел 4,
   «Create».

2. **Кто может отозвать грант.** Тот, кто выдал (`granterId`), **либо**
   текущий `owner` пространства-источника (даже если выдавал не он).
   Получатель (grantee) отозвать не может — может только client-side "hide"
   в своём личном списке отображения (не серверный revoke, объект технически
   остаётся доступным по гранту). Раздел 4, «Revoke», раздел 2.1.

3. **Срок жизни гранта.** Да, опциональный `expiresAt`. UI — три варианта:
   «Без срока» / «На 7 дней» / «До даты» (date picker). Проверяется той же
   живой RLS/endpoint-проверкой на каждый read, отдельный `@Cron` не нужен.
   Раздел 2.1, раздел 4.

4. **История версий объекта.** НЕ включается в grant ни при каком scope —
   только текущее состояние. Обоснование владельца: «в старых версиях могут
   быть сведения, которыми пользователь не собирался делиться». Раздел 3
   (permission matrix), раздел 3.1.

5. **Live projection vs snapshot.** Живые данные — приоритетный и
   единственный вариант первой версии: следующее чтение всегда показывает
   актуальное состояние объекта (RLS читает живую таблицу, сервер намеренно
   ничего не кэширует). Замороженный снимок (полезный, например, для отчёта
   за конкретный период) явно зафиксирован как **предвиденное будущее
   расширение** — отдельная будущая функция, вне объёма текущего решения;
   механизм снимков не проектируется в этом документе.

   `scope: "projection"` с агрегатами (T6, было отдельным пунктом 5 в
   черновике под другим номером) остаётся вне объёма первой версии U09 —
   допустимые измерения/агрегаты per-type — отдельное будущее продуктовое
   решение, не блокирует read-only-full-object срез.

## 6. Первый пользовательский сценарий (UX flow)

Зафиксировано владельцем продукта как ориентир для будущей UI-реализации —
не код, но обязательная последовательность шагов, которой реализация
`SharedController`/клиентского UI обязана соответствовать по форме:

1. **Владелец выбрал объект** — конкретный `(objectType, objectId)` в своём
   пространстве, на который хочет выдать доступ.
2. **Указал получателя и срок** — конкретного пользователя (`granteeUserId`,
   не пространство) и один из трёх вариантов срока действия (раздел 5, вопрос
   3: без срока / 7 дней / до даты).
3. **Проверил, что будет доступно** — владелец видит превью того, что именно
   увидит grantee: конкретный allowlist полей по типу объекта (раздел 3.1),
   явно включая предупреждение для `document` о содержимом всего файла
   целиком (скрытые листы, встроенные изображения и т.п.), если тип объекта —
   документ.
4. **Предоставил просмотр** — создаёт `CrossWorkspaceGrant` со `scope:
   "full"` (в первой версии `projection` недоступна из UI).

У получателя (grantee) на его стороне видны:

- **Источник** — из какого пространства/от кого пришёл доступ.
- **Режим «Только просмотр»** — явно обозначено, что это read-only, без
  каких-либо прав редактирования или дальнейшей передачи.
- **Срок доступа** — если задан `expiresAt`, отображается явно (например
  «доступ истекает 29.09.2026»).

**Никаких прав на дальнейшую передачу через ORION по умолчанию** — grantee не
может re-share объект третьему лицу через ORION; максимум, что доступно
получателю на своей стороне — организовать отображение в своём личном
пространстве (например через «сферы»/избранное из U05) и, отдельно,
client-side "hide" убрать объект из своего списка (раздел 2.1, раздел 4) —
оба действия не меняют сам грант и не влияют на доступ других людей.
