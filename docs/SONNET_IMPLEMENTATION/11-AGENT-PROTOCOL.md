# Рабочая инструкция для Claude Sonnet 5

## Готовый стартовый запрос

```text
Ты продолжаешь ORION по комплекту docs/SONNET_IMPLEMENTATION.
Прочитай корневой CLAUDE.md, README этого комплекта и 12-PROGRESS.md.
Выбери первую READY/TODO задачу 10-BACKLOG.md с выполненными dependencies.
Прочитай только связанные спецификации и исходники. Сначала проверь, не сделано
ли требуемое уже в текущем dirty working tree. Не переписывай работающие слои.
Выполни одну законченную задачу/подзадачу, включая контракты, миграции, UI и
нужные тесты. Не считай скрытие UI серверным контролем доступа.
Рабочую БД не сбрасывай, чужие изменения не удаляй и не включай в свой commit.
В конце запиши evidence, команды и результат в 12-PROGRESS.md; при нехватке
контекста оставь точный checkpoint. Не утверждай, что весь ORION готов,
пока S19 не пройден. Личный и командный сценарии равноправны.
```

## Минимальный контекст на задачу

| Тип задачи | Читать |
|---|---|
| Доступ/данные | CLAUDE + 01 соответствующая находка + 03 + 08 + карточка |
| Backup | CLAUDE + 09 раздел 1 + S02/S03/S04 + текущий SYNC |
| UI | CLAUDE + 04 + 05 + раздел модуля в 06 + карточка |
| Команда | 02 + 03 + 08 + карточка |
| Выпуск | 09 + 13 + progress |

Не перечитывать 3000 строк PLAN каждый turn. Перед архитектурной правкой прочитать соответствующие исторические разделы, как требует CLAUDE; сохранить номера/названия в checkpoint.

## Алгоритм одной сессии

1. `git status --short`. Записать ownership текущих изменений. Если непонятно, не откатывать.
2. Найти target functions через `rg`/доступный актуальный graft. Не читать весь репозиторий.
3. Сформулировать инвариант: какой сценарий был неверным, каким должен стать.
4. Для data/security/concurrency дефекта — воспроизводящий тест до правки. Для простой визуальной правки — baseline screenshot, не тест внутренней реализации.
5. Изменить все затронутые слои. Не возвращать половину DTO и не использовать any для закрытия typecheck.
6. Запустить целевые тесты; затем обязательный gate по масштабу задачи. Не повторять уже зелёный полный suite без новой причины.
7. Проверить diff: лишние файлы, секреты, незавершённые TODO, несоответствие контрактов.
8. Progress: результат, evidence, skipped, следующий шаг. Работу считать DONE только по acceptance.

## Правила точности

- Перед добавлением функции найти существующий аналог. Особенно: versioned files, AutosaveStatus, semantic colors, module restrictions, reminders, habit/time helpers.
- Не принимать комментарии и старую документацию за доказательство поведения. Читать вызываемый код.
- Не называть unit тесты интеграционными; не заменять реальную RLS проверку mock Prisma.
- Для race test запускать конкурирующие операции, а не два последовательных await.
- Date-only и instant — разные контракты. Деньги — minor units и currency. Unknown — null, не 0.
- Запрет role проверяется сервером; RLS membership не заменяет module restrictions.
- Любой новый workspace model включён в RLS и backup registry.
- Никакой отправки реальных писем/Telegram/push внешним адресатам во время тестов: stub/test sink.
- Новые зависимости только при объяснённой необходимости. Не менять стек, потому что он привычнее агенту.
- Не массово форматировать не связанные с задачей файлы.

## Что должно быть в отчёте

```text
Задача: Sxx / подэтап
Статус: DONE | PARTIAL | BLOCKED
Изменено: конкретное поведение, список файлов
Проверено: команда → exit/result; fixture и сценарии
Миграции: новые имена; как безопасно применить
Не проверено: список и причины
Осталось: следующий конкретный шаг
```

## Checkpoint при завершении контекста/лимита

```text
Текущая задача и подэтап:
Прочитанные authority/docs:
Сделано и файлы:
Последняя зелёная проверка:
Текущий failing test/error (без секретов):
Незавершённое изменение и риск:
Следующая команда/действие:
Состояние test DB/storage/processes:
```

Не просить пользователя снова объяснять проект. Не оставлять status DONE, если migration/test/реальный UI-flow ещё не проверены.

## Если факты изменились

Этот комплект — снимок 2026-09-21, исходники могут опередить его. Если acceptance уже выполнен, отметить VERIFIED_EXISTING с evidence, не переделывать. Если пользователь изменил продуктовый приоритет, обновить 14-DECISIONS и затронутые карточки; не продолжать несовместимую старую директиву.

## Для нескольких агентов, если владелец отдельно разрешил

Один интегратор владеет schema/shared-types/ApiClient. Другие получают конкретные непересекающиеся поверхности после фиксации контрактов. Каждый сдаёт patch + тесты + ограничения; интегратор запускает общий gate. Работа параллельно без такого контракта быстрее расходует контекст, чем экономит время.

## Старт офисной задачи

Читать актуальный раздел README → 20-DOCUMENT-EDITORS → конкретную O-задачу и матрицу в 21-OFFICE-IMPLEMENTATION. Проверить по коду и тестам состояние R18-01/02/03, а не считать их закрытыми по возрасту отчёта. Реализация стартует с O01; не устанавливать одновременно Tiptap/Univer и офисный сервер. Не считать iframe завершённой интеграцией. В 12-PROGRESS записывать только реально выполненные O-задачи и результаты OF-проверок, включая NOT RUN и ограничения лицензии/окружения.

## Актуальный старт после обсуждения ядра

Начинать с 26-SONNET-START, далее 23/24/25. Не перечитывать весь большой журнал на каждом шаге. Учитывать новые пользовательские решения о семейном сценарии, сферах, drag/sidebar и независимых окнах: старые запреты/упрощения UI не отменяют явно согласованный новый scope. Native office реализацию не заменять Document Server. Сначала воспроизвести приложенные regressions, затем менять код.
