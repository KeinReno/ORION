## R29-01 · P1 · Отозванный grant работает для участника пространства

**Код:** `apps/api/src/common/prisma.service.ts:97–102`, `apps/api/src/shared/shared.service.ts:38–48`, аналогично content-путь `:114–119`.

`withGrant` вычисляет `active`, но при `false` всё равно вызывает callback. Отсутствие grant-контекста выключает только grant-политику; обычная membership-политика продолжает разрешать SELECT.

Воспроизведено HTTP-тестом:

1. Owner выдаёт grant на заметку пользователю, который также member исходного workspace.
2. Owner ограничивает для member модуль `notes` и отзывает grant.
3. Member вызывает `GET /shared/:grantId` — получает **200 и текст**, ожидается 404.

Второй тест: owner, который не является получателем данного grant, тоже получает 200 на shared-пути. Сам по себе owner уже имеет права на объект; этот тест доказывает нарушение контракта endpoint, а первый — реальный обход ограничения модуля.

**Исправление:** не исполнять callback, если grant отсутствует, чужой, истёк или отозван. Вернуть одинаковый 404. Передавать callback уже проверенные параметры grant, не полагаться на отсутствие объекта в membership-SELECT. Сохранить дополнительную проверку активности grant в SQL при чтении и transaction-local контекст. Не заменять существующие membership-политики.

**Приёмка:** оба приложенных теста; дополнительно expiry + member, document/content + revoked member; обычные workspace API должны продолжать работать по собственным правам независимо от grant.

## R29-02 · P1 · Restore заново открывает отозванный доступ

**Код:** `apps/api/src/sync/snapshot.service.ts:106`, `:287` (`apply`); `snapshot-registry.ts:118–125`.

Grant включён в обычный снимок и восстанавливается вместе с прежним `revokedAt: null`. Проверено через реальный `SnapshotService.serialize/apply` и HTTP чтения, без WebDAV:

`создать grant → снять backup → отозвать → GET 404 → apply старого snapshot → GET 200`.

Это не невозможность отозвать скачанную копию: сервер снова выдаёт доступ к текущим данным. Восстановление содержимого не должно молча восстанавливать внешние полномочия.

**Исправление:** вывести жизненный цикл внешних разрешений из обычного восстановления данных. Рекомендуемый контракт: архивные grant-записи можно хранить для аудита, но ни одна запись из backup не становится активной автоматически; текущие отозванные права не сбрасываются. При необходимости повторного предоставления доступа — новый явный grant владельцем. Учесть старые снимки, порядок удаления сущностей и polymorphic objectId; простое исключение одной строки из registry недостаточно без проверки restore-семантики.

**Приёмка:** приложенный restore-тест, restore снимка без grant-таблицы, отсутствие shared-объектов в backup получателя. Владелец должен видеть, что восстановление не переоткрывает внешний доступ.

## R29-03 · P2 · Shared-путь читает заметку из корзины

**Код:** `apps/api/src/shared/shared.service.ts:43–48`, `shared-grants.service.ts` → `assertObjectOwnedByWorkspace`.

Воспроизведено: внешний пользователь читает заметку по grant; owner удаляет заметку обычным DELETE (soft delete); следующий shared GET всё ещё **200 с полным body**. В shared SELECT отсутствует условие `deletedAt: null`. Выдача нового grant также не проверяет корзину. Для документа metadata SELECT имеет аналогичный пробел, хотя `openContentForGrant` проверяет `deletedAt` и не выдаёт bytes.

**Исправление:** исключить удалённые объекты при выдаче и чтении grant; для document принимать только живой `kind=file`. Зафиксировать единый контракт для списка «Доступно мне» и восстановления из корзины. Рекомендуется не активировать отозванные grants при восстановлении объекта.

**Приёмка:** приложенный note regression; document metadata/content после удаления; попытка создать grant на объект корзины и на папку.

## R29-04 · P2 · RLS даёт получателю изменять сам grant

**Код:** миграция `cross_workspace_grants_rls`, политика `cross_workspace_grants_isolation`.

Политика без `FOR SELECT` допускает получателя через `OR granteeUserId = current_user_id` для всех команд. Отдельный тест под обычным `orion_app`, внутри `withUser(grantee)`, успешно изменил `objectId` grant на другую, не предоставленную заметку владельца.

**Граница доказательства:** это подтверждённый дефект SQL-защиты, **не продемонстрированная атака через существующий HTTP endpoint**. Контроллеры сейчас дополнительно проверяют owner/creator. Тем не менее обещание read-only на уровне RLS для строки разрешения не выполняется, а случайный будущий update-путь сможет расширить доступ.

**Исправление:** новая миграция с отдельной SELECT-политикой и явными INSERT/UPDATE/DELETE-политиками. Получатель получает только SELECT. Выдача — owner, отзыв — допустимый issuer/current owner. Не разрешать UPDATE произвольных objectId/workspaceId/granteeUserId под видом отзыва; закрепить неизменяемость назначения grant выбранным механизмом и тестами. Не менять уже применённую миграцию задним числом.

**Приёмка:** приложенный RLS regression плюс отрицательные create/update/delete для grantee; положительные create/revoke владельцем. Не ослаблять SQL-тест, заменив его тестом guard контроллера.

## R29-05 · P2 · UI не позволяет выбрать внешнего получателя

**Код:** `apps/web/components/share-grant-section.tsx` → `useSearchWorkspaceMembers(workspaceId, query)`; `apps/api/src/workspaces/workspaces.service.ts:105` → `searchMembers`.

Поиск фильтрует roster **исходного** workspace. Человека из другого пространства без membership источника выбрать нельзя. Пользователь вынужден сначала дать ему членство во всём исходном пространстве, что противоречит задаче узкого доступа. Это подтверждается кодом и существующим members-search тестом, который явно исключает внешнего Bob; браузерный тест не запускался.

**Исправление:** отдельный безопасный способ адресовать grant внешнему человеку без source membership: например, подтверждённые контакты пользователя из доступных ему пространств либо точный адрес приглашения с нейтральным ответом без глобального поиска аккаунтов. Выбор/приглашение не должно автоматически делать человека участником источника. Не расширять текущий endpoint до публичного поиска всех пользователей.

**Приёмка:** owner A выбирает человека из B, не добавляя его в A; тот видит только предоставленный объект, обычный endpoint A возвращает отказ. Поддержать также себя как получателя для будущего сценария закрепления в другом своём контексте, если это предусмотрено продуктовым контрактом; само назначение в целевой workspace в текущем срезе не проверено.
