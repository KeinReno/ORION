# Architect proposal — authored software architecture

**Status:** accepted by the owner on 2026-11-18; implementation belongs to the existing ORION DEV / Architect module.  
**Date:** 2026-11-18  
**Owner:** ORION DEV / Architect. No separate Canvases module or project-view extension point is introduced.

## Problem

Architect has three distinct concepts that must remain distinct:

- **Repository map:** observed files, modules, crates and import/call edges, generated by the registered-repository analyzer.
- **Project intent:** a comparison input whose node IDs and kinds correspond to repository paths and analyzer nodes.
- **Workflow:** an editable process graph with task, agent, evidence, decision and result nodes.

Software architecture design needs an authored, typed diagram with reusable node categories. Extending `WorkflowNodeType` would mix architecture components with process steps. Extending `ArchitectProjectSchema` would mix free architecture objects with repository-path comparison, whose contract only accepts analyzer node kinds.

## Proposal

Add a third full working mode, **Архитектура**, to the existing ORION Architect panel, alongside **Кодовая база** and **Процессы**. Keep the diagram model independently stored inside ORION DEV. It must not replace or reinterpret the repository map, project-intent comparison, or workflow graph. No standalone module or new project-view extension point is needed for the accepted scope.

Each authored node has a stable ID, `category`, `type`, title, description, optional metadata, position, and optional typed reference to a live ORION or repository entity. Category is a palette/filter grouping; type determines the node's meaning and rendering. Category is validated against the type so contradictory combinations cannot be saved.

## Initial software-architecture catalog

| Category | Types from the prototype | Purpose |
| --- | --- | --- |
| Software components | Service, API | Runtime services and public integration boundaries |
| Data and infrastructure | Storage, Channel, Process | Databases/files, queues/streams and operating-system processes |
| People and AI | Human, AI agent, Model, IDE, Tool | Owners, model providers, workspaces and execution tools |
| Flow and decisions | Phase, Decision, Verdict | Lifecycle stages, branches and explicit outcomes |
| Controls and evidence | Contract, Evidence, Lock, Fault | Policies, observed proof, exclusive constraints and observed breaks |
| Structure | Group / Contour | Visual boundary that contains related nodes and can move with them |

The palette presents categories first and types within them; search and recently used types keep the full catalog navigable. Labels and icons come from a typed registry, not arbitrary user-supplied CSS or markup. The catalog can later add module/package/external-system types through a reviewed contract update.

## Diagram behavior

- Node cards use the prototype's hierarchy: type/category marker, readable title, short description, and compact metadata footer.
- Typed edges may carry a label and a relation kind; the inspector lists incoming and outgoing neighbors and can remove a relation directly.
- Context-click adds a node at the pointer or opens actions for the selected node. Undo/redo covers node, edge, and layout edits.
- Fit-to-content, zoom percentage, pan/zoom controls, optional minimap, and a layout reset are provided as canvas controls.
- Persist diagrams, node types, relations, positions and viewport in ORION DEV's workspace-scoped storage. Prototype `localStorage` is not a persistence contract.
- A typed reference points to the source entity; it never copies source data or grants access. Missing/inaccessible references render as safe placeholders.

## Boundaries and migration

- Keep the existing workflow schema and endpoints unchanged; its five node types describe process execution.
- Keep `ArchitectProjectSchema` path-based and compatible with map comparison. A diagram node may reference a repository path, but the authored diagram is stored separately.
- Keep diagram entities in ORION DEV / Architect; do not add them to Core or Projects Base.
- Add a separate workspace-scoped table and public shared-types contract. Existing workflow and project-schema JSON remain readable and unchanged.
- Agent access uses the existing Agent Gateway, module permissions, token modes, audit, and proposal behavior. A repository reference stores only a registered repository ID and relative path; it grants no source read/write access by itself.

## Acceptance criteria for a first implementation

1. A user can create a software-architecture diagram and add nodes from every initial category/type above.
2. Category filtering, type search, node editing, grouping and labeled relations work with keyboard-accessible controls.
3. Undo/redo restores both content and positions; save/reopen round-trips the diagram without loss.
4. A reference node does not expose inaccessible source names or data and does not change source permissions.
5. Existing workflow editing, repository maps and project-schema comparison pass their focused regression checks with this module disabled and enabled.
6. The new module and ORION DEV integration use public contracts only; default-enabled behavior and module-disabled behavior are both specified before implementation.

## Decision

The owner accepted the revised direction in the supplied task on 2026-11-18: implement the typed architecture designer as Architect's third mode, reuse the React Flow interaction language, and keep architecture, codebase, and workflow data models separate. This implementation is not authorization to create a standalone Canvas module or a project-view slot.
