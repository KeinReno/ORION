# ADR-0019 — Event API: transactional outbox в Postgres

Статус: **Принято (18.10.2026)**. Первый срез реализован (см. «Реализовано»). Спецификация — [platform-api/EVENTS.md](../platform-api/EVENTS.md); пробел — G3 в [PLATFORM_AUDIT.md](../PLATFORM_AUDIT.md).

## Задача
Модулям и плагинам нужен способ реагировать на изменения в других модулях без прямых обращений к чужим таблицам и сервисам.
Сегодня реакции — прямые вызовы (`tasks.service.ts` останавливает таймер через `tx.timeEntry`; продюсеры уведомлений вызывают
`NotificationCenterService.createTx`) и cron-опросы. Критерий G3: публикация в транзакции записи, подписчик из манифеста,
выключенный подписчик не ломает публикацию, повторная доставка идемпотентна, события не обходят RLS.

## Решение
Таблица outbox в той же PostgreSQL. `EventBus.publishTx(tx, event)` вставляет строку **в транзакции записи** (внутри
`PrismaService.withUser`). Диспетчер (`asSystem`, `FOR UPDATE SKIP LOCKED`) раскладывает события по подписчикам из манифестов
(`events.subscribes`), ведёт таблицу доставок с уникальностью `(eventId, subscriberId)`, повторяет с паузой, помечает исчерпавшие
попытки. Гарантия — at-least-once; потребитель идемпотентен по образцу `Notification.eventKey` (`createMany` с `skipDuplicates`).
Таблицы под RLS (`FORCE`), в реестре снапшота — `ephemeral-excluded`, в `SYNC_CLASSIFICATION` — `not-synced`.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| In-process `EventEmitter` (Nest `EventEmitter2`) | Событие теряется при падении процесса между коммитом и обработкой; публикация внутри транзакции даёт реакцию на ещё не закоммиченные данные (или на откатанные); нет повторов и учёта доставки. Подходит только для не критичных реакций. |
| Postgres `LISTEN/NOTIFY` | Уведомления не хранятся: подписчик, отключённый в момент NOTIFY, теряет событие; ограничен размер payload (8000 байт); нет повторов и статусов. Может быть добавлен позже только как «будильник» диспетчера поверх outbox — не как носитель. |
| Внешний брокер (Redis/NATS/Kafka/RabbitMQ) | Новый обязательный процесс противоречит установке «один `.exe` + встроенный Postgres» и локальному режиму; публикация в брокер вне транзакции БД требует всё равно outbox (dual write). Нагрузка ORION (личное пространство и малые команды) не оправдывает. Остаётся возможным потребителем outbox, если когда-либо понадобится. |
| Опрос таблиц доменных сущностей (как cron сейчас) | Каждый потребитель знает чужую схему — ровно то, от чего уходим (G4); нет единого контракта события. |

## Последствия
- Плюс: атомарность с записью, переживает перезапуск, работает на единственной БД, хорошо ложится на RLS и тесты.
- Плюс: паттерн уже знаком коду (`eventKey`, claim через `updateMany`, `FOR UPDATE` в `RecurringChecker`).
- Минус: задержка доставки равна периоду опроса диспетчера; порядок гарантирован только в пределах источника; рост таблицы
  требует чистки; каждый потребитель обязан быть идемпотентным.
- Требуется: миграция с RLS-политиками (структурный тест `api-rls.integration.test.ts` проверит), схемы событий в
  `packages/shared-types`, поле `events` манифеста станет рабочим, обновление `PLATFORM_API_VERSION` (MINOR).

## Реализовано (первый срез G3)
Таблицы `domain_events` / `domain_event_deliveries` с RLS; `DomainEventBus.publishTx` и подписчики (`apps/api/src/domain-events/`);
диспетчер (cron раз в 10 с, `asSystem`, `FOR UPDATE SKIP LOCKED`, повторы с паузой 30 с ×2, до 5 попыток, чистка через 7 дней);
каталог событий и объявленных подписок в `packages/shared-types/src/domain-events.ts` (из него выводятся `events.publishes/subscribes`
манифестов); издатель `tasks.task.closed` (`TasksService.update`) и первый подписчик — уведомление исполнителю задачи, закрытой
другим участником (`tasks/task-closed-notifier.ts`). `PLATFORM_API_VERSION` 1.1.0. Тест: `apps/api/test/domain-events.integration.test.ts`.
