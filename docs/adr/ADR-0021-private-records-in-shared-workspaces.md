# ADR-0021 — Личные записи внутри общих пространств

Статус: **принято владельцем 19.10.2026 (ответы на вопросы G21), первый срез реализован на заметках.** Пробел — G21 в [PLATFORM_AUDIT.md](../PLATFORM_AUDIT.md).

## Задача
В общем пространстве («Дом», команда) часть данных должна быть личной: остальные участники — и даже владелец пространства — её не видят. Остальное остаётся общим.

## Решения владельца
1. Способ пометки: возможны все три — **метка на записи**, **личная папка**, **отдельное личное пространство**. Личное пространство уже есть (ТЗ-05); в этом ADR — метка на записи; папки — позже, на документах.
2. Кто видит личное: **никто, кроме автора**. Администратор и владелец пространства — тоже нет.
3. Рабочие сессии (режим работы с одним набором данных) **пока не нужны**.
4. Синхронизация: личные записи синхронизируются **только на устройства автора**.

## Решение
Метка — nullable-колонка `privateToUserId` (внешний ключ на `users`, каскад) в таблице записей. Видимость обеспечивает база, а не код сервиса:

```sql
CREATE POLICY notes_private_owner ON "notes" AS RESTRICTIVE
  USING ("privateToUserId" IS NULL OR "privateToUserId" = current_setting('app.current_user_id', true))
  WITH CHECK (… то же …);
```

`RESTRICTIVE` складывается со всеми разрешающими политиками через И — ни членство, ни роль владельца, ни cross-workspace доступ чужую личную запись не открывают. Поэтому поиск, `[[ссылки]]`, ИИ-агенты (они работают с правами выдавшего), гибридная синхронизация и бэкап (читают через `withUser`) автоматически видят только своё. Роль `orion_system` (BYPASSRLS) видит всё — это нужно фоновым задачам (чистка корзины). `WITH CHECK` не даёт создать запись, личную для другого пользователя.

Правила переключения:
- Личной запись делается при создании (`isPrivate: true`). **Общую запись личной сделать нельзя** (409): у заметки нет поля «автор», и иначе участник мог бы спрятать чужую запись. Нужна копия — создайте новую личную.
- Личную можно **опубликовать** (`isPrivate: false`) — она становится общей для всех участников. Обратно нельзя.
- Флаг меняет только человек: синхронизация и агенты его не трогают.

Дочерние таблицы заметки (`note_revisions` — там лежит её текст, `note_attachments`, `note_links`) закрыты теми же RESTRICTIVE-политиками «строка видна, если видна родительская заметка» (миграция `20261019140000_private_notes_children`); без них история личной заметки читалась бы напрямую из базы. Связи `entity_links` раскрывают только id объекта, но не содержимое.

Побочные следствия, которые пришлось закрыть:
- Номер заметки (`N-104`) считается по `MAX` в пространстве; под ограничением RLS участник не видит чужие личные заметки и получил бы тот же номер. Функция `notes_assign_number` стала `SECURITY DEFINER` (утекают только номера, не содержимое).
- Резервная копия, сделанная владельцем, содержит его личные заметки (с `privateToUserId`) и не содержит чужих; восстановление требует, чтобы пользователь с этим id существовал на узле — то же условие, что у `TaskComment.userId`.
- Вики-ссылка из общей заметки на чужую личную остаётся «битой» для остальных (они не видят цель).

## Реализовано
Заметки: колонка и политика (миграция `20261019130000_private_notes`), `isPrivate` в схеме и сервисе, флажок «Личная — видна только вам» при создании, подпись и пункт меню «Сделать общей» в редакторе. Тест: `private-notes.integration.test.ts` (два пользователя в одном пространстве: списки, поиск, автодополнение ссылок, правка/удаление чужой, уровень БД, публикация, запрет «спрятать» общую, `orion_system`).

## Перед расширением на другие сущности (обязательный список)
Политика RLS закрывает всё, что читается от имени пользователя. Роль `orion_system` (BYPASSRLS) её обходит, поэтому каждый фоновый или токенный читатель сущности нужно проверить и исключить личные записи руками. Для заметок таких читателей нет. Для **задач** они есть, и пока они не исправлены, личные задачи делать нельзя:
- исходящий календарный фид по токену (`EventsService.feedByToken`, `asSystem`) включает задачи со сроком — личные нужно исключить;
- `DueTaskCheckerService` (крон, `asSystem`) шлёт напоминания исполнителю или владельцу и в Telegram пространства — для личной задачи адресатом может быть только автор, Telegram пропускать;
- уведомления о комментариях (`TaskCommentsService`, `asSystem`) — адресат только если он видит задачу;
- дочерние таблицы (`task_comments`, `task_activities`, `task_dependencies`, снимки `captures`) — те же политики «видна, если видна родитель», что у заметок;
- кросс-пространственные доступы (`SharedGrantsService`) и `HybridSyncService` проверить на ту же тему;
- подзадачи: общая подзадача под личной задачей остаётся видимой — решить правило (запретить или переносить приватность вниз).
Тот же порядок для списков, событий и документов: сначала перечень чтений от `orion_system`, потом политика, потом тест на двух пользователях.

## Не сделано
Остальные сущности (задачи, списки, события, привычки, документы и папки); подписи «Личная» в списке заметок; личные записи в гибридной синхронизации не проверялись на двух реальных устройствах; рабочие сессии (по решению владельца — позже).
