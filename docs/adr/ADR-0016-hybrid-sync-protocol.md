# ADR-0016 — Протокол гибридной синхронизации (локальные копии и двусторонняя запись)

Статус: **предложено владельцу; этапы 1–3 ТЗ-06 реализованы** (15 октября 2026) за режимом `hybrid` на пространстве, по умолчанию выключенным. Приёмка этапа 0 — «ADR принят владельцем»: до этого решения реализация остаётся прототипом за флагом. Источники: [TZ-06](../tz/TZ-06-hybrid-sync.md), [SYNC.md](../SYNC.md), `apps/api/src/sync/snapshot-registry.ts`.

## Контекст

Решение владельца 2026-10-15: целевая архитектура содержит **оба** режима — общий узел (онлайн-запись) и гибрид (локальная копия + очередь изменений). У пространства всегда один **авторитетный узел** (API + PostgreSQL), клиент — копия. Два узла не считают себя единственной правдой, WebDAV остаётся бэкапом и не транспортом.

## Решения

### 0. Режим на пространство
`Workspace.syncMode`: `local` · `shared` · `hybrid` (по умолчанию `shared` = поведение до этого ADR). Конечные точки синхронизации отвечают `409 sync_mode_not_hybrid`, пока владелец не включил `hybrid` (`PUT workspaces/:id/sync/mode`, только роль `owner`). Значения `local`/`shared` различаются политикой ТЗ-04/05 (кого пускать на узел); синхронизации они не включают. Модели с классом `strict` (деньги) в любом режиме пишутся только онлайн.

### 1. Инвентарь и классы
Источник — `SNAPSHOT_MODEL_REGISTRY`; классификация — `apps/api/src/sync/sync-classification.ts`, тест сверяет оба списка (новая модель без класса ломает тест).

| Класс | Что значит | Модели (кратко) |
|---|---|---|
| `mergeable-text` | автослияния нет, явный конфликт по `revision` | `Note` |
| `lww-fields` | last-writer-wins **по полю**, удаление — tombstone | `List`, `ListItem`, `Task` (этапы 2–3); остальное — `later` |
| `append-only` | только добавление, дубли гасит ключ | журналы, комментарии, показания |
| `strict` | деньги/остатки/уникальные инварианты — только онлайн | вся «Финансы», `InventoryMovement`, `TimeEntry`, `Document*` |
| `not-synced` | личность, секреты узла, эфемерное, здоровье (ADR-0012) | `User`, `AgentToken`, `Notification`, `Health*`… |

Реплицируются на устройство (чтение, этап 1): `List`, `ListItem`, `Note`, `Task` (неудалённые, не шаблонные заметки; корзина не едет). Писать офлайн: списки (этап 2), заметки и задачи (этап 3). Остальное — по решению владельца, отдельным ADR.

### 2. Идентификаторы, порядок, tombstone, идемпотентность

- **Идентификаторы.** Все предметные модели уже имеют `String @id @default(uuid())`. Новые сущности создаёт **клиент** (`crypto.randomUUID()`), узел принимает id клиента при `create` (повтор = no-op). Миграция идентификаторов не нужна.
- **Порядок.** Выбраны два механизма с разными задачами:
  1. **HLC** (hybrid logical clock) у каждой операции: строка `"<мс, 13 цифр>.<счётчик, 4 цифры>.<deviceId>"`, сравнивается лексикографически. Нужен только для **LWW-штампов полей**: правка, сделанная офлайн в 10:00, не должна побеждать онлайн-правку 10:05 лишь потому, что дошла позже. Устройство вливает в свои часы HLC, пришедшие с узла (правило receive), поэтому после первой синхронизации часы не отстают. Узел отвергает HLC дальше чем на 24 ч в будущем (`hlc_in_future`) — иначе устройство со сломанными часами «навсегда» выигрывало бы поля.
  2. **Серверная позиция в ленте изменений** (`sync_changes`, курсор) — только для доставки «что изменилось с вашего последнего визита». Порядок в ленте не влияет на результат слияния.
  Векторные часы отвергнуты: топология «звезда» с авторитетным узлом делает их избыточными (узел сериализует слияние). Чистый серверный счётчик без HLC отвергнут: офлайн-правка получала бы «время доставки», а не «время действия».
- **Лента изменений.** Триггеры БД на `lists`, `list_items`, `notes`, `tasks` пишут `(workspaceId, entityType, entityId, parentId, kind)` в `sync_changes` на **любую** запись — из REST, из sync-push, из крона, из восстановления бэкапа. Лента хранит *что тронуто*, а не значения; `pull` читает **текущее** состояние строк. Следствия: доставка идемпотентна и сходится независимо от порядка/дублей; изменения, сделанные онлайн-пользователями через обычный REST, доходят до гибридных клиентов без правки каждого сервиса.
- **Курсор.** Записи ленты получают `xid = pg_current_xact_id()`; `pull` возвращает только записи с `xid < xmin(pg_current_snapshot())` (все более ранние транзакции завершены) в порядке `(xid, id)`; курсор — последняя пара. Это закрывает классическую потерю записи, когда транзакция с меньшим `id` фиксируется позже.
- **Tombstone.** Удаление = запись `kind='delete'` в ленте (триггер на DELETE); пока она хранится, поздняя правка/создание дочернего элемента удалённого объекта определяется как «объект удалён». Срок хранения ленты и штампов — **90 дней** (`SYNC_LOG_RETENTION_DAYS`); устройство, чей курсор старее, получает `410 resync_required` и обязано загрузить снимок заново (неотправленные операции при этом **сохраняются** в очереди и переигрываются поверх нового снимка; операции над объектами, удалёнными за пределом срока, получают исход `entity_gone`).
- **Идемпотентность.** Операция имеет `opId` (UUID) и `deviceSeq` (счётчик устройства). Узел хранит исходы (`sync_ops`, `UNIQUE(workspaceId, opId)`); повтор с тем же телом возвращает прежний исход (`duplicate`), с другим телом — `op_id_reuse`. `UNIQUE(deviceId, deviceSeq)` ловит **откат устройства из бэкапа**: устройство, восстановившее старое состояние, заново выдаёт уже использованные `deviceSeq` с другими `opId` → `device_rolled_back`; клиент обязан сменить `deviceId`, загрузить снимок и сохранить свои неотправленные изменения как новые операции.
- **Формат журнала.** Операция (контракт — `shared-types/src/sync.ts`):
  `{ opId, deviceId, deviceSeq, hlc, entity: list|listItem|note|task, entityId, parentId?, kind: create|patch|delete, fields?, expectedRevision? }`.
  Узел хранит принятую операцию и её исход; ответ — `results[]` по каждой операции. Применение заметок и задач идёт через `NotesService.updateTx/createTx` и `TasksService.updateTx/createTx` — те же ссылки, журнал `TaskActivity`, повторы и таймеры, что у REST; список полей, доступных офлайн, ограничен (`hybrid-sync.ts`: заголовок/текст/теги/закрепление/архив/дата у заметки; название/описание/статус/приоритет/сроки/оценка/порядок у задачи — проекты, исполнители, зависимости, повторы только онлайн).

### 3. Политики слияния (применяет только авторитетный узел)

| Тип | Правило |
|---|---|
| Списки/пункты (LWW) | Каждое поле имеет штамп HLC (`sync_entity_stamps`). Поле принимается, если HLC операции **больше** штампа; иначе исход `superseded`/`merged` с победившими значениями для устройства. Поле без штампа (его писал обычный REST) сравнивается с `updatedAt` строки; при создании и при первой sync-записи штампуются **все** синхронизируемые поля (без штампа поле «замораживается» на прежнем `updatedAt`), а любая запись мимо sync (триггер ленты: сессия без `app.sync_apply`) снимает штампы изменённых ею полей — правка, сделанная до последней записи по полю, не затирает её. Отметка `checked` — обычное поле; «двое отметили» = одно значение, конфликта нет; «отметил/снял» решает HLC. `checkedBy/At` выставляет узел. Порядок — поле `sortOrder` (LWW), равенство разрешает `(sortOrder, createdAt, id)` при показе. |
| Удаление vs правка | **Удаление побеждает** конкурирующую правку/создание дочернего элемента: правка получает исход `conflict: entity_deleted`, устройство видит это и может создать пункт заново (новый id). Восстановление «Отменить» после синхронизации — новое создание. Удаление идемпотентно. |
| Задачи (этап 3) | LWW по полю как у списков; поля `status`, `completedAt`, `recurrence` и журнал `TaskActivity` порождает узел. `revision` растёт на узле при каждой применённой операции; клиентский `expectedRevision` не обязателен, но если указан и не совпал — исход `conflict: revision` (как `task_revision_conflict`). |
| Заметки (этап 3) | **Без слияния.** Удаление заметки — перенос в корзину (восстановление и очистка корзины — онлайн). Операция `patch` обязана нести `expectedRevision` (клиентский движок проставляет её сам: ревизия основы + число своих правок этой заметки впереди в очереди); несовпадение → `conflict: revision` с текущей версией узла; изменение остаётся в очереди в состоянии `conflict`, пока человек не выберет «загрузить версию узла» или «сохранить мою поверх» (переотправка с новой `expectedRevision`). Версии (`NoteRevision`) пишет узел. |
| Финансы | Офлайн-записи **нет** (класс `strict`). Если владелец позже решит иначе — отдельный ADR: резервирование диапазона идентификаторов + ключ дедупа вроде `importedRef`. |

### 4. Файлы и блобы
В этапах 1–3 блобы **не** реплицируются (`Document*` — `strict`). Целевая схема для следующего решения: передача по sha256 (`BlobBackupService` уже считает хэш по прочитанным байтам), докачка `Range`, лимит устройства (по умолчанию 500 МиБ, настраивается), вложения заметок на устройство не качаются без явного выбора. Вложения заметок в копии показываются как «файл на узле».

### 5. Безопасность
- **Канал:** TLS и доверенное устройство — ТЗ-04. Этот ADR не вводит собственного транспорта; все вызовы идут через `ApiClient` с JWT.
- **Права проверяются на узле при приёме каждой операции**: членство в пространстве (`assertMemberTx`), включённость модуля (`@RequireModule`-эквивалент), RLS, режим `hybrid`, зарегистрированное и не отозванное устройство (`sync_devices`). Ссылочные поля (`parentId`) перепроверяются по этому же пространству. Клиентскому состоянию узел не доверяет: на `pull` отдаётся только то, что видит пользователь под RLS.
- **Подпись операций устройством (Ed25519)** — *описана, не реализована*: при TLS и JWT она защищает только от враждебного ретранслятора; вводится вместе с ретрансляцией (этап 4). Сейчас операция аутентифицируется JWT пользователя + зарегистрированным `deviceId`.
- **Повреждённое/враждебное удалённое состояние:** клиент валидирует каждый ответ узла zod-схемой, отбрасывает неизвестные типы сущностей, не принимает курсор, который не больше предыдущего, и при ошибке валидации не портит локальную копию (остаётся прежняя + статус `error`).
- **Ограничения, фиксируем как есть:**
  1. **Отзыв доступа не отзывает уже скачанное.** При следующем подключении клиент получает 403/404 и **удаляет копию**, но то, что успело быть скачано до отзыва (и любая копия файла IndexedDB, сделанная до удаления), остаётся у владельца устройства.
  2. Локальная копия хранится **в открытом виде** в IndexedDB профиля браузера/WebView; защита — шифрование диска ОС. Шифрование копии ключом устройства — отдельная работа.
  3. Устройство со сломанными часами проигрывает/выигрывает LWW-поля в пределах окна 24 ч — ограничено проверкой `hlc_in_future`, но не устраняется.

### 6. Версии протокола и схемы
`SYNC_PROTOCOL_VERSION = 1` передаётся в каждом запросе (`protocol` в теле/параметре) и в ответе снимка. Узел отвечает `426 protocol_unsupported` с `{ supported: [1] }` при несовпадении мажорной версии; клиент в этом случае не пытается писать и показывает «обновите приложение». Новые поля в операциях — только аддитивно и опционально; удаление/смена смысла поля — новая версия протокола. Состав сущностей снимка версионируется: неизвестную сущность старый клиент игнорирует. Схема Prisma не должна ломать старый клиент: DTO строятся вручную (`toDto`) — набор полей сущности в снимке меняется только добавлением.

### 7. Хранение копии на клиенте
Выбран **документный слой на клиенте** (IndexedDB в браузере/Tauri WebView; интерфейс `ReplicaStorage` в `@orion/core`, реализация — `apps/web/lib/replica-idb.ts`), а не локальная PostgreSQL и не локальный API-узел. Причины: клиентский режим ТЗ-04 не запускает у клиента ни API, ни PostgreSQL; копия — четыре типа сущностей без SQL-запросов; RLS и роли на клиенте не нужны (авторитет — узел). Отвергнуто: «локальный узел с собственной БД на каждом устройстве» — он порождает вторую «единственную правду».

### 8. Состояния для UI и агентов
Каждая запись/операция показывается в одном из четырёх состояний:
`local` (сохранено на устройстве, ещё не отправлялось) → `queued` (отправка начата/ждёт повтора) → `synced` (**только после подтверждения узла**, исход `applied|merged|duplicate`) · `conflict` (узел вернул `conflict`/`superseded` и нужно решение человека или принято решение «узел победил»). «Синхронизировано» не показывается без подтверждения узла. Агенты (ADR-0007) работают напрямую с узлом и видят только его состояние.

## Этап 4 (только описание, не начинать без решения владельца)
Синхронизация через интернет требует: публичного HTTPS-узла и сертификата (ТЗ-04 даёт LAN), подписи операций устройством и привязки устройств к пользователю, ограничения скорости на пользователя/устройство, relay для уведомлений и чата (мгновенный чат в чисто-локальном режиме невозможен), мобильного клиента с собственным `ReplicaStorage` (SQLite/IndexedDB) и политики фонового опроса. Отдельные ADR на каждый пункт.

## Что не делается (по ТЗ)
Переписывание `SnapshotService`; массовые колонки `*version/deletedAt` в моделях; WebDAV как транспорт; показ «синхронизировано» без подтверждения. Новые таблицы (`sync_*`) добавлены в реестр снапшота как `ephemeral-excluded`: лента, штампы, исходы операций и устройства — состояние узла, не данные пространства.
