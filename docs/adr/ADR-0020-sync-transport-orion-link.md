# ADR-0020 — SyncTransport для Orion Link (пакетный транспорт под Hybrid Sync)

Статус: **предложено владельцу; кода нет.** Источники: [ORION_LINK_ARCHITECTURE.md](../ORION_LINK_ARCHITECTURE.md), [ADR-0016](ADR-0016-hybrid-sync-protocol.md), [ADR-0015](ADR-0015-lan-host-client.md), [SYNC.md](../SYNC.md). Состояние базы на момент написания — раздел «Проверка базы».

## Контекст

Orion Link — не новый sync engine. Движок один: Hybrid Sync (ADR-0016) — HLC-штампы, `SyncOp`, `opId`/`deviceSeq`, авторитетный узел (API + PostgreSQL), клиентская копия `ReplicaEngine`. Нужен способ доставлять те же операции, когда прямого HTTPS до узла нет: через WebDAV, S3, позднее собственный сервер.

В коде **уже есть** интерфейс `SyncTransport` (`packages/core/src/sync/replica-types.ts`): `registerDevice / snapshot / pull / push` — это запрос-ответ клиента к *онлайн* узлу. Облачное хранилище так работать не умеет (оно не применяет операции и не отвечает). Поэтому нужны два разных уровня, а не один раздутый интерфейс.

## Решения

### 1. Два уровня, топология «звезда» сохраняется
- **`NodeTransport`** — нынешний `SyncTransport` (переименование отдельным коммитом, поведение не меняется): синхронный обмен клиента с узлом. Реализации: `apiSyncTransport` (LAN/HTTPS), позднее Orion Server.
- **`PacketTransport`** (новый, этот ADR) — асинхронная доставка зашифрованных непрозрачных пакетов между устройством и узлом через «почтовый ящик». Знает только байты и имена, ничего о списках/заметках/задачах (никаких `syncNotes`).
- Мост: на стороне клиента `RelayNodeTransport` реализует `NodeTransport` поверх `PacketTransport` (push — запись пакета, pull — чтение пакетов от узла), на стороне узла `RelayIngress` читает входящие пакеты и вызывает **те же** `HybridSyncService.push/pull`. Правила слияния, RLS, права, идемпотентность не дублируются. Авторитет по-прежнему один — узел; без его онлайна ничего не применяется.

### 2. Контракт PacketTransport
```ts
interface PacketTransport {
  readonly kind: "lan" | "webdav" | "s3" | "orion-server";
  probe(): Promise<{ ok: boolean; latencyMs?: number; reason?: string }>;
  put(box: BoxId, name: string, bytes: Uint8Array): Promise<void>;   // write-once, существующее имя → ошибка/no-op при тех же байтах
  list(box: BoxId, after?: string): Promise<string[]>;               // имена по возрастанию
  get(box: BoxId, name: string): Promise<Uint8Array | null>;
  remove(box: BoxId, name: string): Promise<void>;                   // только очистка уже подтверждённого
}
```
Требования к адаптеру намеренно минимальны: **никаких ETag/conditional write/rename/lock** — иначе нельзя гарантировать работу у произвольного WebDAV (Mail.ru и др. — кандидаты, не гарантии). Единственная «сильная» операция — создание нового имени; перезапись существующего не используется.

### 3. Раскладка ящика (WebDAV/S3 одинаково)
```
orion-link/v1/<workspaceId>/<epoch>/
  up/<deviceId>/<deviceSeq,12 цифр>.pkt     # устройство → узел (пишет только своё устройство)
  down/<deviceId>/<n,12 цифр>.pkt           # узел → устройство (пишет только узел)
  ack/<deviceId>.<kind>.<n>                 # подтверждения применения (малые файлы-метки)
```
Один писатель на каталог ⇒ гонок записи нет, конфликты имён невозможны. `deviceSeq` уже монотонен и защищён `UNIQUE(deviceId, deviceSeq)` (ADR-0016 §2).

### 4. Пакет
Заголовок (открытый, входит в AAD шифрования): `protocolVersion`, `linkVersion`, `workspaceId`, `epoch`, `sourceDeviceId`, `batchId`, `seq`, `kind` (`ops` | `pull-result` | `snapshot-chunk`), `opIds[]` (только для `ops`), `cursorFrom/cursorTo` (для `pull-result`), `keyId`, `createdAt`. Тело — AES-256-GCM(JSON из тех же zod-схем: `PushSyncOpsInput` / `ReplicaPull` / `ReplicaSnapshot`), размер пакета ≤ 1 МиБ (снимок режется на куски с `index/total` и sha256 каждого). Целостность: GCM-тег + проверка заголовка = AAD; получатель отбрасывает пакет с неверным тегом (`corrupt`, в журнал, **не** портит копию), с чужим `workspaceId`/`epoch`, с неизвестной мажорной `protocolVersion` (остаётся лежать, UI «обновите приложение»).

### 5. Ключи
Отдельная модель, **не** `SYNC_SECRET` (тот — ключ узла для бэкапов и паролей удалёнок). Ключ рабочего пространства для Link `K_ws` (32 случайных байта) создаёт узел; новое устройство получает его при спаривании по доверенному каналу (LAN-pairing ADR-0015; затем — обмен X25519 + подтверждение кодом). `K_ws` хранится на устройстве вне облака, пароль провайдера — отдельно. Ротация = новый `keyId`, пакеты старого `keyId` читаются до очистки; отзыв устройства = ротация (уже скачанное отозвать нельзя — те же ограничения, что ADR-0016 §5). Подпись пакетов Ed25519 откладывается как в ADR-0016 (в облаке подписанные и шифрованные пакеты — закрывает подмену записью чужого участника); в прототипе — один владелец, одно пространство.

### 6. «Доставлено» ≠ «применено»
Состояния операции для UI: `local → uploaded (пакет записан в ящик, подтверждено put) → synced (узел записал ack: applied|merged|duplicate)`. Слово «синхронизировано» показывается только после `ack` от узла. `uploaded` показывается как «ожидает узел». Узел публикует результаты в `down/` пакетом `pull-result`, клиент применяет их тем же кодом, что и ответ `pull`.

### 7. Один активный транспорт, `epoch`, ручное переключение
- На пространство — ровно один активный облачный `PacketTransport` (настройка владельца) и **один** `epoch` (целое). LAN как прямой путь на `NodeTransport` может работать параллельно: он идёт через тот же узел и те же `opId`, дубли гасит идемпотентность.
- Переключение провайдера (ручное): 1) узел дочитывает `up/` старого ящика до пустого и ждёт ack; 2) `epoch += 1`, узел записывает метку `EPOCH` в новом ящике; 3) устройства при следующем `probe` видят новый эпоха/провайдера и переключаются; пакеты со старым `epoch` игнорируются. Две «живые» истории невозможны, потому что применять умеет только узел, а он принимает один эпоха.
- **Автоматического failover нет.** Приёмка для него — отдельный ADR после тестов split-brain.

### 8. Ошибки и восстановление
Повтор `put` безопасен (то же имя + те же байты). Частичная загрузка: пакет считается существующим только после успешного `put` целиком; адаптеры WebDAV/S3 пишут во временное имя и выполняют одно финальное `put` под настоящим именем только если провайдер даёт атомарность — иначе клиент проверяет размер/тег при чтении и отбрасывает усечённый файл (повторит позже). Курсор ниже окна хранения → `resync_required` (ADR-0016 §2): узел публикует `snapshot-chunk`. Очередь операций на устройстве переживает рестарт (уже так). Очистка: узел удаляет `up/` пакеты после ack, `down/` — после подтверждения чтения устройством, TTL 30 дней.

### 9. Что не меняется
Модели, правила слияния, классы синхронизации, `SNAPSHOT_MODEL_REGISTRY`, резервные копии (отдельный путь, `SYNC.md`). Backup и Link разные функции с разными гарантиями.

## Чего этот ADR не решает (честно)
- Шифрование локальной копии IndexedDB ключом устройства — отдельная работа; пока копия в открытом виде.
- Реальное поведение Mail.ru/Яндекс WebDAV: ограничения частоты, квоты, доступность из РФ, поведение при больших каталогах (`list`) — нужны замеры; адаптер WebDAV остаётся «кандидатом».
- Интерактивные команды/агенты через облачный ящик — не поддерживаются (задержки), см. AGENT_HUB_ARCHITECTURE.
- Собственный сервер: тот же протокол, `orion-server` как третья реализация `PacketTransport`/`NodeTransport`; миграция очереди — отдельный ADR.

## Проверка базы (18–19.10.2026, commit 836c023, рабочее дерево с чужими незакоммиченными правками)
- `vitest` по `packages/core/src/sync`, `apps/api/src/sync`, `packages/shared-types`: 42 файла / 401 тест — зелёные (в т.ч. `convergence.fuzz`, `replica-engine`, `replica-notes-tasks`, `sync-classification`).
- Не проверялось в этой сессии: интеграционные тесты на PostgreSQL (`hybrid-sync.integration`), CI на чистой БД, LAN между двумя физическими ПК, backup/restore на независимых узлах — остаются пунктами «базы» перед прототипом.

## План прототипа (следующий шаг, после принятия)
1. `PacketTransport` + in-memory и WebDAV-адаптер (`packages/core`, WebDAV-реализация на узле/клиенте Tauri-web через API-прокси, т.к. CORS).
2. Пакетный кодек (AES-GCM, заголовок как AAD) + тесты: повреждённый пакет, повтор, рестарт, чужой epoch.
3. `RelayNodeTransport` / `RelayIngress`, только `list`/`listItem`; тест сходимости двух экземпляров через in-memory-ящик, затем интеграционный на реальном WebDAV-стабе.
