
## Статус прототипа (19.10.2026) — `packages/core/src/link/`
Сделано: `PacketTransport` (+ `MemoryPacketTransport` с отказами/усечением/порчей), кодек пакета (AES-256-GCM, заголовок = AAD, ротация `keyId`), `RelayNodeTransport` / `RelayIngress`. 10 тестов: шифрование и подмена заголовка, чужой ключ/эпоха, усечение; два устройства сходятся через ящик без открытого текста; узел офлайн; потерянный ответ (повтор → `duplicate`); порча ответа; сбой ящика; отзыв 403; чужая эпоха.

Отличия от текста выше (уточнения, найденные при реализации):
- `PacketTransport` путевой: `put(path)/list(dir)/get/remove`, а не `BoxId`; `put` на занятое имя возвращает `false`.
- Вместо `pull-result` пакетов — запрос/ответ с общим `seq`: `up/<dev>/<n>.pkt` → `down/<dev>/<n>.pkt`. `ReplicaEngine` не менялся: он видит обычный `SyncTransport`; потеря ответа = сетевая ошибка → очередь и безопасный повтор.
- Идентификатор Link-устройства (`deviceId` в путях) задаёт спаривание и отличается от `deviceId` движка Hybrid Sync.

Не сделано: WebDAV-адаптер (замеры у провайдеров), заметки/задачи в тестах Link (движок их уже умеет), `snapshot-chunk` для снимков >1 МиБ, очистка по TTL, интеграция в API-узел (`RelayIngress` над `HybridSyncService`), спаривание и хранение `K_ws`, подпись Ed25519. Код нигде не подключён к приложению.

## Статус реализации (19.10.2026, ветка `feat/orion-link`)
Сверх прототипа выше сделано:
- **Узел (API):** миграция `link_devices` / `link_keys` с RLS; `LinkService` (спаривание, отзыв, поиск пользователя по устройству, ключи); эндпоинты `workspaces/:id/link/devices`; фоновый `LinkIngressService` (раз в 10 с, `runJob`) поверх `HybridSyncService` и WebDAV-удалёнки пространства (каталог `orion-link/`). Сквозной интеграционный тест на PostgreSQL: клиентский движок → зашифрованный ящик → применение в БД → отзыв (403).
- **Ящик:** ответ больше 512 КиБ режется на части `<n>.cNNNN.pkt` + манифест (sha256) последним; клиент собирает, порча одной части → повторный опрос; клиент оставляет в ящике 20 последних ответов.
- **Клиент устройства:** `WebdavFetchTransport` (чистый `fetch`: PUT с `If-None-Match`, MKCOL, PROPFIND Depth:1, DELETE) проверен против настоящего HTTP-сервера, включая создание `baseDir` и неверный пароль; `createLinkTransport(pairing, webdav)` собирает транспорт для `ReplicaEngine`.
- **Заметки и задачи** идут через ящик тем же кодом (конфликт заметки по `revision` виден проигравшему).

Известные пробелы: нет UI «Подключить устройство» и защищённого хранения ключа на устройстве; запросы клиента (push) не режутся на части; прямой `fetch` из браузера упирается в CORS провайдера; поведение Mail.ru/Яндекс WebDAV (листинг, лимиты частоты, `If-None-Match`) не измерено; ротация ключа и переключение `epoch` — только в модели данных, без операции; подпись Ed25519 не реализована; автоматического failover нет.
