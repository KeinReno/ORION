# ADR-0001 — Модуль «Схемы» (Canvases): карта мыслей и карта связей

Статус: **предложено, не принято** (требует решения владельца). Дата: 2026-10-10.
Источник требования: `FRONTEND_WORKSPACE_SPEC.md` §4 (UI-09). До принятия этого ADR кода модуля нет и **не должно быть**: ни сущностей Canvas в Core, ни правок внутри Projects Base.

## Контекст

Владелец согласовал визуальную работу «карта мыслей» и «карта связей». Её ценность — связь с **живыми сущностями ORION**, а не отдельная рисовалка. Нужно решить, кто владеет схемой, как проект получает вид «Карта» и какие права действуют на связанные объекты.

## Решение (предлагаемое)

1. **Владение.** Отдельный отключаемый доменный модуль `canvases` («Схемы») владеет схемой, узлами и рёбрами. Он подчиняется общему модульному контракту (`@RequireModule("canvases")`, строка в `MODULE_CATALOG`, выключение не удаляет данные, RLS, бэкап через `snapshot-registry`).
2. **Узел — ссылка, не копия.** Узел бывает свободным текстовым или ссылкой на существующий объект `(type, workspaceId, objectId)`. Данные объекта не копируются: показывается живое название при наличии доступа.
3. **Права.** Недоступный или удалённый объект показывается безопасным placeholder **без названия и подробностей**. Наличие схемы, ссылки или гранта **не расширяет** права автоматически: доступ к узлу проверяется так же, как к самому объекту (тот же `assertMember`/RLS, что у владельца сущности).
4. **«Превратить узел в задачу/заметку».** Это явная операция через API владельца сущности (`TasksService`/`NotesService`), с выбором пространства/проекта и идемпотентным результатом (ключ идемпотентности — id узла; повторное нажатие возвращает уже созданный объект и не плодит копии).
5. **Проект получает вид «Карта» через публичный контракт**, а не правкой `ProjectWorkspacePanel` (см. Extension Proposal ниже и ADR-0003 про идентичность панели).
6. **Первая поставка:** свободный текстовый узел; узел-ссылка; иерархическая и смысловая связь; ограниченный набор фигур и цветов; zoom/pan, fit-to-content, auto-layout; самостоятельная dock-панель и отдельное окно; сохранение положения узлов, масштаба и ревизии. **Позже:** блок-схемы процессов, экспорт изображения/PDF (только после надёжного сохранения и восстановления), свободное рисование, совместные курсоры, презентационный режим.

## Модель данных (набросок для обсуждения)

| Таблица | Поля |
|---|---|
| `canvases` | `id`, `workspaceId`, `projectId?`, `title`, `viewport` (JSON: x, y, zoom), `revision`, `createdAt/updatedAt/archivedAt` |
| `canvas_nodes` | `id`, `workspaceId`, `canvasId`, `kind` (`text`/`link`), `text`, `linkType?`, `linkObjectId?`, `x`, `y`, `w`, `h`, `shape`, `color` |
| `canvas_edges` | `id`, `workspaceId`, `canvasId`, `fromNodeId`, `toNodeId`, `kind` (`hierarchy`/`relation`), `label?` |

Все три несут `workspaceId` + `ENABLE/FORCE ROW LEVEL SECURITY` и попадают в `SNAPSHOT_MODEL_REGISTRY`. Сохранение — с проверкой ревизии (как у заметок), чтобы два окна не затирали друг друга.

## Extension Proposal

```text
Requested extension point:
projects.views (регистрация дополнительного вида проекта)

Plugin/module:
canvases

Reason:
Проект должен показывать вид «Карта», не зная о модуле схем, а модуль схем
не должен править ProjectWorkspacePanel.

Existing points considered:
- PanelDefinition.instanced + navParent (панель-экземпляр проекта)
- ручные вкладки ProjectTab внутри ProjectWorkspacePanel

Why insufficient:
Вкладки проекта жёстко перечислены в коде (ProjectTab); нового вида без
правки Base добавить нельзя. Нужен типизированный контракт:
{ id, label, icon, moduleId, component(projectId) }.
```

## Последствия

- Плюсы: ownership остаётся чистым; выключение модуля прячет вид и не трогает данные; права не размываются.
- Цена: нужен универсальный точечный контракт `projects.views` — это изменение Base, оформляемое отдельным решением до кода (см. ADR-0003).
- Риск: поиск и добавление существующей сущности в схему требует проверки доступа на каждом узле — это самая дорогая часть, закладывать время на тесты RLS.

## Открытые вопросы владельцу

1. Принимать ли отдельный модуль `canvases` (а не плагин внутри Projects)?
2. Нужна ли схема вне проекта (на уровне пространства)? Модель выше допускает `projectId = null`.
3. Нужно ли в первой поставке «Превратить узел в задачу» или достаточно ссылок на существующие объекты?
