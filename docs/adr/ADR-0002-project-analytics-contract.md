# ADR-0002 — Аналитика проекта: контракт данных и условия показа

Статус: **предложено, не принято**. Дата: 2026-10-10. Источник: `FRONTEND_WORKSPACE_SPEC.md` §3 «Проекты», аналитика второго этапа (UI-07).
Код аналитики **не пишется**, пока не принят этот контракт: сегодня у ORION нет истории, на которой её можно честно построить.

## Проблема

Спецификация требует исторический график «объём работ / начато / завершено», план против факта по времени и бюджету, прогноз срока — и запрещает рисовать ложный график при пустой истории. Сейчас в БД есть только **текущее состояние** задач (`status`, `completedAt`, `createdAt`) и журнал `TaskActivity` по трём полям (статус, исполнитель, срок). Этого недостаточно по двум причинам:

1. **Объём работ меняется незаметно.** Удалённая задача исчезает вместе со следом, а значит «scope» в прошлом восстановить нельзя.
2. **Статус по дням не реконструируется надёжно:** `TaskActivity` не покрывает все пути изменения (например, массовые операции, восстановление из бэкапа).

## Решение (предлагаемое)

**Ежедневный снимок вместо реконструкции.** Таблица `project_daily_stats`, одна строка на проект и **локальный день пространства**:

| Поле | Смысл |
|---|---|
| `workspaceId`, `projectId`, `day` (DATE) | ключ `(projectId, day)` — уникальный |
| `scope` | сколько задач в проекте на конец дня |
| `started` | сколько в статусе «в работе» или завершено на конец дня |
| `done` | сколько закрыто (`isTaskClosed`) на конец дня |
| `plannedMinutes` | сумма оценок открытых и закрытых задач (если есть) |
| `trackedMinutes` | учтённое время на конец дня (если включён Time) |
| `spentAmount` | потрачено на конец дня (если включены Finance) |

Запись — идемпотентный `@Cron` ночью через `asSystem` (паттерн из `RecurringCheckerService`: барьер в БД — уникальный индекс, `INSERT … ON CONFLICT DO UPDATE`). Первый снимок создаётся при первом открытии аналитики или при создании проекта, чтобы история начиналась сразу. RLS и включение в `SNAPSHOT_MODEL_REGISTRY` обязательны, как у любой таблицы с `workspaceId`.

## Условия показа (когда график вообще рисуется)

| Элемент | Условие | Иначе |
|---|---|---|
| График «scope / начато / завершено» | ≥ 7 дней истории **и** ≥ 2 различных значения | Текст «Истории пока мало: график появится через N дн.» |
| Изменение объёма | любое изменение `scope` между днями | Линия scope рисуется ступенькой и подписывается (рост — заметен) |
| План против факта по времени | включён Time **и** `plannedMinutes > 0` | Блок скрыт, а не нулевой |
| План против факта по бюджету | включён Finance **и** задан бюджет | Блок скрыт |
| Прогноз срока | ≥ 14 дней истории **и** ≥ 5 закрытых задач **и** скорость закрытия не нулевая | Прогноз не показывается; вместо него — «Недостаточно данных для прогноза» |

Прогноз — это **оценка**, подписанная как оценка («при текущей скорости около …») с диапазоном, а не точная дата; он не заменяет и не перекрывает отчёт автора (`reportedHealth`). Внешние слои Time и Finance подключаются через типизированные слоты и не импортируются напрямую (см. `AI_FIRST_EXTENSION_ARCHITECTURE.md`).

## Не входит (позднее, опционально)

Baseline, критический путь, загрузка команды. Семейный проект (например, поездка) не должен превращаться в обязательную ERP-форму: вся аналитика — отдельный отключаемый раздел.

## Последствия и риски

- Плюс: честная история с первого дня после включения; нет дорогой реконструкции.
- Минус: **прошлого до включения не будет** — задним числом график не построить. Это нужно говорить пользователю явно.
- Риск: граница «дня» (часовой пояс пространства) — взять тот же источник, что у привычек (`habitLocalDayKey`-подход), и не смешивать UTC и локальный день.
- Тесты: идемпотентность снимка, граница суток, поведение при выключенных Time/Finance, восстановление из бэкапа.

## Открытые вопросы владельцу

1. Устраивает ли «история начинается с момента включения» (без восстановления прошлого)?
2. Хранить ли снимки бессрочно или обрезать до N месяцев?
3. Показывать аналитику по умолчанию или только по явному включению?
