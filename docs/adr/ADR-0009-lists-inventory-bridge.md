# ADR-0009 — Мост «Покупки → Склад» (lists-inventory) и слоты `lists.item` / `inventory.item.actions`

Статус: **принято для первой версии, реализовано** (14 октября 2026). Источник: `PRODUCT_DIRECTION.md` — полный цикл `список покупок → покупка → имущество → операция`; `ROADMAP.md` §3 «полезные цепочки… списков/имущества».

## Контекст

«Списки» и «Склад» — независимые модули. Пользователь ведёт список покупок, покупает, а остаток на складе вносит отдельно руками; позиция с низким остатком не попадает в список сама. Связь нужна без того, чтобы «Списки» знали о «Складе» (Конституция п. 5–6), без копирования данных и с сохранением регистра движений как единственного источника остатка.

## Решение

1. **Плагин-мост `lists-inventory`** («Покупки → Склад»), `extendsModuleId: "lists"`, `defaultEnabled: true`. Работает, только когда включены и «Списки», и «Склад»: сервер отвечает 409 (`@RequireModule("lists")` + `@RequirePlugin("lists-inventory")` + `ModulesService.assertEnabledTx(..., "inventory")`), клиент прячет свои части.
2. **Данные — три колонки на `list_items`, без новой таблицы:** `inventoryItemId` (FK, `SetNull`), `quantity` (> 0, по умолчанию 1), `stockedMovementId` (FK на `inventory_movements`, `unique`, `SetNull`). RLS не меняется. В снапшоте `listItems` восстанавливаются после `inventoryMovements`.
3. **«Куплено»** (`POST …/lists-inventory/lists/:listId/items/:itemId/purchase`) в одной транзакции блокирует строку пункта (`FOR UPDATE`), пишет обычный приход через `InventoryService.recordMovementTx` (та же блокировка позиции и логика низкого остатка) и запоминает его в `stockedMovementId`. Повторная отметка, гонка двух окон и «снять отметку → отметить снова» второй приход не создают. Снятие отметки приход не откатывает: исправление остатка — явная корректировка.
4. **«В список покупок»** (`POST …/lists-inventory/inventory/:id/to-list`) создаёт связанный пункт с количеством, которое поднимает остаток выше порога (`restockQuantity`), а открытый пункт этой позиции в том же списке возвращает вместо дубля.
5. Связь проверяет принадлежность обоих концов одному пространству (404 на чужую позицию или список) и не расширяет права.

## Extension Proposal

```text
Requested extension points:
  lists.item              — meta.api { ItemExtra, completeItem(context) }
  inventory.item.actions  — компонент в окне позиции склада

Plugin: lists-inventory

Reason:
  Пункту списка нужна метка связи и возможность «перехватить» отметку,
  а окну позиции склада — дополнительное действие. Хозяева (ListsPanel,
  InventoryPanel) не должны знать о складе / списках.
```

`completeItem` возвращает `null`, когда плагин не берётся за пункт (не связан или «Склад» выключен) — тогда хозяин отмечает пункт как раньше; иначе возвращает промис своей отметки. Контекст содержит `api`, `queryClient` и `isModuleEnabled`, чтобы плагин не импортировал внутренности хоста. Хозяин с выключенным плагином ведёт себя ровно как до моста.

## Проверка

- `apps/api/test/lists-inventory.integration.test.ts`: один приход на повтор и гонку трёх запросов, снятие отметки и отвязка не стирают приход, количество пополнения, отсутствие дубля, 404 между пространствами, 409 при выключенном плагине или модуле «Склад» с сохранением связей.
- `e2e/lists-inventory.spec.ts`: связь, «Куплено» и «В список покупок» через настоящий UI.

## Следующий шаг цепочки — «Покупки → Финансы» (плагин `lists-finance`, реализовано 15 октября 2026)

Решение, которого не хватало выше: **один чек — одна операция**. Купленные пункты списка записываются одним расходом (`POST …/lists-finance/lists/:listId/expense`: пункты, счёт, категория расходов, сумма — по ценам пунктов или с чека).

- Данные: одна колонка `list_items.expenseTransactionId` (FK на операцию, `SetNull`), собственной таблицы нет. Цена пункта — обычное поле `priceMinor` самого модуля «Списки» (`null` = неизвестна, не 0).
- Против двойной записи: строки пунктов блокируются `FOR UPDATE`, пункт с уже заполненным `expenseTransactionId` отклоняется (409) — в том числе при гонке двух окон. «Новый круг» (сброс отметок) очищает эту связь у пунктов: следующая покупка — новая покупка; сама операция остаётся в «Финансах».
- Запись идёт только через `FinanceExpenseWriter` (публичный контракт `finance/public`, пара к `FinanceExpenseReader`): те же проверки счёта и категории и те же оповещения бюджета, что у расхода из панели «Финансы».
- Клиент: слоты `lists.actions` («Записать расход» в шапке списка) и `lists.item.mark` (метка «записано в финансах» у пункта). С выключенным плагином или модулем «Финансы» — 409 на сервере, кнопка скрыта.
- Проверка: `apps/api/test/lists.integration.test.ts` («Покупки → Финансы»: одна операция и ровно один успех при гонке, цена неизвестна → 400, категория дохода → 400, 409 при выключенном плагине/модуле), `e2e/lists.spec.ts`.
