# ТЗ-06 — Hybrid Sync Engine (локальные копии и двусторонняя синхронизация)

> **PARTIAL / HISTORICAL BASELINE (19.10.2026):** Hybrid Sync для Lists/Items/Notes/Tasks реализован в отдельных этапах, полная двухустановочная приёмка и охват остальных модулей не выполнены; Orion Link с облачным relay не является готовой функцией. [SYNC](../SYNC.md), [STATUS](../STATUS.md).

Зависит от ТЗ-04 и ТЗ-05. Это **самое дорогое** направление: [SYNC.md](../SYNC.md) прямо называет его отдельным проектом, а не продолжением backup. Решение владельца 2026-10-15: целевая архитектура включает оба режима (общий узел и гибрид). Работать строго по этапам; каждый этап заканчивается решением «идти дальше / остановиться».

## Принципы (не обсуждаются в ходе работ)
- Синхронизируются **операции над сущностями**, а не файлы PostgreSQL и не снимки целиком. WebDAV остаётся бэкапом.
- Режим выбирается **на пространство**: «только локально» · «общий узел (онлайн-запись)» · «гибрид». Личные — локальные по умолчанию; финансовые операции — только общий узел, пока не доказана безопасность merge.
- У каждого общего пространства есть **авторитетный узел**; два узла не считают себя единственной правдой.
- Локально сохранено ≠ синхронизировано: UI и агенты показывают состояния раздельно (`local`, `queued`, `synced`, `conflict`).
- Права проверяются на авторитетном узле при приёме каждой операции (клиент не доверяется).
- Существующие данные не затираются; первичное объединение — только процедурой (ТЗ-05 §5.5).

## Этап 0 — Исследование и ADR (без кода продакшна)
Результат — ADR-0016 «Протокол синхронизации» (номер 0015 занял ADR LAN Host/Client) (+ черновик в `docs/`), содержащий:
1. Инвентарь workspace-моделей (опираться на `SNAPSHOT_MODEL_REGISTRY`) с классификацией: *mergeable-текст*, *LWW-поля*, *append-only*, *денежные/строгие*, *не синхронизируется*.
2. Идентификаторы (UUID уже есть?), порядок (HLC/векторные часы/серверный счётчик — выбрать и обосновать), tombstones и их срок, идемпотентность (`opId`), формат журнала операций.
3. Конфликт-политики по типам: заметки/документы (явный конфликт, как `note_revision_conflict`), задачи (по полям + `revision`), списки (add-wins/set-флаги), финансы (запрет offline-записи или резервирование идентификаторов + дедуп по `importedRef`-подобному ключу).
4. Файлы/блобы: передача по хэшу (sha256 уже считается), докачка, лимиты.
5. Безопасность: шифрование канала (ТЗ-04), подпись операций устройством, что делать с повреждённым/враждебным удалённым состоянием, **отзыв доступа не отзывает уже скачанное** — зафиксировать как ограничение.
6. Миграции протокола и схемы Prisma между версиями клиентов (версия протокола в рукопожатии, отказ при несовместимости).

## Этап 1 — Локальные копии, режим чтения
Клиент хранит копию выбранного пространства (какой слой хранения: отдельная локальная БД клиента или локальный узел — решить в ADR), загружает снимок состояния с хоста и показывает его офлайн **только для чтения**. Явная метка «данные на <время>». Запись офлайн запрещена и объяснена.

## Этап 2 — Прототип двусторонней записи на одной модели
**Одна модель — списки (`List`/`ListItem`)**: очередь локальных операций, повторная отправка, идемпотентность, tombstones, конфликт «двое отметили/удалили». Автоматические тесты: разрыв сети, дубль доставки, перестановка порядка, одновременное удаление и правка, откат устройства из бэкапа. Только если прототип проходит набор — этап 3.

## Этап 3 — Расширение на заметки и задачи
Конфликты заметок — явный UX (не молчаливый merge); версии/`revision` как основа. Документы/таблицы и финансы — **вне этапа**, отдельное решение.

## Этап 4 — Расширенная сеть (только описание)
Синхронизация через интернет, выделенный постоянный узел, мобильные клиенты, relay — отдельные ADR; не начинать без решения владельца.

## Не делать до этапа 2
Переписывать `SnapshotService`, менять схему моделей ради sync «заранее», добавлять колонки `*version/deletedAt` массово. Не использовать WebDAV как транспорт синхронизации. Не показывать «синхронизировано» без подтверждения хоста.

## Приёмка по этапам
- Этап 0: ADR принят владельцем; классификация охватывает **все** модели реестра (тест сверяет список).
- Этап 1: клиент без сети открывает копию, запись невозможна, после возврата сети данные обновляются; отзыв членства удаляет копию при следующем подключении (с оговоркой об уже скачанном).
- Этап 2: набор тестов сбоев зелёный (включая property-/fuzz-тест на перестановку и дубли операций), сходимость двух реплик доказана тестом.
- Этап 3: тот же набор на заметках/задачах; UX конфликтов проверен вручную на двух ПК.
- На каждом этапе — обновление `SYNC.md`: честный статус «что работает / что нет»; никаких обещаний «offline sync» для модулей, не прошедших этап.
