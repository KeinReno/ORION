Пункт 5.6 по идентичности устройств и полная проверка двух ПК — не закрыты, новая приватность заметок появилась отдельно (ADR-0021). [STATUS](../STATUS.md).

Зависит от ТЗ-04 (рабочий LAN-хост). Цель: сценарий владельца «Reno + Варвара» полностью работает на одном хосте и **проверен тестами**.

| Пространство | Reno | Варвара |
| --- | --- | --- |
| Личное Reno | полный | нет доступа |

## Что уже есть
`Workspace`, `WorkspaceMember` (+ роли owner/member/lead), `WorkspaceInvite` + `/invite?token=`, RLS, `assertMember`, приватные счета (миграции `*_private_accounts`), адресные уведомления (`recipientId`), назначение задач (`assigneeId`), общие списки (`checkedById`), poll списков 15 с.

## Задачи

### 5.1 Сквозная проверка модели (в первую очередь — это аудит, а не фича)
Интеграционный набор «два пользователя, три пространства»: для каждого workspace-scoped модуля — пользователь без членства не видит ни строк, ни связей, ни файлов, ни результатов поиска, ни записей журнала агентов, ни бэкапа; `EntityLink` на объект чужого пространства не создаётся. Найденные дыры — отдельными исправлениями с тестами. Особое внимание: поиск (`search`), `documents` (stream контента), `notifications`, `inbox`, `agent*` (токен привязан к пространству и человеку), `calendar-feed` по токену, снапшот/бэкап (кто имеет право его скачать — только owner).

### 5.2 Приглашения для LAN
Приглашение формируется на хосте: ссылка/код для устройства в LAN (в связке с ТЗ-04). Варвара создаёт **собственный аккаунт на хосте** (не общий), затем принимает приглашение в «Дом». Статусы `pending/expired/used/revoked` уже есть — использовать. Роль при приглашении выбирается (member/lead); смена роли — только owner.

### 5.3 «Дом» и «Семейные финансы»
- Шаблон создания пространства «Дом» (модули: списки, задачи, календарь, дом/коммуналка, склад; финансы — опционально) — через существующий `workspace-seed.ts`, без отдельной логики.
- Финансы: права по назначенной роли — определить в ADR минимальную модель (например, `view` / `add` / `manage` на уровне пространства; приватные счета уже есть) и реализовать **только если** без неё сценарий невозможен; иначе — задокументировать существующее поведение.
- Обновление данных у второго пользователя: проверить, что опрос/инвалидация react-query даёт «видно у обоих» без перезагрузки для списков, задач, календаря; для остальных модулей описать задержку честно.

### 5.4 Личные пространства
Подтвердить и закрепить тестами: при регистрации на хосте создаётся личное пространство; оно **не** предлагается как общее; владелец хоста **не получает** доступа к личному пространству Варвары через UI (администратор БД физически имеет доступ — зафиксировать в документации как ограничение доверия, не скрывать).

### 5.5 Подключение существующих баз (миграция/слияние) — **процедура, не автослияние**
Если у Варвары уже есть локальный ORION с данными: при переходе в «Клиент LAN» данные **не перезаписываются и не сливаются молча**. Реализовать явный путь: «Перенести моё пространство на узел» = экспорт её пространства `.orion` (существующий snapshot+blob-backup) → импорт на хост **как новое пространство** с новыми ID пользователя-владельца (проверка конфликтов ID, dry-run превью). Пока не реализовано — UI честно говорит «останется только локально».

### 5.6 Идентичность устройств
Связь «пользователь ↔ доверенные устройства» (из ТЗ-04) отображается в профиле; выход пользователя не отзывает устройство, отзыв устройства не удаляет пользователя.

## Не делать
Синхронизацию двух независимых баз (ТЗ-06), федерацию между узлами, облачные аккаунты, новый уровень владения «группа/семья» (иерархия остаётся: пользователь → пространство → необязательный проект).
