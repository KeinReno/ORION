# ORION: ворота закрытой беты и простой установки

Срез: 12 октября 2026 года. Это **чек-лист приёмки**, не утверждение, что релиз готов. Прежние CI/ручные прогоны привязаны к старым ревизиям; после последних изменений все ворота нужно проверить заново. План продукта — [ROADMAP.md](ROADMAP.md).

## Первый выпуск

Рекомендуется закрытая web-бета для доверенных пользователей на **одном сервере**: Next.js, NestJS, PostgreSQL 16, постоянное хранилище файлов, HTTPS и reverse proxy. Личное/семейное пространство и малая команда одинаково важны. Конкретная ОС и способ хостинга ещё не выбраны. GitHub Actions на Ubuntu не означает обязательный Linux-деплой. Локальный режим может сохраняться для одиночного использования; окончательная стратегия устройств описана в [SYNC.md](SYNC.md) как открытое решение.

Для автономной **локальной** Windows x64 установки добавлен отдельный путь `pnpm build:desktop-installer`: NSIS включает API, Node.js и PostgreSQL 16, а при первом запуске создаёт базу и применяет миграции в LocalAppData. Простая команда `tauri build` без подготовки runtime не является релизной сборкой. Инструкция и границы проверки — [WINDOWS_INSTALLER.md](WINDOWS_INSTALLER.md). Этот локальный путь не заменяет многопользовательский сервер и не закрывает ворота web-беты ниже.

На машине сборки 12 октября локальный NSIS был установлен в отдельную папку и запущен: новая БД, 80 миграций, production API, WebView и входная страница, затем проверены регистрация/вход/первое пространство на изолированном каталоге. Контроль на чистой офисной машине и восстановление всей установки из резервной копии пока отсутствуют; выпуск следует помечать beta.

## Особо проверить перед релизом

- Исторически наблюдался обход grant UPDATE на уровне RLS; позже документировалось исправление. Нужна новая негативная проверка на текущей схеме, а не перенос прежнего FAIL/PASS.
- `login-rate-limit.guard.ts` и `register-rate-limit.guard.ts` раньше читали `X-Forwarded-For` напрямую. Теперь используют `req.ip`; по умолчанию заголовок не доверен, а `ORION_TRUSTED_PROXIES` принимает только явные IP/CIDR. Изолированные HTTP-тесты с ротацией подложного заголовка для входа и регистрации прошли 11 октября; на staging остаётся проверить адрес реального прокси, перезапись им входящего `X-Forwarded-For` и прямую недоступность API извне.
- `apps/web/lib/api-base.ts` ранее имел `localhost:4000` fallback. `resolveApiBaseUrl` отклоняет в удалённом production-клиенте и отсутствие `NEXT_PUBLIC_API_URL`, и явно вшитый loopback URL (в том числе из локального `.env.local`); на `localhost`/Tauri fallback сохраняется. Проверить production build из другой машины и собирать его с публичным адресом API.
- WebDAV-тесты в старых CI имели ошибки; причину подтвердить и исправить, не ослабляя защиту URL. Отдельно проверить восстановление файлов, а не только строк БД.
- Office round-trip: документ с формулами, форматированием, merged cells, chart/pivot и версиями не должен молча терять неподдерживаемое содержимое; если формат не поддержан, пользователь получает честное предупреждение и исходник сохраняется.

- `users`, `refresh_tokens` и `user_preferences` остаются без RLS (структурный тест `rls-coverage.integration.test.ts` фиксирует этот список и падает при появлении любой новой таблицы без RLS). Хеши refresh-токенов защищены только кодом и ролью БД; перевод `AuthService`/`SettingsService` на `asSystem`/`withUser` и включение RLS — задача усиления после беты, не блокер.

## Резервная копия и восстановление узла

Снимок рабочего пространства `.orion` намеренно не содержит учётных записей, сессий и грантов, поэтому сервер им не восстановить. Для всего узла есть `apps/api/src/ops` (нужен `DATABASE_URL` роли миграций):

```text
node dist/ops/cli.js backup  <пустой каталог>   # все 51 таблица одним снимком REPEATABLE READ + файлы документов + manifest.json с SHA-256
node dist/ops/cli.js verify  <каталог>          # офлайн-проверка сумм, БД не нужна
node dist/ops/cli.js restore <каталог>          # в ПУСТУЮ БД с теми же миграциями и пустой STORAGE_DIR
```

Восстановление отказывается работать на непустой БД или каталоге, при другом наборе миграций и при повреждённой копии; после загрузки сверяет число строк и контрольную сумму каждой таблицы с копией, проверяет внешние ключи и хеши файлов. В копию **не** входят `JWT_SECRET` (без него просто перестанут действовать сессии) и `SYNC_SECRET` (без него не расшифруются пароли WebDAV/календарей и зашифрованные снимки): храните их отдельно, restore предупредит о несовпадении ключа. Каталог копии содержит данные всех пользователей и хеши паролей: храните и шифруйте как саму БД. Внешнее хранилище (`STORAGE_DRIVER=webdav`) в копию не входит.

Проверено 11 октября: интеграционный тест `node-backup.integration.test.ts` (временная БД, миграции, файлы, самоссылки, подделка копии) и репетиция на рабочей dev-БД (51 таблица, 1429 строк, 43 файла): восстановление в новую БД, запуск `node dist/main.js` в `server`-режиме, вход прежним паролем, чтение пространств под RLS и скачивание 20 файлов. Не проверено: объём больше локального (копия таблиц сейчас собирается в памяти по одной таблице), регулярность и хранение копий, `pg_dump` как альтернатива, восстановление на другой машине.

## Развёртывание и откат

1. Снять и **проверить** согласованную резервную копию до миграции. Держать секреты вне Git.
2. Подготовить PostgreSQL 16 с раздельными ролями миграций и приложения; применить `infra/postgres/init/01-app-roles.sql` и `prisma migrate deploy` на чистой staging-БД. **Файл создаёт `orion_app` с паролем, опубликованным в репозитории**: сразу после применения выполните `ALTER ROLE orion_app PASSWORD '<свой>'`, смените и пароль `orion`; в `server`-режиме API не стартует с опубликованными паролями. В новой БД внутри уже существующего кластера роли есть, но права нужно выдать заново: `GRANT USAGE ON SCHEMA public` и `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public` для `orion_app` и `orion_system` (без этого вход падает с `permission denied for table users`).
3. Собрать web с публичным URL API (`NEXT_PUBLIC_API_URL`), собрать API (`pnpm --filter @orion/api build`: `tsc` плюс `scripts/build-api-runtime.mjs`, который кладёт скомпилированный `@orion/shared-types` в `dist/node_modules`) и запустить `node dist/main.js` с `ORION_MODE=server` за HTTPS proxy; ограничить прямой доступ к БД и файлам. До 11 октября `node dist/main.js` не запускался вовсе (workspace-пакет отдавался как `.ts`), рабочим был только dev-режим. В `server`-режиме процесс не стартует (`server-config.ts`), если слабый `JWT_SECRET`, не задан `APP_DATABASE_URL` или совпадает с `DATABASE_URL`, нет HTTPS-`WEB_ORIGIN`/`PUBLIC_API_URL`, некорректны `ORION_TRUSTED_PROXIES`/`SYNC_SECRET`, а также если подключение идёт ролью с суперправами или BYPASSRLS.
4. Проверить `/system/health`, вход, права двух пользователей, upload/download и backup/restore.
5. При сбое остановить запись и восстановить согласованную пару БД+файлы+ключи. Старый binary сам по себе не откатывает необратимую миграцию.

После закрытой беты могут идти мобильный клиент, полный offline sync, чат, AI API, marketplace и внешние интеграции. Дефекты прав, сохранения данных и восстановления откладывать нельзя.
