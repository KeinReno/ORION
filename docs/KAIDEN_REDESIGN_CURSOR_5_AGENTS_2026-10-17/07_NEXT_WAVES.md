# После первой волны: закрытие полного редизайна Orion

> **Статус: PROPOSED BACKLOG, не поручение к немедленной реализации (19.10.2026).** Первая волна завершена и слита PR #8–#12. Пункты второй/третьей волны необходимо сверять с текущим [STATUS.md](../STATUS.md) и уже выполненными G1–G26; нельзя повторно создавать существующие компоненты или считать весь список неизменным обязательным планом.

Первая волна охватывает пять крупных экранных вертикалей и темы. Нижеперечисленное — **обязательный backlog до утверждения полного редизайна**, а не задачи, которые разрешено самовольно выполнять параллельно с волной 1.

## Волна 2 — общая архитектура UI (ПОСЛЕ интеграции волны 1)
Работать последовательно на уровне общего кода (один координатор владеет shell/registry/shared-types), остальные агенты — отдельные компонентные поставщики без параллельной модификации общих файлов.

### 2.1 Единый инспектор объектов
Единые вкладки свойств/связей/истории/доступа для поддерживаемых сущностей. Общие UI-контракты, workspace ACL, локальные адаптеры; не копировать на каждый модуль свои несовместимые инспекторы. Приёмка: открыть проект, задачу, заметку и документ штатным способом, одинаковые действия на общих вкладках, запрет чужих объектов.

### 2.2 Навигационное дерево и пространство работы
Дерево объектов/групп, быстрый переход, drag/drop только при существующих разрешениях, keyboard navigation, связи модулей, отсутствие дублей маршрутов. Существующие три уровня навигации не ломать. Для смешанных пространств и новых рабочих сессий прежде определить ADR и модель ACL: это **новая функциональность**, не маскировать как CSS-редизайн.

### 2.3 Долговременное состояние и надёжность
Состояния панелей и фильтров, история назад/вперёд после перезапуска, scroll restoration, recovery черновиков после принудительного закрытия с ограничением хранения/приватности. Восстановленные объекты должны проверять доступ и факт существования; удалённые/выключенные — безопасный fallback. Тест: аварийное закрытие → reopen → корректное и безопасное восстановление. Отдельно проверить Tauri окна и multi-monitor bounds.

### 2.4 Остальные встроенные модули и плагины
После инвентаризации catalog/registry — матрица миграции всех оставшихся экранов, включая финансы, здоровье, ресурсы, Opportunity Hub, расширения и настройки. По каждому — владелец, карта экранов, отсутствие функциональной регрессии, API/security, 320/390/desktop, клавиатура, палитры. Не объявлять всё закрытым по пяти панелям первой волны.

## Волна 3 — новые концепции (отдельный продуктовый scope)
Command, Atlas, смешанные пространства и рабочие сессии — **не реализованы на момент исходного handoff**; сначала дизайн-решения, ADR, UX-макеты/прототипы, контракт доступа и модель синхронизации, затем разработка и отдельная приёмка. Эти концепции не должны тихо менять архитектуру первой волны.

## Волна 4 — десктопная и межустройственная приёмка
- Сборка установщика из текущего master; чистый Windows-профиль и безопасная тестовая БД.
- Тесты открытия/возврата popout окон, закрытия с несохранённым вводом, DPI, нескольких мониторов, клавиатуры и WebView2/CSP (PDF/XLSX).
- Два реальных ПК: разные пользователи и личные/общие пространства, LAN discovery, permission propagation, hybrid sync и конфликтные записи; не считать эмуляцию двумя компьютерами.
- Обратная совместимость хранения/backup/restore, восстановление пользовательских палитр, отсутствие утечки приватных данных.
- Сборка и smoke — подтверждённые действием, не документацией.

## Критерий завершения проекта редизайна
Только когда по всем волнам есть статусы DONE/ACCEPTED (или пользователь явно исключил конкретное требование), общие тесты проходят на актуальном HEAD и ручные сценарии на Windows подтверждены, можно писать «редизайн KAIDEN Orion завершён». Иначе указывать точный процент/перечень срезов без выдуманного «100%».
