# Правила пяти параллельных чатов Cursor в одной рабочей копии

> **Статус: HISTORICAL — инструкция для неиспользованного варианта запуска пяти Cursor-чатов (19.10.2026).** Фактическая реализация шла в раздельных облачных ветках и PR #8–#12, см. `reports/AGENT_01..05.md`. **Не запускать по этой инструкции заново.** Современные правила параллельной разработки: [AGENTS](../../AGENTS.md) и [протокол документации](../DOCUMENTATION_LIFECYCLE.md).

**Режим:** одна актуальная локальная директория Orion; без специальных Git-веток/worktree. Изоляция достигается **исключительно владением файлами и очередью общих операций**. Вся информация о задачах ниже — инструкция, не доказательство реализации.

## Перед редактированием — КАЖДОМУ
1. Прочитать `docs/STATUS.md`, handoff редизайна, свой файл ТЗ, относящиеся MODULE/AI_CONTEXT/ADR.
2. Проверить `git status --short`, текущий HEAD и фактический код. Записать только для отчёта baseline. Существующие незакоммиченные изменения **не трогать**.
3. Найти реальные компоненты с `rg`; имена файлов в ТЗ — ориентиры, не разрешение менять весь каталог.
4. Сообщить конкретный поднабор файлов внутри своей зоны до начала правок. Если обнаружен конфликт владения — НЕ редактировать спорный файл.
5. Создать/обновлять только свой итоговый отчёт `docs/KAIDEN_REDESIGN_CURSOR_5_AGENTS_2026-10-17/reports/AGENT_0N.md` (отчёт может появиться после начала работы).

## Изолированные зоны
- Чат 1: код механизма палитр, настройки выбора/управления темами и theme-only API/UI. Единственный уполномоченный на изменения дизайн-токенов после сверки зависимостей; не менять `TasksPanel` / `ProjectsPanel` / `NotesPanel` / `DocumentsPanel` / `CalendarPanel`.
- Чат 2: проекты и принадлежащие им дочерние UI-компоненты; не менять задачу или общий инспектор.
- Чат 3: задачи и принадлежащие им дочерние UI-компоненты; не менять проекты или общий инспектор.
- Чат 4: заметки/документы и их собственные UI-компоненты; сначала заметки, затем документы.
- Чат 5: календарь и его собственные UI-компоненты; без изменения общего event API/recurrence implementation.

Новый компонент можно добавлять под область своего модуля; нельзя создавать альтернативную общую дизайн-систему или копировать чужую бизнес-логику.

## Общие файлы — ЗАПРЕТ самостоятельного изменения
`package.json`, `pnpm-lock.yaml`, `schema.prisma`, `apps/web/app/**` (если это общие стили/оболочка), `packages/ui/**` (кроме отдельно выделенных theme-owned файлов), shell, роутинг, shared-types, `@orion/core`, общие React hooks, registry, Prisma migrations, тестовые и CI-конфиги, desktop/Tauri, root .env и инфраструктура. Исключение: чат 1 может предложить минимальные theme-only изменения после явной записи перечня и подтверждения координатором; до подтверждения оставить блокировку, не «продавить» обход.

Если задача действительно требует общих файлов, сохранить в своём отчёте:
`BLOCKED: <путь>; зачем нужен; минимальный diff/контракт; кто может внести; какой тест нужен`.
Координатор последовательно объединяет изменения и снимает блокировку; каждый чат продолжает только свою часть. **Не разрешается молча править общий файл «пока другие не заметят».**

## Работа с Git и тестами
- Агенты НЕ выполняют `git checkout`, `switch`, `pull`, `merge`, `rebase`, `reset`, `clean`, `stash`, `commit`, `push`, не удаляют чужие файлы.
- Никогда не использовать `git add .` / `git add -A`: в общем каталоге это включает работу других чатов.
- Не делать `pnpm install`, миграции, `prisma generate`, `pnpm build`, Tauri build, массовые форматирования, bulk codemod, общее `pnpm test` и E2E одновременно. Эти операции — строго через координатора и по очереди.
- Разрешены чтение, проверка конкретного модуля, локальный дифф своих файлов, целевые безопасные тесты, если они не изменяют общие артефакты и БД. При сомнении — поставить в очередь.
- Не править реальные пользовательские данные или производственные секреты. Никаких «удалить кэш и пересобрать» с непроверенным путём. Не подменять тесты и не удалять провалившиеся проверки.

## Проверка после каждого среза
Агент описывает UI-путь, негативные сценарии, скриншоты «до/после» (если доступны), результат/отсутствие тестов, дифф файлов и проблемы. Координатор сверяет изменения, выполняет общие проверки **после остановки конкурирующих записей**, поэтапно фиксирует коммиты только со специально перечисленными путями.

## Конфликтный сценарий
Если файл изменился чужим процессом между чтением и записью, **не перезаписывать**. Остановиться, показать базовую и текущую версию/предлагаемый diff, передать конфликт координатору. Не откатывать «чужие» незакоммиченные изменения. Если тесты падали на baseline, указать отличие и не приписывать его себе.

## Ограничения контроля
Такой режим возможен, но **менее надёжен, чем отдельные worktree**: npm-артефакты, индекс Git, общие generated-файлы и одновременное сохранение всё ещё могут конфликтовать. Протокол минимизирует, а не исключает риск. Если пересечения станут систематическими, необходимо временно сериализовать агенты или вернуться к физической изоляции.
