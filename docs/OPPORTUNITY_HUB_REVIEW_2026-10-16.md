## Решение о готовности

Проверены и доработаны локальный рабочий процесс R0 и серверный протокол R1, начатые Claude. Полный R1 по ТЗ **не принят**: реального адаптера hh.ru, чатов с message IDs и живой приёмки G20 нет. Внешний LLM не настроен. Имитация исполнения подтверждает протокол, но не факт работы с реальным HH.

База проверки — HEAD `298cb91` и незакоммиченные изменения Claude. Они сохранены; общего сброса/переписывания checkout, коммита или публикации не выполнялось. Папка `C:\Users\Reno\Desktop\HH` не менялась, её автоматизация не запускалась. Реальные резюме и отклики не использовались.

## Найдено и исправлено

| Проблема | Исправление и проверка |
| --- | --- |
| Состояние подключения читалось до ожидания блокировки; при гонке могла использоваться старая версия | Чтение после `FOR UPDATE`. PostgreSQL-тест удерживает блокировку и приостанавливает подключение, пока claim ожидает: задание не выдаётся |
| Disable → enable в пределах TTL возвращал старому grant право на отправку, вопреки §3.1 ТЗ | Транзакционный lifecycle-контракт Core; Execution отзывает grants/очередь и ставит connection на паузу, Manager приостанавливает policy. Проверены все три зависимости и выключение Base-модуля; повторное включение не возрождает полномочия |
| Обработка истёкшей аренды могла пересечься с heartbeat/reserve/result | Блокировка попытки, `SKIP LOCKED` в обслуживании, единый порядок attempt → grant. UTC timestamp задаётся явно, независимо от часового пояса PostgreSQL |
| Действие менеджера могло пережить срок политики/выключение менеджера без открытия его экрана | Публичный `ExecutionAuthorityRegistry`; повторная проверка при claim, heartbeat, reserve. Тесты expiry, disabled provider, quiet hours, unresolved send |
| После обработки первых 200 карточек менеджер переставал видеть следующие | Стабильная пагинация `afterId` через публичный read-port; тест на 201 карточке |
| Аккаунт наблюдался только до длительной подготовки формы | Повторная проверка аккаунта и baseline после prepare; payload/account передаются финальному submit-контракту; при смене аккаунта ни reserve, ни submit не выполняются |
| Стоп проверялся раз в 15 секунд и не прерывал ожидающий prepare | Опрос каждую секунду, AbortSignal и немедленный abort. Тест останавливает ещё ожидающую подготовку. Живая задержка HH не измерялась |
| Evidence могло не содержать идентификатора события или иметь невозможное будущее время | Непустой ref, время не раньше резервирования, верхняя граница времени наблюдения; отрицательные тесты |
| RTF с обычными байтами Windows-1251 искажал русский текст | Декодирование raw ANSI по ansicpg, версия `orion-rtf@2`; проверено «Привет» и escaped/Unicode варианты |
| Распаковка DOCX полагалась только на заявленный размер | Ограничение фактически распакованного потока и проверка исходных ZIP-путей; тест поддельного uncompressed size |
| Несохранённый черновик можно было потерять при переходе или обновлении другой версии | Dirty-state проходит через публичный details-slot; подтверждение закрытия/перехода, сохранение локального текста при refetch, CAS по исходной revision, явная загрузка актуальной версии |
| Длинное имя профиля растягивало внутренний scroll-container Dock, хотя ширина страницы оставалась нормальной | Перенос текста кнопки и ограничение ширины flex-элемента; responsive-тест теперь проверяет `.orion-scroll`, а не только documentElement |
| Импорт 10 000 карточек не укладывался в 60 секунд | Insert-only batch-port до 25 записей, пакетная запись captures, summary-запросы без большого plan. Проверены дубли одного externalId и сохранность ручной карточки |
| E2E зависел от случайно поднятого в корень JSZip | Прямая root devDependency `jszip@3.10.1`; lockfile обновлён, runtime-зависимости не изменены |

Новая точка расширения описана в [Extension Proposal](extensions/OPPORTUNITY_EXECUTION_AUTHORITY.md). Base не импортирует конкретные расширения. Политика проверяется вкладом менеджера через контракт Execution; обратной зависимости нет.

Для конфигурации добавлен отдельный [lifecycle-контракт](extensions/CAPABILITY_LIFECYCLE.md): Core вызывает зарегистрированные вклады внутри своей транзакции и не знает таблиц Hub. Проверены rollback настройки при ошибке вклада и отсутствие потери override при двух параллельных изменениях.

## Что отделено от готового локального среза

1. **Реальный HH-адаптер и G20.** В `opportunities-execution/AI_CONTEXT.md` явно указано: “Never send for real without the owner's explicit permission for the concrete account and action.” Также запрещено писать/запускать live hh.ru script без этого разрешения. Конкретный аккаунт, профиль, получатель и согласованный текст в текущем запросе не заданы. Никакого скрытого внешнего действия не выполнено.
2. **Полный R1.2:** чат с message IDs, живое наблюдение событий, проверенная работа адаптера при смене формы/резюме, CAPTCHA и реальном подтверждении события. Серверные фикстуры этого не доказывают.
3. **Внешняя модель:** нужен выбор провайдера, бюджета и полей, разрешённых к передаче. Сейчас работает локальный `rules-v1`, без сетевой передачи материалов.
4. **Интеграционные расширения:** байты screenshot evidence в storage с retention, AI scopes/events, мосты Tasks/Calendar/Notes/Projects. Текущий протокол хранит evidence refs/hash. Это отдельные публичные контракты/bridge-срезы; произвольные внутренние импорты не добавлены.
5. **Дополнительные возможности импорта:** старый OLE `.doc`, OCR и общий persisted manifest нескольких пакетов. Они явно не выдаются за реализованные.
6. **Поставка:** ручной проход установленного окна и чистой машины, полный screen-reader аудит. Фоновый менеджер сейчас отсутствует; цикл выполняется только по кнопке. Гранулярный ACL профиля и lead-role не обещаны R0/R1 (§4.1 ТЗ): персональное хранится в личном workspace, общий профиль публикуется с явным предупреждением.

Для продолжения нельзя обходить эти границы переключателем «автономность» или называть simulated outcome живым откликом. Нужны реальные адаптерные доказательства и оставшиеся проверки ТЗ, прежде чем объявлять весь R1 завершённым.
