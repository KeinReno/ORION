# Orion Agent Hub — совместная работа ИИ-агентов до GitHub

**Статус:** целевое продуктовое направление обсуждено 18.10.2026; описанные здесь оркестрация, адаптеры подписок и общее рабочее состояние **не реализованы как единый Agent Hub**. Эта спецификация подчиняется [PLATFORM.md](PLATFORM.md), [AGENTS.md](../AGENTS.md) и границам [AI_FIRST_EXTENSION_ARCHITECTURE.md](AI_FIRST_EXTENSION_ARCHITECTURE.md). Состояние кода — [STATUS.md](STATUS.md).

## 1. Проблема и конечная цель

Сейчас разработка распределена между Cursor (включая Composer/агентов), Claude Code и ChatGPT/Codex, потенциально Hermes/Gemini и другими клиентами. Каждый работает в своей среде; GitHub показывает результат коммитов и PR, но не обеспечивает сквозной обмен намерениями, промежуточными выводами, вопросами, блокировками и общим контекстом **до коммита**.

**Цель:** сделать Orion единой площадкой координации независимых ИИ-инструментов **без замены их редакторов и IDE**. В Orion видны проекты, участники-агенты, задачи, текущая работа, сообщения, артефакты, решения, вопросы, согласования, история и зависимости. Агенты могут обсуждать промежуточный результат, передавать друг другу подзадачи, обращаться за помощью и получать от пользователя подтверждения. GitHub остаётся источником истины для версионированного кода, но не единственным способом обмена рабочим контекстом.

### Ключевое требование по оплате

**Максимально использовать существующие пользовательские подписки**, когда конкретный поставщик **официально** допускает вход и автоматизацию соответствующего CLI/приложения. **Не требовать отдельную оплату inference API** как условие работы Orion Agent Hub. Не использовать cookies, неофициальное извлечение токенов из веб-чата, браузерные обходы, подмену клиентов или технические способы обхода ограничений провайдеров.

Подписка не даёт гарантированного безлимита, универсального стороннего API или доступа к внутренней сессии приложения. Перед реализацией каждого адаптера проверить текущие тарифы, лимиты, условия автоматизации, способы входа и отделённость CLI-подписки от API-биллинга; при необходимости функция помечается как `unsupported` или требует отдельного явно подтверждённого режима API.

## 2. Что уже реализовано в Orion

По документации 18.10.2026:
- [ADR-0007](adr/ADR-0007-ai-bridge.md): AgentToken, scopes, отзыв, audit, предложения/подтверждения, задания и обмен сообщениями; эти примитивы **нельзя переписывать заново** без доказанной необходимости.
- [ADR-0018](adr/ADR-0018-agent-gateway.md), [AGENT_MANUAL.md](AGENT_MANUAL.md): `/ai/v1` для контекста, создания/поиска/связывания объектов, MCP stdio в установленной версии, мастер подключения к локальному Orion.
- Agent Manager и его автономность/разрешения — уже существующий слой; нужно расширять, сохранив права пользователя и аудит.
- Нет доказанной полной межклиентской оркестрации, реальной online-presence независимых IDE, общего потока рабочих артефактов и согласованного планировщика задач Agent Hub.
- Отображение действительных токенов **не равно** подтверждённому online-состоянию работающих агентов. Heartbeat/lease должны быть реализованы отдельно.
- Прямой доступ внешнего облачного ChatGPT к локальному `127.0.0.1` отсутствует. [ADR-0017](adr/ADR-0017-agent-remote-access.md) — предложение, **не** готовый удалённый доступ.

Важно: существующий MCP — интерфейс к Orion, а не автоматическое право удалённо запускать или читать закрытый внутренний диалог любой подписочной модели.

## 3. Разделение ответственности

```text
Человек: Orion Projects / Tasks / Approvals / Activity / Devices
                         |
                 Agent Hub (координация)
               задачи / сообщения / контекст
           события / presence / артефакты / аудит
                         |
      Agent Gateway (MCP/REST, authn/authz, scopes)
                         |
           Agent Runtime Adapter contracts
            /              |               \
    Claude Code CLI     Codex CLI       Cursor adapter*
       подписка          подписка          доступность уточнить
            \              |               /
               Локальные процессы / IDE
                         |
            Git worktree / repo / test / PR
```

`*` Интеграции Cursor и других приложений зависят от документированного CLI/MCP/extension API и разрешённой модели использования; не считать их интерфейсы эквивалентными Claude Code/Codex. ChatGPT как конкретный веб-диалог **не становится программно управляемым агентом по факту подписки**. Если допустимо, использовать официальный Codex/интеграционный путь, сохраняя различие между ним и текущим разговором в ChatGPT.

- **Orion Core:** identity, workspace, permissions, события, хранилище, transport, модульная инфраструктура. Не встраивать вызовы конкретных LLM или CLI в Core.
- **Agent Gateway:** стабильная граница инструментов, авторизации, audit, выдача минимального контекста.
- **Agent Hub:** отдельный функциональный модуль/платформенное расширение над Gateway, с проектной моделью координации.
- **Runtime adapters:** изолированные интеграции по провайдеру (Claude Code, Codex, Cursor и т. п.) со стандартизованными capability flags, запуском/остановкой в дозволенных режимах, событием статуса и привязкой к проекту.
- **Orion Link:** доставка между узлами; не подменяет интерактивную шину Agent Hub облачной WebDAV-папкой. См. [ORION_LINK_ARCHITECTURE.md](ORION_LINK_ARCHITECTURE.md).

## 4. Рабочая модель и возможный контракт

Кандидатные сущности (названия/схемы ещё требуют ADR и ревью модели доступа):
- `AgentInstance`: адаптер, capabilities, владелец, workspace, host device, допустимые операции, истечение lease, `lastHeartbeatAt`, статус `online|busy|offline|unknown`.
- `AgentSession`: связка экземпляра с проектом/задачей, `externalSessionRef` **только если** клиент официально предоставляет безопасный resume.
- `HubTask`: автор, исполнитель/пул, требования, зависимости, приоритет, статусы `queued|claimed|working|blocked|review|done|failed|cancelled`, версия и дедлайн lease.
- `HubMessage`: отправитель/получатель/тема/проект, тип `question|answer|handoff|status|review`, идемпотентный идентификатор и разрешённые ссылки на артефакты.
- `HubArtifact`: файл, diff, plan, тестовый отчёт, результат исследования или ссылка на ветку, checksum, происхождение, правовая/доступная область.
- `HubDecision` и `HubApproval`: принимаемые человеком архитектурные решения, блокирующие действия, чей ответ ожидается, документированный итог.

Контракт адаптера (идея, не публичный API v1): `detectCapabilities`, `connect`, `startTask`, `cancelTask`, `observeStatus`, `postMessage`, `collectArtifact`, `resumeSession?`. Не требовать `resumeSession`, прямого обмена сообщениями внутри LLM или фонового запуска, если клиент этого не поддерживает. Для адаптеров только с MCP/ручным режимом Orion предоставляет «получить контекст → выполнить в привычной IDE → отправить промежуточный ответ», без ложного обещания автоматизации.

## 5. Как выглядит совместная работа

Пример проекта Orion:
1. Пользователь ставит цель и определяет роли: Claude Code — архитектурное исследование, Cursor — UI, Codex — проверки. Роли не жёстко привязаны к бренду.
2. Координатор создаёт `HubTask` с версиями контрактов и материалами (документы Orion, связанные задачи, актуальные решения, границы доступа).
3. Агент берёт задачу через claim/lease, публикует намерение, статус и промежуточные результаты. Другие агенты могут подписаться на события, задать уточнение, предложить помощь.
4. Агенты публикуют сообщения и артефакты **до push/PR**. Агент разработки может передать агенту проверки diff/план/тесты, а не целый необработанный диалог.
5. Владелец Orion видит прогресс, очереди, кто что меняет, нерешённые конфликты, версии решений, стоимость только там, где она реально доступна через официальный канал, и запросы подтверждения.
6. После проверки результат коммитится/отправляется в GitHub в соответствии с существующими правилами проекта. Orion сохраняет ссылки на commit/PR и трассировку выполнения.

Агенты не должны одновременно редактировать один и тот же рабочий каталог без координации: выделять worktree/ветки и ownership файлов, резервировать зоны работы с TTL, перед объединением проверять конфликтующие изменения. Не считать лог сообщений заменой Git. На уровне агентских задач необходимы queue, lease, retry, heartbeat, idempotency, cancellation, dead-letter и наблюдаемая история попыток.

### Контекст и память

Общая память — **версионированные проектные артефакты и решения**, а не неконтролируемая выгрузка всех приватных чатов и полная синхронизация скрытых рассуждений модели. Хранить краткие handoff-сводки, ссылки на источники, ограниченные разрешениями выдержки, планы, риски, неизвестные, тестовые результаты и авторство. Разделять постоянное знание проекта и временные рабочие сообщения, помечать устаревший контекст и не загружать агентам всё пространство без необходимости.

## 6. Безопасность, пользовательский контроль, доступность

- Агент работает только в разрешённом workspace, с явной матрицей scopes, атрибуцией, журналом и отзывом. Право на чтение/запись Hub-объекта не означает доступ к соседнему проекту, файлу, модулю или подписке.
- Команды удаления, финансовые действия, публикации, merge, изменение политик, выполнение произвольного shell при высоком риске — через пользовательское подтверждение по существующему Agent Manager/новым policy contracts.
- Подписочные учётные данные остаются в официальном безопасном хранилище клиента; Orion **не** сохраняет пароль, cookie или токен поставщика. Фиксируются только конфигурация адаптера и состояние подключения.
- Prompt injection из issue, сообщения или файла не может расширять права адаптера. Вызов инструментов валидируется на границе Gateway; аудит и секреты разграничены.
- На старте Coordinator/Hub можно размещать на локальном ПК, без отдельного сервера, пока компьютер включён. Позднее переносить системные службы на **собственный сервер** и сохранять те же контракты. Важно: перенос координатора не переносит подписочные CLI автоматически на сервер; их запуск, авторизация и правила провайдера зависят от устройства/среды.
- С телефона Orion показывает задачи, агентские события, проверки и позволяет отправлять сообщения; **исполнение на выключенном ПК невозможно** без другого доступного runtime. WebDAV сам по себе — не онлайн-RPC канал команд.

## 7. Аналоги: что взять, а что нет

Архитектурный ориентир — [Q00/ouroboros](https://github.com/Q00/ouroboros): общий координатор, интерфейс runtime-адаптеров, инструменты MCP, журнал этапов, контрольные точки и проверка результатов (детали конкретной ревизии и лицензия перепроверяются перед заимствованием). В отличие от модели «планировщик → исполнитель → оценка», Orion Hub должен обеспечивать **долговременное сотрудничество различных внешних клиентов в проекте**, включая сообщения и handoff до GitHub. Не утверждать, что Ouroboros или любой подписочный клиент предоставляет недокументированные методы.

Другие мультиагентные фреймворки и API-first системы полезны для очередей/оркестрации, но **не** решают ключевое ограничение пользователя — работу через существующие подписки — автоматически. Дизайн адаптера должен поддерживать `subscription-cli`, `external-mcp/manual` и отдельно опциональный `api-key` режим; последний **не включён по умолчанию** и не должен тайно создавать расходы.

## 8. Этапы внедрения и приёмка

Приоритеты ниже не отменяют Stage 0 и этапы [PLATFORM.md](PLATFORM.md): сначала стабилизация платформы/публичных контрактов, затем Agent Hub.

1. **Инвентаризация:** проверка действующих AgentToken, Gateway, Manager, agents messaging, MCP, статусов в UI и ограничений установщика. Фиксировать конкретный commit; не выдавать реестр токенов за online presence.
2. **Спецификация/ADR:** определить сущности, scope-модель, журнал событий, адаптерный контракт и extension points, не ломая уже существующие права/аудит.
3. **Совместная работа без запуска:** проектная лента, task board агентов, сообщения, handoff, артефакты и явные статусы; два тестовых агента взаимодействуют через Gateway до коммита.
4. **Первый подписочный адаптер:** Claude Code **только в допустимом официальном режиме** с подтверждением доступности; затем Codex CLI при аналогичной проверке. Не заявлять полную интеграцию с ChatGPT-чата.
5. **Остальные:** Cursor (в зависимости от документированных interfaces), Gemini/Hermes и другие — по capability matrix. Раздел «Устройства и агенты», heartbeat, владелец может остановить/отозвать, просмотр и подтверждения с телефона.
6. **Масштабирование:** несколько local runtimes, изоляция worktrees, очередь/leases, перенос coordinator на собственный сервер, удалённое безопасное управление как отдельный transport.

Критерии: два разных допустимых клиента видят общую задачу и сообщения, передают артефакты до push, не теряют handoff после рестарта Orion, не получают лишних scopes; задача не выполняется дважды при повторной доставке; устройство корректно становится offline по истечении heartbeat; без API-ключа базовый тест не вызывает платный LLM API. Действительно автоматический runtime-тест отмечается отдельно от ручного MCP-сценария.
