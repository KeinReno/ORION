# Локальный разбор и упрощение первого запуска — 19.10.2026

Статус: отчёт конкретного локального среза, не новый roadmap. Приоритеты задаёт PLATFORM.md.
Первоначальный осмотр: `2fa6473`; перед изменением входа HEAD обновился до `331cef0` (PR #48–49).
Рабочая ветка: `codex/simple-local-start`. Код первого запуска описан ниже отдельно от исходного аудита.

## Вывод по направлению

ORION продвинулся от монолита с переключателями к проверяемой модульной платформе. В актуальном коде есть:

- 16 модулей, 48 встроенных плагинов, типизированные UI-слоты;
- регистрация модуля по манифесту, генератор `create:module`, пример Pet Care;
- версии контрактов (Platform API 1.1.0), реестр разрешений, диагностика компонентов;
- transactional outbox и диспетчер доменных событий;
- инструменты агента, объявляемые подключаемым модулем;
- библиотека тем, личные заметки и защита дочерних таблиц;
- локальный установщик с Node/PostgreSQL и встроенный обновлятор.

Старые формулировки аудита «нет событий / манифестов / генератора» уже нельзя использовать как текущую диагностику.
Но это ещё не полная Platform 1.0: компоненты поставляются сборкой, а не устанавливаются независимо из интерфейса.

## Что остаётся доделать, по порядку

1. **Закончить Stage 0.** Пройти установленный Windows-клиент: создание профиля, вход, рабочие панели,
   сохранение черновиков, открепление окон, DPI/мониторы, темы. Проверить отказ обновления, сохранность ввода,
   повтор после сбоя и восстановление. Большая новая функция не заменяет такую приёмку.
2. **Две реальные установки.** Пройти SYNC_TWO_INSTALL_ACCEPTANCE.md: LAN pairing, потеря связи,
   повтор отправки, конфликт правок, отзыв доступа, личные записи. Проверка двух браузеров на одном API
   не доказывает работу двух независимых установок.
3. **Данные и восстановление.** Отдельно подтвердить backup/restore всего узла (БД, файлы, ключи).
   Обновление EXE и откат схемы данных — разные операции. Для компонентов нужны версии данных,
   предварительная копия, контролируемое применение миграций и восстановление после сбоя.
4. **Модульность довести небольшими срезами.** Декларативное подключение плагинов, установка/обновление
   совместимых пакетов, реальные полномочия компонента и сокращение списка временных межмодульных исключений.
   Зелёный architecture-check сегодня допускает задокументированный долг из module-boundary-exceptions.mjs.
5. **ИИ и мобильность — после базовой надёжности.** Чат-ассистент уже есть, но это не весь Agent Hub.
   Orion Link, Android и Agent Hub пока проектные направления; у них нет автоматической готовности
   от наличия документации. Не создавать второй sync engine. Проверять небольшой вертикальный сценарий:
   запись на одном устройстве → доставка → применение на другом → видимый конфликт/результат.

Практическая цель следующей вехи: человеку понятно, как начать, его ввод переживает сбои,
данные восстанавливаются, а второй компьютер получает ровно разрешённые изменения.

## Конкретные наблюдения по коду

- Первоначально установленная beta.3 возвращала `applying` для тестового релиза; скрипт был создан,
  журнала выполнения не было. Пока шёл разбор, PR #48 изменил способ запуска скрипта. Поэтому
  первоначальное наблюдение **не считается доказательством дефекта текущего HEAD**.
- В `updates/update.service.ts` загрузка тела установщика не имеет собственного timeout/отмены;
  таймауты есть у запросов метаданных. Нужен тест зависшего/оборванного тела и восстановление состояния.
- `updates/apply-script.ts` принудительно завершает окна, а кнопка установки не проходит через общий
  реестр несохранённого ввода. Предупреждение текстом не заменяет проверку и сохранение/отмену.
  Отдельно проверить код выхода установщика и успешный запуск новой версии.
- `ascii-path.cjs` использует общий каталог копии PostgreSQL в ProgramData и меняет ACL его родителя.
  Нужна проверка двух Windows-пользователей, кириллицы и разных версий runtime. Это вывод из кода,
  не воспроизведённый в этом разборе отказ на второй учётной записи Windows.
- На свежем Windows-кластере с TimeZone Europe/Moscow первоначальный полный интеграционный запуск
  дал падения двух тестов domain-events. Итог всего запуска не был сохранён при смене запроса.
  Проверить отдельно сравнение `TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP` и времени Node/Prisma,
  а также гонки диспетчера; причина этим отчётом не установлена.
- Ассистент пока хранит диалог в состоянии панели, а не как восстанавливаемую беседу. Проверка
  настоящего провайдера и платных запросов в этом разборе не выполнялась.

## Решение по первому запуску

Пользователь явно выбрал чистый старт: старые аккаунты и данные больше не нужны;
новый профиль, пространство и проект он создаёт сам.

Краткий продуктовый brief:

- Пользователь: владелец своего Windows-компьютера.
- Задача: открыть ORION и начать с собственной учётки, без почты и предсозданного «Владельца».
- Результат: имя + PIN → своё пустое пространство → свои проекты; повторный вход — PIN.
- Последствие изменения UI: изменяется первый запуск и выбор профиля; существующие данные не мигрируются кодом.
- Очистка текущей машины — отдельное явно разрешённое действие; она не выполняется при обычном обновлении приложения.
- Серверная политика продолжает проверяться API; локальная форма не отменяет строгую политику сервера.

Решения: `rule/smallest-intervention` (правильные defaults), `rule/cover-reachable-states`
(0/1/несколько профилей, ошибка, загрузка), `rule/name-object-scope-consequence`
(отдельное согласие на очистку), `rule/keyboard-complete-flow` (PIN с клавиатуры и экранных кнопок).

Что изменено:

- один локальный профиль сразу выбран для разблокировки; список остаётся доступным через «Другой профиль»;
- PIN можно набрать клавиатурой, вставить или ввести экранными кнопками; четвёртая цифра отправляет вход;
- локальная регистрация предлагает имя и PIN, без поля email; пароль остаётся альтернативой;
- убран рекламный блок с техническим текстом из регистрации;
- интерфейс регистрации не создаёт пространство сам; API сохраняет прежнее поведение при отсутствии нового флага;
- первое пространство создаётся явной формой, пустой шаблон выбран по умолчанию;
- убрана навязчивая команда создания заполненного пространства ORION;
- импорт и приглашение спрятаны в раскрываемый дополнительный раздел.

## Проверки

- До изменения входа на `2fa6473`: typecheck, lint (26 предупреждений), architecture-check,
  plugin-contract-check, module registry, module docs — прошли; 1328 unit-тестов прошли
  с `--maxWorkers=2 --testTimeout=30000`; обычный массовый запуск упёрся в таймауты worker-процессов.
- На том срезе `pnpm build` прошёл (50 страниц), все 133 миграции применились к отдельной свежей PostgreSQL.
- После изменения входа на базе `331cef0`: 1331 unit-тест, 26 интеграционных тестов login-policy
  и shared-workspaces — прошли. Typecheck, lint (0 ошибок), architecture-check, plugin-contract-check,
  module-docs:check и module-registry --check — прошли.
- Отдельный тест проверяет регистрацию без почты и автопространства, самостоятельное создание
  пустого личного пространства и последующий вход по PIN. Существующие сценарии личного/общего
  доступа и политики local/home/strict сохраняются в интеграционном прогоне.
- Визуальная проверка выполняется на синтетической базе, отдельно от очищенной установленной программы.
  Через браузер пройдены: создание PIN-профиля без email → создание собственного пустого пространства;
  повторный экран сразу показывает единственный профиль и PIN. После обнаруженной потери фокуса
  PIN-поле на время запроса переведено в readOnly вместо disabled.
- Собран автономный NSIS-пакет `v0.1.0-windows-beta.5` (база `331cef0` + локальные изменения этой ветки),
  первая установка завершилась кодом 0. Запущенный installed API: health/database ok,
  mode=local, loginPolicy=local, `GET /auth/accounts` вернул пустой массив.
- Финальная пересборка desktop-export + Tauri/NSIS с исправленным фокусом также прошла;
  повторная установка завершилась кодом 0. Побайтовая сверка установленного EXE со сборкой:
  размер одинаковый, различаются только три байта маркера типа упаковки (`UNK` → `NSS`),
  который Tauri патчит при упаковке NSIS; прочие байты совпадают.

Полный аудит всех состояний каждого экрана, все интеграционные тесты текущего HEAD,
реальный провайдер модели и два физических устройства **не подтверждены**.

Владелец отдельно подтвердил полный сброс старых аккаунтов и данных. Активные процессы штатно остановлены;
PostgreSQL остановлены через pg_ctl/scripts/postgres.mjs до очистки файлов.

- Сброшены `AppData/Local/com.orion.desktop` (включая старые сессии, базу и настройки узла),
  dev-кластер `infra/postgres/data`, локальные `.data`, старые тестовые/резервные каталоги в tmp.
- Демодистрибутив, два старых каталога установщиков, старая checkout-копия в Documents/Codex
  перенесены в Корзину. Дополнительные worktree сняты с регистрации; их коммиты/ветки сохранены в Git.
- Из-за ошибки штатного переноса оставшихся npm-кэшей их остатки изолированы в
  `tmp/obsolete-checkout-remnants-20261019/`; это не действующие установки.
  Тестовые данные/restore-rehearsal из этих остатков отдельно перенесены в Корзину.
- На рабочем столе оставлены текущая папка исходников `ORION` и ярлык установленного приложения.
  Устаревший ярлык остановки удалён в Корзину. NSIS-регистрация исправлена: InstallLocation указывает
  на `AppData/Local/ORION`, а не на прежний тестовый каталог.
- Безвозвратное рекурсивное удаление PowerShell отклонила автоматическая проверка (`blocked by policy`);
  использованы обратимые операции. Корзина не очищалась.

Профиль владельца, PIN, пользовательское пространство и проекты после сброса агентом **не создавались**.
