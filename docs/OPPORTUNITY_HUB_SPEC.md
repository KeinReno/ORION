## 1. Задача, результат и границы достоверности

**Задача пользователя:** находить подходящие вакансии и заказы, понимать причины выбора, готовить достоверные предложения и доводить взаимодействие до результата в одном пространстве ORION.
**Желаемый результат:** из списка возможностей пользователь получает проверяемое решение, черновик и историю дальнейших действий; ИИ-менеджер сокращает ручную работу в заданных границах.
**Последствия действий:** импорт копирует выбранные данные в пространство; редактирование меняет локальную версию; отправка раскрывает выбранные сведения внешнему получателю и может быть необратима. Эти операции имеют разные разрешения.

Личное использование и небольшая команда равноправны. Вакансия и заказ — два вида одной возможности с разными условиями и материалами ответа. Кандидат, участник ORION и подключённый внешний аккаунт — разные сущности.

Предыдущая концепция ChatGPT доступна только частично: пользовательские сообщения прочитаны, полные ответы возвращаются ссылками-заглушками. Этот документ задаёт явные решения для реализации, а не объявляет восстановленной прежнюю концепцию.

## 2. Состав первой рабочей версии

Первая версия поставляется последовательными проверяемыми срезами. **R0 — полезный первый этап; R1 — завершённая первая версия ИИ-менеджера. R0 нельзя называть готовым R1.**

| Срез | Обязательный результат |
| --- | --- |
| R0.1 — Base | Вакансии/заказы: создание, чтение, правка, поиск, фильтры, статусы, архив/восстановление, экспорт |
| R0.2 — Профили и импорт | Профили людей/команды, версии материалов, предварительный просмотр и импорт HH с происхождением и дедупликацией |
| R0.3 — Ассистент | Сопоставление требований с подтверждёнными фактами, объяснение результата, черновики, пробный запуск |
| R1.1 — Управляемый HH | Подключение аккаунта и локального исполнителя; отправка конкретного согласованного отклика; доказательства и сверка |
| R1.2 — ИИ-менеджер | Постоянные лимиты, ограниченная автономность, остановка/возобновление, обработка неопределённого результата, отчёт |
| R1.3 — Приёмка | Личный/командный режим, права, backup/restore, выключенные расширения и живая проверка выбранного HH-сценария |

Для заказов в R1 обязательны ручной захват, оценка, черновик предложения и ручная фиксация взаимодействия. Автоматическая отправка на произвольные биржи не входит в R1: у каждой площадки нужен отдельный проверенный адаптер.

За пределами R1: marketplace, загрузка стороннего кода, обход CAPTCHA/защиты, автономные платежи, массовые рассылки, полноценная ATS работодателя, управление наймом сотрудников, автоматические переговоры о цене/зарплате, бесконфликтная двусторонняя offline-синхронизация.

## 3. Владение модулем и расширениями

Технический ID модуля: `opportunities`; подпись: «Возможности»; продуктовая конфигурация: KAIDEN Opportunity Hub. Это дополнительный предметный модуль, а не новый Core и не форк ORION.

| Владелец | Обязанности | Поведение при отключении |
| --- | --- | --- |
| Base `opportunities` | Возможность, её условия, источник/происхождение, жизненный статус, минимальные журнал/поиск/экспорт | UI/API и задания блокируются; данные сохраняются |
| `opportunities-profiles` | Профили, доказанные факты, треки, версии резюме/портфолио и выбор профиля | Base остаётся пригодным для ручного списка; материалы сохраняются |
| `opportunities-hh-import` | Адаптер файлов HH, mapping, preview, импорт исторических журналов | Уже импортированные карточки доступны без плагина |
| `opportunities-assistant` | Оценки, черновики, план действий, доменные правила автономности | Чтение Base доступно; генерация и агентские действия остановлены |
| `opportunities-hh-browser` | Подключение HH, чтение/отправка, доказательства, сверка через локального исполнителя | Новые внешние действия блокируются; история доступна |
| Module Bridges | Связи с Tasks, Calendar, Documents, Notes, Projects | Недоступная связь скрывается/блокируется, исходные данные сохраняются |

Каждый плагин расширяет ровно `opportunities`. Bridges используют публичные контракты, не внутренние сервисы/таблицы соседей. Профили и импорт нужны в продуктовой конфигурации Hub, но не обязательны для полезности Base.

Base не импортирует конкретные плагины. Внешние операции не входят в Core AI. Core сохраняет общие auth/workspaces/storage/реестры; доменные правила и специализированное исполнение принадлежат Hub.

### 3.1. Включение и defaults

Текущая модель модулей ORION включает отсутствующий в `disabledModules` ID. В R0 не менять этот механизм побочно: новая панель доступна как обычный модуль; существующие данные и панели не мигрируют по смыслу. Если потребуется opt-in самого модуля, это отдельное решение и миграция defaults.

Новые плагины по умолчанию выключены. Действие «Настроить Opportunity Hub» явно включает выбранные расширения в текущем пространстве. ИИ-менеджер и внешняя отправка не включаются автоматически, даже если включён весь профиль Hub.

Выключение профилей блокирует новые действия, которым нужен профиль; внешнее исполнение требует также включённого ассистента и подтверждённой версии материалов. Выключение любого необходимого компонента инвалидирует ещё не исполненные разрешения. Состояние проверяется сервером, а не только UI.

## 4. Пользователи, профили и права

### 4.1. Два равноправных сценария

**Личный:** человек ведёт свои вакансии и заказы; может хранить несколько профессиональных треков. Включение другого профиля никогда не выбирает автоматически его аккаунт HH.

**Командный:** общее пространство ведёт возможности студии, предложения и ответственных; личные резюме по умолчанию размещаются в отдельном личном пространстве. Если человеку нужна работа от имени кандидата в общем пространстве, профиль явно получает видимость `workspace` после предупреждения о доступе участников.

R0/R1 не обещают приватность отдельной карточки внутри общего пространства при одной только workspace-RLS. Гранулярное скрытие полей/профилей потребует отдельного ACL-контракта. Приватные browser credentials остаются у владельца подключения и не становятся общими с публикацией профиля.

### 4.2. Минимальные роли

| Операция | Кто может |
| --- | --- |
| Читать возможности и общие профили | Участник с доступом к модулю; при restricted-модуле — по текущим правилам ORION |
| Создавать/править карточки, архивировать, готовить черновики | Участник с правом записи; агент только с отдельным scope |
| Настраивать модуль/плагины, общий экспорт и импорт | Владелец пространства; возможная роль lead — только через явную проверку контракта |
| Подключать внешний аккаунт | Человек-владелец аккаунта; привязка подтверждается в UI |
| Разрешать внешнюю отправку/политику автономности | Владелец подключения с текущим правом записи в пространстве |
| Исполнять отправку | Зарегистрированный исполнитель под ограниченным capability grant |
| Удалять профиль с персональными материалами | Владелец пространства через явный preview; по умолчанию предлагается архив |

Токен ORION, назначение ответственным или включённый плагин сами по себе не дают права использовать чужой аккаунт. Ревокация токена, выход из пространства, ограничение модуля и отзыв подключения перепроверяются перед исполнением.

## 5. Предметные данные

Все доменные сущности имеют `id`, `workspaceId`, `createdAt`, `updatedAt`; изменяемые — `revision` для optimistic concurrency. Идентификаторы пользователя и агента фиксируются отдельно в аудите.

| Сущность | Обязательные поля и смысл |
| --- | --- |
| `Opportunity` | `kind: job\|contract`, title, organizationName, description, sourceType, canonicalUrl?, externalId?, status, conditions, archivedAt?, revision |
| `OpportunitySource` | Название/тип источника и public metadata; никаких cookies/паролей |
| `OpportunityCapture` | opportunityId, capturedAt, sourcePath/URL, fileHash/contentHash, schemaVersion, sanitized snapshot, historical flag |
| `CandidateProfile` | displayName, kind `person\|team`, workspace visibility, ownerUserId?, preferences, archivedAt, revision |
| `ProfileFact` | profileId, утверждение, категория, состояние `unverified\|confirmed\|disputed`, источник и дата подтверждения |
| `PositioningTrack` | profileId, название роли/услуги, подтверждённые factIds, предпочтения, исключения |
| `MaterialVersion` | profileId/trackId, тип `resume\|portfolio\|proposal`, content или ссылка Documents, immutable version/hash, provenance |
| `OpportunityAssessment` | opportunityId, profileId/trackId, source/profile/rules/model версии, hard exclusions, must-have/matches/gaps, score и rationale |
| `ResponseDraft` | opportunityId, profileId, materialVersionIds, cover/proposal text, answers, факты-основания, state, revision |
| `InteractionAttempt` | action, opportunity/profile/connection IDs, idempotencyKey, payloadHash, grantId, state, evidenceRefs, timestamps |
| `HistoricalInteraction` | Исходный статус/текст/дата, importRunId, sourceRecordHash, mapped state; отдельно от новых попыток |
| `ImportRun` | adapter/schemaVersion, manifestHash, previewVersion, target workspace, actor, counts/errors, state, appliedAt |
| `AutonomyPolicy` | Профиль/подключение, режим, allowlist действий, лимиты/таймзона/quiet hours, условия, expiry, revision |
| `ActionGrant` | Одноразовое или ограниченное разрешение на неизменяемый payloadHash; человек, scope, срок, состояние |
| `ExecutionJob` | Доменные параметры, attemptId, lease/heartbeat, runnerId, policyVersion, state; без browser secret |

### 5.1. Условия возможности

Для вакансии: employmentType, workFormat `remote\|hybrid\|office\|unknown`, city/country, relocation, salary min/max/currency, salary period, gross/net/unknown, seniority, experience years, must-have/nice-to-have, deadline.

Для заказа: бюджет min/max/currency, fixed/hourly/unknown, предполагаемые deliverables, deadline, duration, skill requirements, ограничения географии/договоров. Не подменять бюджет заказа месячной зарплатой.

Неизвестное поле остаётся неизвестным. `0` не обозначает отсутствующую зарплату; верхняя граница диапазона не доказывает гарантированный доход. Денежные значения хранятся decimal/minor units, валюта — явным кодом. Конверсия валют требует отдельного источника и даты.

### 5.2. Изоляция и хранение

- Каждая workspace-таблица получает `ENABLE` и `FORCE ROW LEVEL SECURITY` плюс политику, совместимую с текущей ORION-RLS.
- Membership, доступность модуля/плагина и владельцы связанных ID проверяются внутри актуального контекста транзакции `PrismaService.withUser`.
- FK запрещают ссылку на профиль/черновик/источник другого workspace; где Prisma не выражает составную связь, нужна проверка и DB constraint.
- Наружу только Zod-валидированные DTO; поля Prisma/внутренние credentials не сериализуются целиком.
- Тяжёлые документы/скриншоты — через storage, без безразмерного base64 в JSON. Metadata и ссылка проверяются на права.
- Draft/assessment не перезаписывают оригинальные файлы HH. Новая версия материала создаёт новый snapshot.
- Для экспортируемых версий хранить происхождение и stable external keys, не использовать абсолютный путь ПК как идентификатор доменной записи.

## 6. Статусы и достоверность действий

### 6.1. Статус возможности

`new → reviewing → shortlisted → in_contact → interview_or_discussion → offer_or_agreement → won`.
Из любого активного состояния разрешены `rejected` и `closed`; обратный переход разрешён вручную с записью причины. Архивирование — отдельное `archivedAt`, не удаление и не новый бизнес-статус.

Для вакансии UI подписывает этапы «Переписка», «Собеседование», «Оффер», «Работа получена»; для заказа — «Переписка», «Обсуждение», «Согласование», «Заказ получен». Терминальные изменения не автоматически выводятся из вежливого текста.

Изменение статуса вручную не создаёт доказательства внешней отправки. Каждое изменение хранит старое/новое значение, actor и причину.

### 6.2. Статус исполнения

`draft → awaiting_approval → approved → queued → running → confirmed`.
Альтернативы: `rejected`, `canceled`, `failed_before_send`, `sent_unconfirmed`, `already_exists`, `needs_user_action`.

- `confirmed`: наблюдается новое соответствующее событие, связанное с аккаунтом, получателем и действием.
- `already_exists`: отклик существовал до текущей попытки; новые отправки +0.
- `sent_unconfirmed`: действие могло совершиться; повторная отправка запрещена до сверки.
- `failed_before_send`: доказано, что внешний submit не произошёл; допускается ограниченный retry.
- `needs_user_action`: вход, CAPTCHA, неизвестный вопрос, неверное резюме или изменившиеся условия; автоматическая отправка остановлена.

`success`, наличие iframe, текста в textarea или одного скриншота без связи с действием не достаточны для `confirmed`.

## 7. Импорт HH

### 7.1. Способы

R0: выбрать подготовленный пакет файлов/каталог в desktop; в web — загрузить поддерживаемые файлы. Удалённый API не читает произвольный `C:\...` на ПК пользователя. Локальный упаковщик читает HH и отдаёт sanitized manifest; исходники остаются неизменными.

Архив/пакет проверяется на path traversal, симлинки вне выбранного каталога, лимиты распаковки и тип содержимого. Предлагаемые лимиты R0: 100 МиБ входных данных, 10 000 записей; превышение объясняется до применения. Большие пакеты разбиваются на части.

### 7.2. Mapping

| HH | Назначение |
| --- | --- |
| Markdown/TXT резюме трёх людей | Раздельные профили и material versions; факты первоначально `unverified` |
| `Cover_Letters`, сопроводительные письма | Примеры/исторические материалы, не утверждённые новые отклики |
| `vacancies_*.json`, списки/детали Варвары | Capture и Opportunity; адаптер поддерживает разные исходные shapes явно |
| `applications/*.json`, `applications_log.json` | HistoricalInteraction; cross-file дедупликация; исходный claimed status сохраняется |
| `autonomous_decisions.jsonl`, sessions | Исторические оценки/ошибки, не действующие задания или разрешения |
| `gap_analysis`, rejection analysis | Аналитические заметки с датой и происхождением, не доказательства причин отказа |
| Матрица навыков | Возможные навыки и gap-каталог; не автоматическое подтверждение фактов |
| Учебные документы Егора | Материалы подготовки; bridge в Notes/Documents после проверки их доступности |
| PDF/DOC/RTF | Исходные вложения; извлечение по реальному формату, версия parser; ошибки видны |

Исключены по умолчанию: browser profiles, `hh_storage_state.json`, `browser_state.json`, cookies, Local Storage, `.autopilot.json`, диагностика мониторов, pycache, код Python/PowerShell, HTML page dumps, диагностические screenshots. Скриншоты действий выбираются отдельно и проходят preview: могут содержать персональные данные и URL с секретами.

Ни одного импортированного скрипта не исполнять. Никаких автоматических сообщений/подключений/новых откликов по импортированным правилам.

### 7.3. Предварительный просмотр и применение

1. Чтение и классификация создают preview: файлы, целевые профили, новые/дубли/конфликты/пропуски/ошибки.
2. Пользователь выбирает workspace, профили и категории. При общем workspace явно указано, кто увидит данные.
3. Preview фиксирует hashes исходников, parserVersion, target workspace, revision и выбор; срок действия — 24 часа.
4. Apply передаёт previewId, manifestHash и idempotencyKey; перепроверяет права, hashes и enabled-state. Изменившийся файл требует нового preview.
5. Каждая порция применяется транзакционно с устойчивым checkpoint. Отчёт различает committed rows и неудавшиеся записи; частичный результат не называется завершённым.
6. Повторное применение того же manifest не создаёт дублей. Изменение локального статуса/описания не перезаписывается новым импортом молча.

Dedup Opportunity: `(workspaceId, sourceType, externalId)` при наличии ID. Для HH ID извлекается только из валидного URL/поля. Tracking query удаляется из canonicalUrl. При отсутствии ID — нормализованный contentHash и список возможных совпадений; одинаковое название у разных компаний не равно дублю.

Dedup исторического действия: внешний event ID, иначе source record hash + candidate identity + vacancy ID + event type/time. Если уверенности нет, пометка `possible_duplicate`; не суммировать такие строки как новые подтверждённые отправки.

`verified` из HH импортируется как `legacy_claimed_verified`. Причина `already_applied` маппится в `already_exists`. Исторические данные без новых доказательств не становятся `confirmed` нового исполнителя. Не складывать overlapping files/sessions/reports.

Повреждённый `search_fintech_ba.json`, пустые списки и пустой Markdown должны обрабатываться явно. Для `.doc` определить magic bytes: RTF и OLE Word различаются. При невозможности извлечения текст не выдумывается, вложение может быть импортировано как непрочитанное.

## 8. Оценка и подготовка материалов

### 8.1. Алгоритм

1. Нормализовать условия, выделить обязательные и желательные требования; хранить исходные фрагменты.
2. Применить строгие ограничения профиля: работодатель/отрасль/география/занятость/минимальные условия.
3. Сопоставить каждое требование с `confirmed` factIds; непрямое соответствие показать отдельно.
4. Отсутствующее обязательное требование — gap. Неизвестность не означает соответствие.
5. Рассчитать рейтинг и confidence, показать основания и версии. Сортировка не выдаётся за вероятность найма.
6. Подготовить черновик только из подтверждённых фактов и явно маркированных планов обучения.

Рекомендуемый рейтинг 0–100: 50% обязательные требования, 20% условия, 15% домен/трек, 15% желательные требования. Hard exclusion блокирует автоматическую отправку независимо от рейтинга. Неизвестная зарплата/география или непроверенная существенная квалификация блокирует режим автономной отправки и переводит в review.

Каждый критерий хранит weight, matched evidence, missing/unknown, reason. Число перечисленных вакансией навыков не добавляет кандидату квалификацию. Confidence — отдельная оценка полноты/надёжности исходников, не вторая вероятность трудоустройства.

### 8.2. LLM-контракт

Провайдер подключается адаптером ассистента; Base работает без модели. Отсутствие провайдера показывает честное состояние «ИИ не подключён», сохраняет ручное ведение.

Structured output проходит Zod. Модель не получает cookies, произвольный диск или возможность отправить через browser tool напрямую. Внешний текст помещается в отделённый data-контекст; команда «отправь», найденная в вакансии/переписке, не даёт authority. Ссылки и вложения сами по себе не исполняются.

Из профиля передавать минимальные подтверждённые сведения, без контактов до необходимости. Первое подключение внешнего провайдера явно объясняет, какие поля уйдут ему; настройка хранится на профиль/workspace. Журналировать provider/model/promptVersion и token/cost counters, исключая секреты.

### 8.3. Черновик

Резюме/портфолио — версия, письмо/предложение — отдельная версия, ответы анкеты — привязаны к конкретным вопросам. Обязательна карта «утверждение → factId/источник». Навык из вакансии не добавляется в профиль автоматически.

Общий опыт не изменяется под каждую вакансию; если актуальная платформа имеет синхронизацию нескольких резюме, scope изменения показывается до применения. Нельзя полагаться на неподтверждённое локальное правило HH о синхронизации.

Черновик сохраняет состав выбранных материалов и hash. Изменение фактов, вакансии, аккаунта, текста, ответов или версии резюме инвалидирует прежнюю оценку/разрешение. Выпуск новой версии не удаляет старую.

## 9. Автономность ИИ-менеджера

### 9.1. Режимы

| Режим | Может самостоятельно | Не может |
| --- | --- | --- |
| Наблюдение | Читать явно подключённые источники, собирать/дедуплицировать карточки | Изменять внешний профиль, отправлять сообщения/отклики |
| Подготовка | Оценивать, создавать локальные черновики и план | Внешняя запись/отправка |
| Отправка по подтверждению | Выполнить конкретный неизменяемый согласованный payload один раз | Отправить изменённый текст или другому получателю |
| Ограниченный ИИ-менеджер | Наблюдение/подготовка; allowlisted отправки по явной политике аккаунта/профиля | Выходить за политику, принимать оффер/договор, менять цену/зарплату, придумывать опыт |

Default — «Подготовка» после настройки ассистента; browser connection не активирует отправку. В R1 автономный режим можно выпускать только после прохождения G11–G17 ниже. До этого он отсутствует как доступная операция, а не имитируется переключателем.

### 9.2. Политика

Обязательны: profileId, connectionId, allowed actions, allowed sources/domains, exclusions, min rating/confidence, обязательные fact IDs, дневной лимит, таймзона, минимальный интервал, quiet hours, срок действия, policyRevision, бюджет модели/задач.

Предлагаемые стартовые значения: максимум 5 внешних откликов в день на профиль и аккаунт; интервал не менее 180 секунд; Europe/Moscow для пользователя при создании, затем явная настройка; отправка ответов в чаты только по подтверждению. Это продуктовые defaults, не утверждение о правилах HH.

Неизвестные вопросы, выбор из конфликтующих резюме, изменение аккаунта, CAPTCHA/логин, неоднозначное условие и неподтверждённый факт останавливают конкретную цепочку. Повторные системные сбои ставят connection в pause после 3 последовательных неудач, с понятным восстановлением.

### 9.3. Постоянные ограничения

- Лимит хранится в PostgreSQL на `(workspaceId, profileId, connectionId, actionType, localDate)`; отдельный общий лимит аккаунта исключает обход несколькими профилями.
- Резервирование бюджета происходит атомарно до submit; параллельные процессы/рестарт его не сбрасывают.
- Попытка с возможной отправкой расходует reservation до сверки; `already_exists` не увеличивает newSent, но её проверка ограничена собственным rate budget.
- Разрешение и актуальные права перепроверяются непосредственно перед внешним submit. UI-галочка не является проверкой.
- Пробный запуск технически не получает capability внешней записи; конфигурация не может повысить его до send.
- Кнопка «Остановить» отзывает будущие grants, отменяет очередь и просит runner прервать операцию до submit. Уже отправленное не называется отменённым.

## 10. Локальный исполнитель HeadHunter

R1 не зависит от обязательного API HH. Минимум: ручной/файловый захват; расширение browser чтения/отправки работает через явно выбранный аккаунт. Будущий API-адаптер может реализовать тот же публичный контракт.

Для локальной установки runner работает на ПК пользователя; для общего сервера — отдельное зарегистрированное устройство владельца подключения с outbound HTTPS. Отсутствующий/спящий runner даёт `waiting_for_device`, не ложное выполнение. Server не открывает доступ к локальному CDP через интернет.

### 10.1. Подключение

Пользователь запускает подключение и вручную входит в HH. Пароль/MFA/SMS-код не собираются ORION и не передаются агенту. UI показывает распознанный аккаунт/профиль и просит связать его с выбранным CandidateProfile. Подключение имеет ownerUserId, runnerId и ограничение домена.

Browser secret хранится отдельно от импортируемых данных: локальное защищённое хранилище ОС либо одобренный credential adapter. В PostgreSQL только credentialRef/metadata. В backup/export секрет не попадает; восстановление требует нового подключения.

Перед каждым действием runner проверяет аккаунт, домен, нужное резюме по stable external ID и его version/hash. Подключение к «первой попавшейся вкладке HH» запрещено. Потеря сессии — пауза; тихого fallback в другой аккаунт нет.

### 10.2. Протокол задания

`actionType`, `attemptId`, `workspaceId`, `connectionId`, `profileId`, opportunity external ID, material IDs/hashes, точный payload, payloadHash, grantRef, expiry, leaseToken, contractVersion.

Runner не получает полномочие выполнять произвольную команду shell или загруженный Python. Разрешены только версии compiled-in adapter с фиксированными action types. Результат содержит typed state/error и evidence, без cookies/HTML всего аккаунта.

Generic AgentJob из AI Bridge может нести ссылку на доменное задание, но его текст/status не заменяет lease, payloadHash, права или доказательство исполнения. Не строить вторую общую шину сообщений ради Hub; специализированный executor использует публичный bridge к существующему AI там, где контракт достаточен.

### 10.3. Отправка и сверка

1. Перепроверить permissions, enabled-state, grant/policy, аккаунт, source/material revision, лимиты.
2. Зафиксировать baseline существующих откликов/сообщений; если уже есть — `already_exists`.
3. Найти конкретное резюме; если не найдено/обновление не подтверждено — остановиться.
4. Заполнить письмо/ответы, прочитать значения обратно и сравнить с утверждённым payload. Неизвестный вопрос нельзя заполнить общим ответом.
5. Перед click атомарно зарезервировать attempt и budget; повторно проверить отмену/grant.
6. Выполнить submit один раз; записать время и непосредственный результат.
7. Подтвердить новую запись/событие для того же адресата и аккаунта; где доступно — stable event/message ID, иначе связанный UI-переход + текст + время + скриншот.
8. Если браузер потерян после click — `sent_unconfirmed`; дальнейшее действие только reconcile, без автоматического повторного click.

Нельзя гарантировать exactly-once для внешнего UI без idempotency платформы. Цель — локальная идемпотентность, один конкурентный исполнитель и fail-closed при неопределённости. Скриншоты неизменяемы, имеют hash, timestamp и attemptId; одинаковое имя файла не перезаписывает доказательства.

Переписка анализируется по последнему входящему сообщению, sender/message ID и уже отправленным ответам. Собственный текст и полная история с вопросительным знаком не запускают повторный ответ. Автопринятие условий и согласие на оффер/договор отсутствуют.

## 11. Публичные контракты и API

Все пути ниже **проектируемые**, не существующие endpoints. Общий prefix человеческого API: `/workspaces/:workspaceId/opportunities`.

| Группа | Контракт |
| --- | --- |
| Base | `GET /`, `POST /`, `GET /:id`, `PATCH /:id`, `POST /:id/archive`, `POST /:id/restore`, `GET /export` |
| Profiles plugin | `/profiles`, `/profiles/:id/facts`, `/profiles/:id/tracks`, `/profiles/:id/materials` |
| Import plugin | `POST /imports/preview`, `GET /imports/:runId`, `POST /imports/:runId/apply` |
| Assistant plugin | `POST /:id/assessments`, `POST /:id/drafts`, `PATCH /drafts/:draftId`, `POST /drafts/:draftId/approve`, `POST /drafts/:draftId/reject` |
| Execution plugin | `/connections`, `POST /attempts`, `POST /attempts/:id/reconcile`, `POST /connections/:id/pause`, `/policies` |
| Domain runner | Версионированный `/opportunities-executor/v1`: claim, heartbeat, result; только capability auth, не обычный пользовательский JWT |

Перед созданием API уточнить route ordering (`export`, `profiles`, `imports` не перехватываются `/:id`). Пагинация cursor, default 50/max 200; фильтры kind/status/source/profile/archived/query. Сортировка stable `(updatedAt,id)`. Limit/query bounds валидируются.

PATCH требует `expectedRevision`; конфликт возвращает 409 и актуальную revision. Пустое изменение отклоняется. Submit/import требуют idempotencyKey, но повтор с другим payloadHash возвращает конфликт. Ошибки имеют стабильные codes и requestId без secret/raw HTML.

Предлагаемые AI scopes: `opportunities:read`, `opportunities:write`, `opportunities:assess`, `opportunities:draft`. Это новые scopes после отдельного контракта; `tasks:write`/`agents:delegate` их не заменяют. Внешняя отправка требует отдельного grant владельца подключения, а не расширенного универсального agent token. Существующие proposal actions удаления не переиспользовать для отправки.

События версии v1: `opportunity.created`, `opportunity.status_changed`, `opportunity.archived`, `draft.ready`, `attempt.needs_user_action`, `attempt.confirmed`, `attempt.sent_unconfirmed`, `import.completed`, `import.partial`, `policy.paused`. Общий envelope: eventId, schemaVersion, workspaceId, entityId, occurredAt, actor, sanitized payload. Доставка at-least-once предполагает idempotent consumers; если нужен transactional outbox, ограничить его данным срезом и отдельным proposal, не объявлять текущий Core готовой очередью.

## 12. Интерфейс

Использовать `@orion/ui`, существующий PanelShell/Workbench, токены и плотность ORION. Не менять оформление соседних модулей. Панель `opportunities` регистрируется в общей навигации; новые виды/действия расширений только через slots из ADR-0008.

### 12.1. Основной экран

- Заголовок «Возможности», одна основная команда «Добавить возможность».
- Видимые переключатели «Все / Вакансии / Заказы», строка поиска, фильтр статуса/источника; профиль доступен при включённом profiles plugin.
- Строка: название, организация, вид, условия, статус, источник/дата захвата; рейтинг только при наличии актуальной оценки.
- Полноценная карточка — в основной рабочей области; короткие свойства — в контекстном инспекторе по принятому UX ORION. На узкой панели список и карточка последовательно с возвратом.
- Карточка показывает исходный текст/условия, происхождение, материалы и историю. Работа с длинным черновиком не помещается в узкую шторку.

### 12.2. Импорт

Последовательность: выбор источников → preview/mapping → применение → отчёт. Один рабочий поток, без вложенных modal. Видны target workspace, профили и доступ участников, количество новых/дублей/ошибок, исключённые категории. Команда «Импортировать N записей в …» сообщает объект и scope.

### 12.3. Проверка ответа

Показываются аккаунт, получатель, вакансия/заказ, выбранная версия резюме, точный текст, ответы, gaps и обновляемые внешние поля. «Сохранить черновик» и «Разрешить отправку» — разные действия. Если платформа не позволяет письмо или требует изменение общего опыта, прежнее разрешение не подходит.

Разрешение привязано к payload; повторное редактирование возвращает состояние «Требует проверки». Для отправки важна дополнительная защита от double-submit и понятный pending, а не длинная церемония для обычной локальной правки.

### 12.4. Состояния

| Состояние | Обязательное поведение |
| --- | --- |
| Loading | Стабильная геометрия, понятный предмет загрузки |
| Empty | «Добавьте вакансию или заказ» + доступная первая команда |
| Empty filtered | Объяснение активных фильтров и сброс; не выглядит как отсутствие данных |
| Error | Причина при наличии и «Повторить»; введённый текст сохранён |
| Forbidden/disabled | Объяснить недоступность, не показывать старые данные из другого workspace |
| Partial import | Количество сохранённого и оставшегося, список ошибок, повтор только неуспешного |
| Stale assessment | Версия исходников изменилась, пересчитать; старая оценка видна как историческая |
| Offline/device missing | Локальные черновики читаются, внешние действия ждут устройства |
| Sending | Disable повторной отправки; не писать «отправлено» до результата |
| Sent unconfirmed | «Отправка требует проверки» + сверить; новой отправки нет |
| Archived | Возврат из архива; history/materials сохранены |

Все основные операции выполняются клавиатурой, focus видим и возвращается при закрытии overlay. Контролы имеют доступные имена, статус не передаётся одним цветом. Длинные русские названия/URL, 320px и узкая dock-панель не создают недоступных действий.

### 12.5. Основания продуктовых решений

| Решение | Основание |
| --- | --- |
| Одна основная команда, повторное использование оболочки | UX ORION; `rule/one-primary-action`, `rule/smallest-intervention` |
| Видимый выбор вида возможности | `rule/control-matches-cardinality` |
| Карточка/preview сохраняют контекст, нет вложенных modal | UX ORION; `rule/inline-before-modal`, `rule/no-nested-modals`, `rule/preserve-mental-model` |
| Отдельные импорт/правка/отправка с точным scope | `rule/name-object-scope-consequence`, `rule/destructive-proportional` |
| Ошибка/частичный результат/потеря устройства и сохранение ввода | `rule/cover-reachable-states`, `rule/preserve-user-input`, `rule/error-states-recovery` |
| Начальное пустое состояние с действием | `rule/empty-state-action` |
| Клавиатура, семантические действия/ссылки и focus | `rule/keyboard-complete-flow`, `rule/accessible-name-required`, `rule/navigation-vs-action`, `rule/no-custom-focus-bypass` |

Coverage gap: правила product-design не задают отраслевую модель подтверждения внешней browser-отправки; её проверяемый контракт определён разделами 6, 9, 10 и G11–G17. Не выдавать его за готовый стандарт HH.

| Search/Notifications | Public providers с membership/enabled checks; нет обхода доступа через результаты поиска и уведомления |

Если bridge API/slot отсутствует, зарегистрировать Extension Proposal; не вводить внутренний import соседнего сервиса ради сокращения реализации.

## 14. Backup, экспорт и эксплуатация

Каждая новая Prisma-модель классифицируется в `apps/api/src/sync/snapshot-registry.ts`. Порядок восстановления учитывает FK; восстановление не запускает external jobs.

Backup включает возможности, captures, профили, факты, версии, историю/оценки/черновики и доменные policies как paused. Не включает browser credentials, runner tokens, одноразовые grants, активные leases, текущие разрешения отправки. Очередь после restore становится canceled/needs_review; внешняя отправка не возобновляется автоматически.

Экспорт Base — версия JSON/CSV с происхождением; экспорт Hub отдельно включает выбранные профили/материалы. CSV защищён от formula injection. Секреты и диагностические HTML не экспортируются. Скриншоты включаются только явным выбором.

Исторический аудит действий неизменяем при обычной правке. Хранение доказательств управляется явной политикой retention; удаление attachment оставляет отметку, hash и причину удаления, не переписывает историю успеха. Архивирование и выключение не удаляют данные. Полное удаление/псевдонимизация профиля — отдельный preview с перечнем зависимостей и ограничением доступа к оставшимся персональным снимкам.

Health: доступность БД/runner/подключения/провайдера, last heartbeat, возраст source snapshot, pauses, лимиты. Не включать HH session/cookies в лог. LLM-бюджет и внешние лимиты сохраняются через рестарт. Поиск/импорт с пагинацией, время и потребление памяти измеряются на реальном тестовом наборе.

### 15.1. Порядок и handoff

1. Принять ADR/контракты, зафиксировать UI/defaults baseline соседних панелей.
2. R0.1: schema/DTO/RLS/API/клиент/UI/export; проверка disabled/restricted.
3. R0.2: профили и неизменяемые материалы; импорт preview/apply/retry; отдельный импорт HH только после выбора пользователя в UI.

5. R1.1: connection/runner/grants; один reviewed отклик и reconcile.
6. R1.2: политики/постоянные лимиты, чат с message IDs, остановка/рестарт.

Каждый срез получает MODULE/AI_CONTEXT, решение/ограничения, проверенные команды/результаты и оставшиеся критерии. Следующий агент сначала сверяет git status/history и actual contracts; старое ТЗ не считается доказательством готовности.

### 16.1. Измеримые нефункциональные ориентиры

- На согласованном локальном тестовом ПК: 10 000 opportunities/3 profiles; API страницы 50 строк p95 ≤500 мс после прогрева, исключая внешнюю сеть.
- Импорт 10 000 normalized records ≤60 секунд и ≤512 МиБ дополнительной памяти; замеры указывают оборудование/форматы, binary extraction отдельно.
- Local pause ack ≤2 секунд при живом runner; offline runner блокируется revocation/expiry при следующем claim, не считается немедленно остановленным физически.
- Lease 60 секунд, heartbeat не реже 15 секунд; эталонный runner проверяет остановку каждую секунду. Истёкший lease после возможного submit требует reconcile, не нового send.
- Подтверждение отправки не имеет обещанной скорости/доступности внешней платформы; timeout классифицируется по месту сбоя.

Ориентиры — критерии будущего измерения, не существующие результаты и не SLA HH.

## 17. Открытые решения и состояние

Разрешено начинать R0 по этому документу после принятия соответствующих контрактов. Неясность полной старой концепции не мешает ручному модулю; при получении её текста различия оформляются новой версией, а не скрытой заменой требований.
