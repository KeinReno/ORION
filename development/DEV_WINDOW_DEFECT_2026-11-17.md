# DEV-WINDOW DEFECT — окно десктопа появляется и умирает (2026-11-17)

## РАЗГАДКА (вечер 17.11)

1. **Stack overflow главного потока — виноват GamePP** (сторонний оверлей, внедряется во
   все процессы; в логах каждого краша — `fail CreateFileMapping GAMEPP-IPC-OVERLAY`).
   С выключенным GamePP процесс стабилен: краша нет, окно живёт.
2. **Чёрное окно без содержимого** — вебвью процесс (msedgewebview2.exe) для приложения
   вообще не создаётся (проверено: 0 дочерних webview-процессов, 0 подключений к dev-серверу,
   свежий профиль %LOCALAPPD%\com.orion.rust.desktop\EBWebView не помог, системный прокси
   127.0.0.1:16757 — нет: `curl -x` через него в localhost виснет, но `--proxy-server=direct://`
   чёрный экран не убрал). WebView2 Runtime установлен (157.0.4341.60), другие webview-приложения
   работают. Причина не найдена — глубже копать Tao/wry (wry = webview бэкенд Tauri).
3. Вывод: **dev-окно на этой машине пока недоступно; рабочий путь — браузер** (см. обходной
   путь). Для нативного выбора папки встроен **обзор каталогов в самом приложении**
   (`GET …/repositories/browse`) — одинаково работает в браузере и в окне, путь не печатается.

## Симптом (исторически)
`orion-desktop.exe` запускается, главное окно появляется на секунды и исчезает;
процесс остаётся висеть без окон (только `com.orion.rust.desktop-siw` и
`Tao Thread Event Target`); повторные запуски иногда падают с
`0xC0000005 (STATUS_ACCESS_VIOLATION)` или завершаются с кодом 1.
Наблюдается и в `tauri dev` (debug), и в собранном `target\release\orion-desktop.exe`.

## Что исключено

- Мои изменения не причина: симптом предсуществует коммиту 047b8826 (16.11,
  «fix dev-mode window loading devUrl» — тогда же описан «no window ever appeared
  in development», т.е. окно в dev в этой копии до этого вообще не доходило).
  Плагин dialog (2.7.3) совместим с tauri 2.11.5; `cargo check`/`tauri build` чистые.
- Конфликта с установленной бетой нет: идентификатор этой копии
  `com.orion.rust.desktop`, single-instance не срабатывает.
- Крэш-дампов WebView2 (Crashpad reports/attachments) нет — вебвью не падает как процесс.
- Кодовый путь, закрывающий главное окно, в main.rs не найден
  (on_window_event закрывает только дочерние окна; run-handler exit — release-only).
- Отложенное появление окна не подтверждено ни разу за ~20 наблюдений через
  UIAutomation/`agent-desktop list-windows`.

## Ключевые наблюдения

- Диагностика сразу после `window.build()` в setup(): `hwnd=Err(Unavailable)`,
  `size/visible/title=Err(FailedToReceiveMessage)` — ожидаемо для фазы setup
  (цикл событий ещё не крутится), само по себе не диагноз.
- В логе после «window built» ничего нет: ни webview-навигации, ни ошибок.
- Процесс не завершается при потере окна в debug (exit-handler скомпилирован
  только под release) — поэтому «зомби без окон».

## Гипотезы (не проверены)

1. WebView2 умирает молча при навигации на dev-сервер (localhost:3011):
   FailedToReceiveMessage похож на умерший канал вебвью. Проверить: открыть
   exe с `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--disable-gpu`, смотреть
   `chrome://gpu`-эквивалент; либо подменить devUrl на about:blank и смотреть,
   живёт ли окно.
2. Окно создаётся в невидимом состоянии и его показывает код, который в dev
   не вызывается (release-only startup flow). Проверить: `visible:` в конфиге
   окна tauri.conf.json при старте + `window.is_visible()` из on_page_load.
3. Окно-вспышка через launcher vs отсутствие через Start-Process — различие
   window station/наследования консоли. Проверить: запуск exe интерактивно
   (двойной клик) и наблюдение.

## Обходной путь

Веб-приложение полностью работоспособно в браузере: `pnpm dev:api` (:14000) +
`pnpm dev:web` (:3011) → http://localhost:3011. Единственное ограничение —
кнопка «Выбрать папку…» (Tauri dialog) в браузере скрыта, остаётся ручной ввод
пути; всё остальное (регистрация, «Создать репозиторий здесь», карта, git)
работает.

## Заодно починено в этой сессии (предсуществующее)

- `scripts/launch-desktop.mjs`: проверка готовности postgres через
  `docker exec orion-postgres pg_isready` отвергала любой не-docker postgres;
  теперь TCP-подключение к host:port из `apps/api/.env` (DATABASE_URL).
- Порты лаунчера приведены к портам рабочей копии: API :14000, web :3011
  (были :4000/:3010 установленной беты — коллизия и мёртвый опрос).
