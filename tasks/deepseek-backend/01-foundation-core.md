# 01 — Foundation Core: единая модель связей, события, lifecycle модулей

**Зона ответственности:** ядро платформы (`apps/api/src/entity-links/` (нов.),
`apps/api/src/domain-events/`, `apps/api/src/modules/`, Prisma-блок `BEGIN 01`).
**Волна:** 1. **Никакого фронтенда.**

## Контекст

План (разделы 3, 25 переписки) требует: единую модель связей сущностей,
событийную систему с подписками модулей, корректный жизненный цикл модулей
(выключенный модуль не выполняет фоновую работу) и механическую защиту
архитектурных границ.

Уже есть: модель `EntityLink` в схеме (связи между сущностями с типом),
`domain-event-bus` с outbox (`DomainEvent`, `DomainEventDelivery`),
реестр модулей `apps/api/src/modules/` с guard'ами включения.

## Задачи

### 1.1. Единый сервис связей (entity-links)

- Сервис `EntityLinksService` (новый NestJS-модуль, Core-уровень): create/list/
  delete связи с типами `blocks | depends_on | relates_to | continues | replaces |
  duplicates | references`. Типы — enum в БД (миграция), значения не хардкодить
  строками по всему коду.
- Направленность: `fromEntity`/`toEntity` + опциональный `bidirectional` флаг
  для `relates_to` (парность не дублируется — по образцу `ProjectRelation`).
- Инварианты: обе сущности существуют и принадлежат одному workspace; запрет
  самосвязи; запрет циклов для `depends_on`/`blocks` (проверка в транзакции);
  каскадное поведение при удалении сущности — связь удаляется, но не вторая
  сторона.
- Публичный SDK-контракт для модулей: другие модули используют только этот
  сервис, не свои таблицы связей. Существующие специализированные связи
  (TaskDependency, ProjectRelation, KnowledgeRelation) **не трогать** — это
  доменные контракты; EntityLinks — универсальный слой для новых связей.
- Permissions: `entity-links.read`, `entity-links.manage`; операции через audit
  (кто/когда/что).
- Domain events: `entity_link.created` / `.deleted` с payload {type, from, to}.

### 1.2. Событийная система: подписки модулей

- Типизированный каталог доменных событий: реестр допустимых `type` с версией
  payload (`eventType + payloadVersion`), регистрация из модулей через
  декоратор/провайдер, централизованная валидация payload zod-схемой при публикации.
- Подписки: модуль регистрирует handler'ы на типы событий; dispatcher доставляет
  только включённым модулям; ошибка handler'я одного модуля не блокирует
  остальных (изоляция + журналирование в `DomainEventDelivery`).
- API диагностики: состояние outbox (pending/failed/delivered, возраст) —
  endpoint для будущего Resource Monitor / диагностики.
- Ретраи: экспоненциальная задержка с потолком, dead-letter состояние после N
  попыток, ручной replay endpoint.

### 1.3. Жизненный цикл модулей

- Реестр фоновых заданий модуля: декларативная регистрация (cron/interval/
  on-event задачи) через модульный провайдер; supervisor останавливает задачи
  выключенного модуля и возобновляет при включении; состояние видно через API.
- При выключении модуля: фоновые задачи остановлены, обработчики событий
  отписаны, данные и настройки сохранены (повторное включение восстанавливает).
- Проверить и закрыть: существующие фоновые процессы (напоминания, outbox
  dispatcher, sync) корректно учитывают module-enabled guard.

### 1.4. Архитектурный CI-гейт

- `pnpm architecture-check` — обязательный шаг в `.github/workflows/ci.yml` и
  `ci-selfhosted.yml` (существующие файлы, править точечно); при падении —
  fail job.
- Проверить, что `plugin-contract-check`, `module-docs:check`,
  `platform-map:check` также присутствуют как обязательные шаги; если нет —
  добавить.

## Критерии приёмки

1. Все новые связи создаются/читаются только через EntityLinksService; циклы
   `depends_on` невозможны (тест с попыткой цикла → 409/422).
2. Handler выбрасывающий модуль не влияет на доставку остальным (интеграционный
   тест с двумя подписчиками).
3. Выключение модуля останавливает его фоновые задачи (тест: тикающая задача
   перестаёт тикать; включение — возобновляется).
4. Обязательные проверки из `00-README.md` зелёные; миграции применяются с нуля.
5. Отчёт-блок в `docs/STATUS.md`.
