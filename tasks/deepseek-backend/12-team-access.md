## Контекст

Уже есть: `Workspace`, `WorkspaceMember`, `WorkspaceInvite`, `CrossWorkspaceGrant`,
роли и permission-проверки, плагин `team` (defaultEnabled: false — дефолт НЕ

уведомления, изоляция личных/общих данных.

## Задачи

### 12.1. Разделение principal-моделей

- Ввести явную модель principal: `kind: human | agent` на уровне членства —
  членство агента = ссылка на `AgentHubAgentProfile`, членство человека — на
  `User`; одна таблица членства с дискриминатором (миграция существующих
  human-членов без изменения семантики).
- Модели полномочий раздельны: permission-check обязан знать principal kind;
  агент никогда не получает прав human-по-умолчанию (нет «наследования» прав
  создателя); agent-права — только через scope-аренду (ADR-0007) + явные grants.
- API команды: `GET /workspaces/:id/members` — единый список с kind, статусом
  (active/invited/disabled), ролью; фильтры по kind.

### 12.2. Приглашения

- Расширить `WorkspaceInvite`: роль при приглашении, срок действия (default 7
  дней, nullable = бессрочно — как у agent-аренды, скрытых дефолтов нет),
  отзыв до принятия, повторная отправка, audit (кто пригласил/отозвал).
- Агент-«приглашение» = подключение профиля через существующий owner-control
  flow (ADR-0047) — НЕ дублировать; здесь только отображение в списке членов.

### 12.3. Комментарии, упоминания, уведомления

- Упоминания `@name` в `TaskComment` (и ProjectLogEntry — задание 05
  использует ту же механику, согласовать формат парсинга): парсинг при записи,
  создание `Notification` для упомянутых (human — в ленту; agent — в его
  очередь событий Agent Hub), защита от упоминаний вне пространства.
- Изоляция: уведомления не раскрывают содержимое объектов, к которым у
  получателя нет доступа (проверка прав при чтении уведомления).

### 12.4. Одновременное редактирование

- Унифицировать optimistic concurrency для ключевых сущностей (Task, Note,
  Project, KnowledgeItem): версия `updatedAt`-etag по существующему CAS-паттерну;
  конфликт → 409 с текущей версией в ответе; endpoint разрешения не требуется —
  последняя явная правка побеждает (фиксация решения: merge-ui не вводим).
- Существующие механики CAS (publications, sync) не менять — привести
  задачи/заметки к общему контракту.

## Критерии приёмки

1. Агент-член с правами read не может выполнить мутацию, даже если создатель —
  owner (интеграционный тест); ошибка указывает на отсутствие scope, а не 500.
2. Приглашение: истёкшее не принимается (410/409 с причиной), отзыв до
   принятия работает, audit записан (тесты).
3. Упоминание создаёт уведомление только для членов пространства; уведомление
   без прав на объект не раскрывает его содержимое (тесты).
4. Параллельные правки одной задачи → второй получает 409 с etag (тест на
   двух клиентах).
5. Проверки из `00-README.md` зелёные; миграции с нуля PASS; team plugin
   defaultEnabled: false — не изменился (plugin-contract-check).
6. Отчёт-блок в `docs/STATUS.md`.

## Out of scope

Фронтенд (экран команды, приглашения UI), real-time collaboration (CRDT,
websockets — отдельное решение), внешний доступ вне LAN (Orion Link — отдельный
модуль), пересмотр CrossWorkspaceGrant semantics, биллинг/квоты.
