# 11 — Orion Dev + Git Workspace + MCP-доступ инструментов (backend)

**Зона ответственности:** `apps/api/src/development/**`,
`apps/api/src/mcp/**` (точечно), Prisma-блок `BEGIN 11`, миграции, тесты.
**Волна:** 3. **Никакого фронтенда.**
Локальные документы: `adr/ADR-0046-development-workspace-overview.md`,
`adr/ADR-0045-development-review-apply.md`, `docs/DEV_KIT.md`,
`docs/AGENT_MANUAL.md`.

## Контекст

Orion Dev существует (обзор направлений, import с consent/apply, атомарный
apply — ADR-0045/46). MCP есть (Agent Gateway, аренда, scope-ceiling).
План (разделы 10–12, 16 переписки): Git Workspace (интерактивное дерево),
Architect (анализ репозитория, данные для 2D-редактора), полный маршрут
поручения человека → план → исполнение → проверка → приёмка, и доступность
инструментов Orion агентам через MCP.

## Задачи

### 11.1. Git Workspace (backend)

- Сервис чтения локальных репозиториев: обёртка над системным `git`
  (child_process; путь к репозиторию — только из разрешённых корней:
  каталоги проектов Orion Dev, заданные владельцем; защита от выхода за пределы).
- API: `GET /development/git/:repoId/graph` — ветки, коммиты (sha, author,
  date, message), слияния, теги, PR-заглушка (null, если внешний провайдер не
  подключён); `GET .../compare?from=&to=` — список отличающихся коммитов и
  файлов (diffstat); фильтры по автору/ветке/дате; пагинация по истории
  (cursor по sha).
- Кэширование графа в памяти с инвалидацией по `git reflog`/mtime .git;
  тяжёлые репозитории — лимиты (max N коммитов на запрос, default 500).

### 11.2. Привязка коммитов к задачам Orion

- Конвенция + ручная привязка: из message парсится `#<taskRef>` (настраиваемый
  префикс) → `TaskCommitLink`; без ссылки в message — ручной link/unlink
  endpoint (permission `tasks.manage`).
- Путь задачи: `GET /tasks/:id/trace` — цепочка: создание → поручение →
  коммиты → проверки (QA-интеграции — контракт-заглушка) → релиз (Updates
  releases — если есть привязка); единая timeline-структура.

### 11.3. Architect: данные для 2D-редактора

- Анализатор репозитория: файловая карта + граф импортов для TS/TSX и Rust
  (regex/lexer-уровень, без полноценного AST-инструмента — не добавлять
  тяжёлые зависимости): модули → файлы → импорты (внутренние/внешние).
- API: `GET /development/architect/:repoId/map?path=`: ноды {id, name,
  kind: file|dir|crate|module, path}, рёбра {from, to, kind: import|call?},
  метрики (число файлов, размер); сохранение пользовательских нод-позиций и
  ручных правок схемы (jsonb, по образцу canvas-layout).
- Сравнение фактической и проектной схемы: загруженная проектная схема (jsonb)
  vs фактический анализ → отчёт расхождений (лишние/отсутствующие связи).

### 11.4. MCP-доступ инструментов

- Динамический tools/list: инструменты Orion экспортируются как MCP-tools из
  module capabilities (модули декларируют agent-facing операции с permission
  strings); реестр собирает их, AgentGateway отдаёт агенту только разрешённые
  scope-арендой (существующий механизм — не дублировать).
- Инструменты задач 10 (search, commands) и 06 (knowledge) — проверить как
  образец интеграции; новые: git.graph (read-only), architect.map (read-only).
- Аудит каждого вызова через AgentAuditEntry.

## Критерии приёмки

1. Git-граф эталонного тестового репозитория (создаётся в fixture через git
   init + коммиты) возвращает верное дерево с ветвлением и слиянием (тест).
2. Commit message с `#42` создаёт привязку к задаче 42; ручная привязка и
   отвязка работают с правами (интеграционные тесты).
3. Architect map: на синтетическом TS-проекте находит N модулей и внутренние
   импорты; сравнение с проектной схемой находит вставленную лишнюю связь (тест).
4. MCP tools/list содержит новые read-only инструменты только при действующей
   аренде scope (тест).
5. Проверки из `00-README.md` зелёные; миграции с нуля PASS.
6. Отчёт-блок в `docs/STATUS.md`.

## Out of scope

Фронтенд (дерево, нодовый редактор), внешние Git-хостинги (GitHub API —
позже), push/fetch/опасные git-операции (только чтение), QA-v2/v3 в ядро
(только интеграционные контракты), локальные тесты-исполнители (Orion Dev
этап исполнения — следующий этап).
