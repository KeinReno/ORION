# 03 — Центр проектов: иерархия, шаблоны, портфель (backend)

**Зона ответственности:** `apps/api/src/projects/**`, Prisma-блок `BEGIN 03`,
миграции, тесты projects. **Волна:** 2. **Никакого фронтенда.**
Локальные документы: `docs/MODULES_AND_PLUGINS.md` (раздел 9 Projects),
`docs/platform-api/` (существующие контракты Projects), `docs/PROJECT_REFERENCE_CONTRACT_2026-10-25.md`.

## Контекст

План (раздел 4.1 переписки): полноценная рабочая область проекта + портфель.
Уже есть: `Project` (статус, приоритет, сроки, участники), `Milestone` +
`MilestoneDependency`, `ProjectStatusUpdate`, `ProjectLogEntry` (+Tasks),
`ProjectRelation` (типы связей проектов), архивация. Нет: дочерних проектов,
шаблонов, агрегирующего портфель-API, истории изменений.

## Задачи

### 3.1. Иерархия проектов

- `parentId` (self-ref, nullable) на `Project`: дерево с защитой от циклов
  (проверка предков при каждом назначении; цикл → 409 с путём).
- Семантика: дочерний проект наследует workspace и видимость родителя; права
  управления дочерним — отдельная проверка, наследование ролей не предполагается
  (явное членство).
- Индексы для ancestor-запросов (recursive CTE через Prisma `$queryRaw` —
  допустимо, вынести в репозиторий); ограничение глубины (max 6) — отказ с
  понятной ошибкой.
- События: `project.parent_changed`.

### 3.2. Шаблоны и дублирование структуры

- `ProjectTemplate` (workspace): имя, описание, набор элементов —
  milestones, задачи (с title/description/priority/estimate/status, без
  исполнителей и дат-конкретных значений — только сдвиги от стартовой даты),
  типы записей logbook, дочерние проекты (структура дерева сохраняется).
- `POST /projects/from-template`: создаёт проект + всю структуру в одной
  транзакции; даты вычисляются от переданной `startDate` (сдвиги по дням
  относительно шаблона).
- `POST /projects/:id/duplicate`: копия структуры (без исполнителей, комментариев,
  вложений-файлов — ссылки на документы не копируются, контент задач — по флагу
  `withContent`, по умолчанию false).
- Шаблон — не проект: отдельная таблица, отдельные права (`projects.templates.*`).

### 3.3. Портфель проектов (API агрегации)

- `GET /api/projects/portfolio`: сводка по всем проектам пространства —
  прогресс (по задачам), ближайшие дедлайны и просрочки, риски
  (проект без задач с датами; milestone без даты; зависимость от заблокированного
  проекта), загрузка по участникам (число открытых задач), распределение по
  статусам. Параметры фильтрации: участник, статус, дата-окно.
- Поддержка «архив»/«активные» режимов; heavy-агрегации — с пагинацией и
  явными лимитами (портфель может быть большим).

### 3.4. История изменений и решений

- Audit trail проекта: запись кто/когда/какое поле изменил (на базе domain
  events; чтение через endpoint `GET /projects/:id/history` с фильтрами
  по полю и периоду).
- Решения: тип записи `decision` уже частично покрывается Logbook (задание 05);
  здесь — только endpoint связывания истории с записями журнала (через
  EntityLink API задания 01 — НЕ дублировать таблицу).

## Критерии приёмки

1. Цикл parentId невозможен (попытка → 409, путь цикла в ошибке).
2. from-template создаёт полную структуру атомарно; при ошибке посередине —
  ничего не остаётся (интеграционный тест).
3. Portfolio endpoint возвращает консистентные агрегаты на тестовом наборе
  из fixture (прогресс, риски, загрузка) — сценарии зафиксированы в тестах.
4. Проверки из `00-README.md` зелёные; миграции с нуля PASS.
5. Отчёт-блок в `docs/STATUS.md`.

## Out of scope

Фронтенд, канбан-представления, ресурсы/бюджеты проекта (Finance-мост),
кросс-пространственный портфель, изменения ProjectRelation (существует),
двусторонняя синхронизация.
