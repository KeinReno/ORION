# 04 — Планирование: тайм-блоки, Гантт, матрица, учёт времени (backend)

**Зона ответственности:** `apps/api/src/planning/**` (нов.), `apps/api/src/time/**`,
`apps/api/src/events/**` (точечно), Prisma-блок `BEGIN 04`, миграции, тесты.
**Волна:** 2. **Никакого фронтенда.**
Локальные документы: `docs/TIME_CALENDAR_CONTRACTS_2026-10-25.md`,
`docs/TASK_TIME_BRIDGE_2026-10-25.md`, `docs/GOALS_PROJECTS_ATLAS_2026-10-26.md`.

## Контекст

План (разделы 4.4–4.9 переписки): календарь планирования, Гантт, матрица
Эйзенхауэра, управление фокусом, учёт времени. Принцип: **матрица, Гантт и
календарь — представления существующих задач, а не новые сущности.**
Уже есть: `Event` (календарь), `TimeEntry`, `TaskDependency`,
`SentReminder`. Есть поля в задачах importance/urgency (добавляются заданием 02)
— здесь только потребление, с graceful-фолбэком, если полей ещё нет
(опциональные в запросах).

## Задачи

### 4.1. Тайм-блоки планирования

- `PlanningBlock`: окно (start/end), опциональная привязка к задаче (nullable),
  тип (focus / meeting / buffer / personal), уверенность/фиксация (draft |
  committed), workspaceId + RLS.
- API: CRUD, перенос между днями (update окна), конфликт-детекция: пересечения
  с событиями календаря и другими блоками возвращаются в ответе (warning, не
  блокировка); событие `planning.block.moved` с оценкой «что затронуто».
- Идемпотентность операций переноса (clientMutationId/etag по образцу
  существующих CAS-механизмов).

### 4.2. Гантт-данные и критический путь

- `GET /api/planning/gantt?projectId=`: задачи проекта + зависимости +
  milestones в формате {id, start, due, estimate, dependencies[], milestone};
  без создания новых таблиц — выборка из существующих.
- Расчёт критического пути (CPM: forward/backward pass по depends_on) —
  endpoint возвращает `criticalPath: taskId[]`, `totalFloat` per task,
  `conflicts`: нарушения зависимостей (дочерняя раньше родительской даты),
  перегрузки по исполнителю (если есть assignee).
- «Оценка последствий переноса»: `POST /api/planning/reschedule-impact` —
  для задачи с новой датой возвращает затронутые зависимые задачи, milestones,
  блоки планирования и календарные события с величинами сдвига. Никаких
  изменений — только расчёт (dry-run семантика).

### 4.3. Матрица управления

- `MatrixPreset` (workspace): пары осей (xAxis/yAxis каждая — {field, kind:
  importance/urgency/priority/status/customFieldId}), набор пресетов:
  Эйзенхауэр (importance × urgency) — встроенный, неудаляемый; пользовательские
  пресеты CRUD.
- `GET /api/planning/matrix?presetId=&projectId=`: распределение задач по
  квадрантам — вычисляется запросом по полям задач (не хранится!). Запись
  назначения в квадрант — обновление полей задачи (importance/urgency) —
  одна сущность, много представлений.
- Кастомные оси на пользовательских полях задач — через TaskFieldDefinition
  (задание 02): если поля нет, ось недоступна (409 с объяснением).

### 4.4. Учёт времени

- Расширение `TimeEntry`: свободный секундомер (без задачи — уже поддержать
  явно), пауза/возобновление (pausedDuration учёт), ручная корректировка
  (edited flag + audit), плановое время (по задаче — estimateMinutes из
  задания 02, плюс отдельное plan на неделю — `TimePlan` (workspace, week,
  plannedMinutes) — отдельная таблица в блоке 04).
- Переключение между задачами: активный таймер один на пользователя —
  старт нового останавливает прежний (с событием).
- Аналитика: `GET /api/time/analytics?from=&to=&projectId=`: факт по проектам/
  задачам, план/факт, свободное vs привязанное время.
- Календарные контракты (`TIME_CALENDAR_CONTRACTS`) не ломать.

## Критерии приёмки

1. CPM на эталонном графе (fixture из 8 задач с ветвлением) возвращает
   правильный критический путь и float — тест против ручного расчёта.
2. reschedule-impact показывает цепочку затронутых объектов без изменений в БД.
3. Матрица: Эйзенхауэр-пресет распределяет задачи по квадрантам только выборкой;
   «запись» меняет поля задачи (интеграционный тест).
4. Два одновременных таймера у одного пользователя невозможны; старт второго
   закрывает первый (тест).
5. Проверки из `00-README.md` зелёные; миграции с нуля PASS.
6. Отчёт-блок в `docs/STATUS.md`.

## Out of scope

Фронтенд (DnD, рендеринг), синхронизация с внешними календарями, напоминания
(существуют), AI-перераспределение нагрузки (только фундамент данных здесь),
Rust-реализация оптимизатора.

## Примечание для будущей Rust-очереди

Автокомпоновка и оптимизация расписаний (переборные задачи: SAT-подобная
раскладка, минимизация конфликтов) — кандидаты на перенос в Rust-модуль
оптимизации. Паттерны: Simulated Annealing / Genetic Algorithm; ориентир —
`aryashah2k/metaheuRUSTics` (MIT), но API библиотеки заточен под непрерывные
benchmark-функции — для Orion нужны комбинаторные представления решения;
брать идеи и отдельные реализации, не подключая как core-зависимость.
