# 05 — Журнал проекта (Logbook): типизация записей (backend)

**Зона ответственности:** `apps/api/src/projects/**` (логбук-часть),
Prisma-блок `BEGIN 05`, миграции, тесты logbook. **Волна:** 2.
**Никакого фронтенда.**
Локальные документы: существующий плагин `projects-logbook` (default-full),
`docs/AI_REFACTOR_MIGRATION_MAP.md`.

## Контекст

Logbook уже реализован: `ProjectLogEntry` (наблюдения/решения/изменения),
`ProjectLogEntryTask` (ссылки на задачи с локальным комментарием),
межпроектные связи через `ProjectRelation`. План (раздел 7 переписки)
требует типизацию записей и автоматическую фиксацию изменений.

## Задачи

### 5.1. Типы записей

- Поле `type` на `ProjectLogEntry`: enum `observation | decision | hypothesis |
  result | incident | change`. Миграция существующих записей → `observation`.
- Семантика полей по типам:
  - `decision`: обязательное `rationale` (обоснование); опциональные
    альтернативы (jsonb список {option, whyNot}).
  - `hypothesis`: опциональный `verificationDue` (дата проверки).
  - `result`: ссылка на `hypothesis`/`decision` которое подтверждает/опровергает
    (optional FK в рамках того же проекта).
  - `incident`: severity (low/medium/high), опциональный resolution note.
  - `change`: source (`manual | event`) — см. 5.2.
- Валидация на уровне сервиса; несоответствие полей типу → 422 с картой ошибок.

### 5.2. Автозаписи из событий

- Подписка на доменные события (через domain-event-bus): изменение статуса
  проекта, завершение milestone, назначение исполнителя задачи проекта,
  изменение сроков → автоматическая запись `type: change` с `source: event` и
  ссылкой на исходное событие.
- Дедупликация: события при bulk-операциях группируются в одну запись
  (одна запись на bulk-применение, а не N).
- Автозаписи нельзя редактировать (read-only, удаляются вместе с проектом);
  ручные записи с `source: manual` редактируются автором и менеджером проекта.

### 5.3. Связи с материалами

- Прикрепление материалов (Knowledge, Documents, Notes) к записи — через
  EntityLinksService (задание 01): расширить запись jsonb-полем списком ссылок
  НЕ нужно — использовать универсальный слой связей; endpoint
  `GET /project-log/:id/related` агрегирует связанные сущности всех типов.

### 5.4. Фильтры и аналитика журнала

- Расширить списочный endpoint: фильтры по типу, автору, периоду, проекту
  (включая дочерние — recursive CTE по parentId), наличию связанных задач.
- Endpoint сводки: `GET /projects/:id/logbook/summary` — количества по типам
  за период, открытые гипотезы с просроченным verificationDue, инциденты без
  resolution, решения без привязанных результатов.

## Критерии приёмки

1. Типы: decision без rationale → 422; миграция старых записей в `observation`.
2. Автозапись создаётся ровно одна на bulk-операцию (интеграционный тест);
   read-only для `source: event`.
3. Связанные материалы читаются через EntityLinks без дублирования в таблице
   записи.
4. Проверки из `00-README.md` зелёные; миграции с нуля PASS.
5. Отчёт-блок в `docs/STATUS.md`.

## Out of scope

Фронтенд (лента, DnD), изменение ProjectRelation, преемственность между
проектами (уже есть через `continues`/`replaces`), экспорт журнала,
уведомления по записям.
