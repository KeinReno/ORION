# ORION-Rust — задания для параллельных бэкенд-агентов

Этот каталог содержит самостоятельные задания на бэкенд-реализацию модулей
KAIDEN Orion (фокус: Rust-направление; текущий стек backend — NestJS + Prisma +
PostgreSQL в `apps/api`). Каждый файл — отдельное задание для отдельного агента.
Фронтенд (`apps/web`, `packages/ui`) **в объём работ не входит**.

## Порядок чтения (обязателен для каждого агента)

Прежде чем писать код, агент читает в этом порядке:

1. `AGENTS.md` (корень репозитория) — обязательные правила и проверки.
2. `ORION_CONSTITUTION.md`.
3. `docs/PLATFORM.md` — утверждённое направление (Platform 1.0, Stage 0).
4. `docs/STATUS.md` — что код реально делает сегодня.
5. `docs/MODULES_AND_PLUGINS.md` — модель модулей/плагинов/связей.
6. `docs/AI_REFACTOR_MIGRATION_MAP.md` — кто чем владеет; классификацию не менять.
7. Свой файл задания из этого каталога + локальные документы, перечисленные в нём.

## Железные правила (все задания)

- **Миграция Orion Classic исключена.** Ничего не делать для переноса Classic → Rust:
  ни мастеров, ни совместимости БД, ни staging-импорта Classic. Резервное
  копирование, восстановление и миграции схем внутри самого Orion сохраняются.
- **Parity before redesign.** Нельзя одновременно менять UX-контракт, модель данных
  и «заодно» переписывать соседний модуль. Существующие API и данные не ломать.
- **Core → Contracts/SDK → Modules → Extension Points → Plugins.** Обратных
  зависимостей нет: модули не импортируют внутренности друг друга. Межмодульное
  взаимодействие — только через публичные контракты/SDK, модель `EntityLink`
  (`apps/api/prisma/schema.prisma`) и шину `domain-events`.
- **Один объект — много представлений.** Не создавать параллельных хранилищ одной
  сущности. Новые «представления» (матрица, Гантт, холст) работают с теми же
  таблицами через API/запросы.
- **Workspace-scoping и RLS обязательны.** Любая новая таблица: поле
  `workspaceId`, миграция с RLS-политиками по образцу существующих, доступ через
  Prisma с проверкой членства пользователя в пространстве.
- **Права.** Новые операции регистрируют permission-строки по образцу существующих
  (`tasks.read`, `projects.manage` и т.п.); опасные операции — с явным подтверждением.
- **События.** Значимые изменения публикуются в `domain-event-bus`
  (`apps/api/src/domain-events/`). Подписок на чужие внутренние сервисы нет.
- **Агентный доступ сразу.** Новые инструменты проектируются так, чтобы позднее
  выдать их агентам через MCP (`apps/api/src/mcp/`) без переделки.
- **Отключаемые модули.** Фоновые задания/таймеры модуля не работают, когда модуль
  выключен в workspace (см. `apps/api/src/modules/`); при отключении ничего не
  удаляется.
- **Plugin contracts не ломать.** `pnpm plugin-contract-check` (сейчас 11 тестов,
  контракт tasks 1.5.0) обязан остаться зелёным; слоты и версии менять только
  через регламент репозитория.

## Технические требования к сдаче (каждое задание)

1. Всё — в одной ветке от актуального `master`. Агент работает только со своими
   зонами файлов (перечислены в задании). Общие файлы (`schema.prisma`,
   `app.module.ts`) — конфликтные: править минимально, добавлять, не переставляя
   чужое. Новые Prisma-модели — строго в конец `schema.prisma`, в блок
   `// --- BEGIN <task-id> ---` / `// --- END <task-id> ---`.
2. Обязательные проверки перед сдачей:
   - `pnpm --filter api typecheck` (и web, если затронуты общие типы);
   - `pnpm lint` — 0 errors, warnings не добавлять;
   - `pnpm architecture-check` — зелёный;
   - `pnpm plugin-contract-check` — зелёный;
   - `pnpm module-docs:check` и `pnpm platform-map:check` — зелёные;
   - unit-тесты новой логики + прогон затронутых сьютов;
   - интеграционные тесты на временной PostgreSQL (`node scripts/postgres.mjs`,
     порт 5433): все миграции применяются к чистой БД, сценарии задания PASS;
   - production build API.
3. Тесты пишутся на реальную БД там, где меняется схема; моки — только для
   внешних систем.
4. В конце — краткий блок-отчёт в `docs/STATUS.md` по образцу существующих разделов
   (дата, факты, проверки, ограничения; без маркетинга).
5. Коммиты — по истории репозитория, один логический коммит на веху задания.

## Не делать (всем)

- Не запускать подагентов и не менять чужие зоны.
- Не менять дефолты включения существующих плагинов (default-full parity).
- Не удалять и не «чистить» чужой код и данные.
- Не трогать `orion-rust/` (Rust runtime), `apps/desktop`, инсталляторы.
- Не ставить новые npm-зависимости без явной необходимости; если критично —
  обосновать в отчёте.
